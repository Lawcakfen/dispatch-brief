# 发布管道：一份源 → 两个出口

> 自用版是**源**，公开版是**产物**。方向单向，绝不倒推。
>
> ★ 每次汇报都要先说清「这次改的是哪一边」—— 用户问过一次「这次改的是公开版吗？」
> 就是因为源和产物长得几乎一样。不先说，他必然要问。

## 0. 两个目录，角色不同

| 路径 | 角色 | 能不能手改 |
|---|---|---|
| `skills/productivity/dispatch-brief/` | **源**（含真名、内部账本） | ✅ 只改这里 |
| `repos/dispatch-brief/` | **产物**（脱敏，由脚本生成） | ❌ 改了下次生成被冲掉 |

**产物 ≠ 镜像**，两处不对称必须记住：

```
公开版少   publishing-status（内部账本，build_public 按来源标记跳过）
公开版多   scripts/ README LICENSE docs（不在生成范围，手工维护）
```

## 1. 脚本分工

```
publish-map.json    脱敏词表（人名/品牌/客户/三种路径写法）。长词自动排前。
build_public.py     生成公开版：删私有块 → 跳过内部账本 → 换词 → 换旧文件名 → 自检
                    自检不过 → 一个文件都不写
build_plan()        对外暴露「公开版每个文件应该是什么」，供逆推检查复用
verify_public.py    轻量把关：私有词/死链/旧文件名/frontmatter
audit_deep.py       深度审计 A(自用) + B(公开) + C(逆推) + S(文档↔代码一致)
verify_all.py       总入口：结构审计 + 单测 + 服务探活
check_drift.py      每日：只查会自己变坏的 4 件事，全正常静默
weekly_audit.py     每周：一行心跳，用来发现「检查器自己坏了」
backup_skill.py     自用版 git 提交 + git bundle 单文件备份（留最近 10 个）
make_dist.py        打包「轻版」给朋友：方法通读 + 坑清单 + 指令模板 + 一页说明
```

## 2. 改完内容的四步

```bash
python build_public.py      # 生成；自检不过就不写
python verify_all.py        # 结构 + 单测 + 服务
git -C repos/... diff       # ★ 人眼看一眼 —— 这步不能自动化
git -C repos/... push
```

**★★★ 第三行不能省。** 实测过一次：私有词 0、死链 0、旧名 0 全绿，但内部账本
照样被发到公开仓库上 —— 因为它不含私有词，只是「不该公开」。**门禁全绿 ≠ 内容正确。**

## 3. 检查分三层（不是所有检查都该每天跑）

```
改完 / 发布前   verify_all.py        全量
每天 09:00      check_drift.py       只查：源改了没发布 / 本地远端分叉 / 服务死了 / 备份过期
                                     全正常时【一个字都不输出】
每周一 09:30    weekly_audit.py      一行结论，发现检查器本身坏了
```

**★★ 结构审计查的是「自洽」，内容不变时永远绿。每天推一条「全部通过」= 训练用户忽略。**
会自己变坏的才值得定时查；自洽只有「你动了」才会变。

## 4. 最狠的一条：逆推（C 轨）

```
repo 里每一个生成文件 == build_plan(自用版)
```

一条检查同时抓三种病：

```
① 有人手改 repo（下次 build 静默冲掉）
② 改了源但忘了重跑生成（repo 落后）
③ 生成器漏了某个变换（产物和源对不上）
```

它逼出了「README 里有假数字」这类问题 —— 因为 README 不在生成范围，一比就露。

## 5. 实测踩过的六条（都是静默错误）

**① 改名脚本连「来源标记」一起改 → 内部账本被公开**

```
build_public 靠一行来源标记决定跳过哪段（形如 HTML 注释 + 来源 编号/总数 + 源文件名）
但改名脚本把标记里的文件名也改了 → 标记失效 → 内部账本发出去（22KB→29KB）
★ 而私有词检查是绿的（它确实不含私有词）
修法：改名只作用于【正文】，绝不碰标记行。
```

**② 删了源又重跑生成器 → 产出空壳且「成功」退出**

```
10 份 references 全被写成空壳（合计 421 行 / 坑清单 0 条），退出码 0
修法：生成器自己校验源总行数 < 8000 就中止，不写任何文件。
     是 verify 的「没丢内容」那条（新旧行数比 0.71）抓到的。
★ 生成器必须自己知道「源丢了」，而不是等下游发现。
```

**③ 词表只覆盖一种路径写法**

```
有 <库根>（双反斜杠）/ <库根>（正斜杠）
漏了 <库根>（单反斜杠）→ 自检拦下
修法：三种写法都要进词表；路径类还要单独加「路径段」正则，见 10-检验标准 §检查器会撒谎
```

**④ 在 README 里写「Files: 18」当历史引用**

```
我为了说明「删掉了旧角标」，把那个数字原样写进说明 → 等于自己留了个假数字
被自己的 B5 门禁抓到
修法：任何地方都不写死可变数字，连「历史值」也别写。
```

**⑤ README / scripts 不在生成范围 → 会漂移**

```
实测：README 写着「SKILL.md 402 行」「不含实现代码」，全是旧的
修法：README 不写数字；scripts 手工同步，并在逆推里核对「repo 里的文件集合 == 计划集合」
```

**⑥ 用户分不清「改的是源还是产物」**

```
他问过：「这次修改的是公开版的 super-agent 是吗？」
真实情况：内容改源（自动生成），但 README 和 scripts 是直接改在 repo 里的
修法：汇报时永远先说「这次改的是哪一边」，并把「手改例外」单独列出来
```

## 6. 改名一个 skill 的正确顺序

**★ 改名前先查 GitHub 有没有撞名** —— 用 `api.github.com/search/repositories?q=<name>+in:name&sort=stars`。
实测：

```
agent-manager    wainmann/agent-manager    701★   今天是活跃产品
agent-foreman    mylukin/agent-foreman     249★   也在讲「完成度/验收」
foreman          ddollar/foreman          6164★   进程管理器
dispatch-brief   只有 0★ 的相似项          ← 选了这个
```

**判据不是「有没有同名」，是「会不会被误认成那个东西」。** 用通用词（manager / agent）命名
专有方法，注定被淹；用这套方法独有的词（dispatch / brief）才站得住。

改名步骤（漏一步就会静默坏）：

```
① 先确认 git 工作区干净（改了才移，能回滚）
② mv 目录（.git 会跟着走）
③ 写替换脚本：保护「仓库名」这种里层含旧名的字符串（用占位符），否则会变成 xxx-brief-writing
④ 扫全部脚本，不只 skill 正文（实测 11 个脚本、23 处）
⑤ 连带改名：备份文件前缀（否则每日检查误报「没有备份」）、分发目录、打包名
⑥ 更新两个旧指针 skill 的对照表（skill_view(name='新名')）
⑦ 更新 memory 里那条「X=新单一入口」
⑧ build_public → verify_all → 两边提交
```
