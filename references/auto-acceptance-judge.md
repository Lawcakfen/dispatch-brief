## 一、为什么是「脚本 + 按需起 LLM」，不是「agent cron」

| 方案 | 空跑成本 | 判断质量 | 结论 |
|---|---|---|---|
| 每 15 分钟 agent cron | 32 次/天 × 3–5k token，其中 30 次白烧 | 有 | ✗ |
| 每 2 小时 agent cron | 12 次/天，90% 白烧 | 有 | △ |
| **no_agent 快路 + 事件触发 judge** | **0**（无事件纯脚本 0.5s） | 有 | ✓ |

**★★ 关键事实：`hermes -z` 已经能被 Python subprocess 调用**，所以不需要 cron 级联。

```python
import shutil, subprocess
HERMES = shutil.which("hermes") or "<venv>\Scripts\hermes.exe"   # 按你的安装位置改
r = subprocess.run([HERMES, "-z", prompt, "-t", "file,terminal"],
                   capture_output=True, text=True, timeout=200,
                   encoding="utf-8", errors="replace")
```

**实测耗时：**
```
空 prompt（-t ""）　　　　　　 6.8 – 10.7 秒
真判断（-t file,terminal）　　164.7 秒
```

**★★ 164 秒决定了必须加锁**（见第四节）。

## 四、锁：判断跑 164 秒，必须防重叠

```python
LOCK = os.path.join(CACHE_DIR, "judge.lock")   # ★ CACHE_DIR 在文件顶部 CONFIG 区定义

def acquire_lock():
    """拿不到锁就降级（只报事实，不给判断），绝不阻塞。"""
    if os.path.exists(LOCK):
        if time.time() - os.path.getmtime(LOCK) < 600:   # 10 分钟视为僵死
            return False
        os.remove(LOCK)
    open(LOCK, "w").write(str(os.getpid()))
    return True

def release_lock():
    try: os.remove(LOCK)
    except Exception: pass
```

**★★ 降级文案要给用户看懂**，不要静默吞掉：

```
（这轮判断没跑起来 —— 可能上一轮还在跑。事实已报，判断下次补。）
```

## 五、和 wb_watch 的接法（三个要点）

### ① 一次扫描里同一项目的多个完成事件，合并成一次判断

```python
by_proj = {}
for e in events:
    by_proj.setdefault(e["proj"], []).append(e)

judged = {}
if events and acquire_lock():
    try:
        for proj, evs in by_proj.items():
            files = J.scan_recent(os.path.join(pw.ROOT, proj))
            mem, _ = new_memory_text(...)
            judged[proj] = J.judge(proj, evs, mem, files)
    finally:
        release_lock()
```

**★ 不合并的话，一次扫描打 3 个勾 = 调 3 次 LLM = 500 秒。**

### ② 同轮既有「动了」又有「完成」→ 省掉「动了」

```python
done_projs = {e["proj"] for e in events}
beats = [b for b in beats
         if not (b["kind"] == "start" and b["proj"] in done_projs)]
```

**★ 否则用户会同时收到「▶ 它动了」和「✅ 完成了」—— 前者是纯噪音。**

### ③ 判断失败不能影响打勾

**打勾在调 judge 之前就已经写盘了。** judge 挂了只是少一段判断，
**队列状态不受影响** —— 这是「宁可漏判断，不可错打勾」的落地。

## 六、沙盒测试配方（7 项，缺一不可）

```python
# 用 mock 替掉 judge，避免每次测试烧 164 秒
CALLS = []
def fake_judge(p, items, mem, files, verbose=False):
    CALLS.append({"proj": p, "n_items": len(items), "n_files": len(files)})
    return "【看起来完成了什么】\n…"
import judge as J
J.judge = fake_judge
W.J = J
```

| # | 造的场景 | 期望 |
|---|---|---|
| 1 | `--init` 建基线 | stderr 提示，**不产生任何事件、不设标记** |
| 2 | 追加一段 memory（WB 动了） | ▶ 报一次「动了」+ 摘要 |
| 3 | 再追加一段（同单继续写） | 静默 |
| 4 | 追加完成信号 | ✅ 打勾 + 出判断（CALLS 长度 1） |
| 5 | 队列空后再追加 | 静默 |
| 6 | 新派一单 | 静默（刚开始等） |
| 7 | 手动改 `__pending_since` 为真 5 小时前 | ⚠ 报「卡住了」，且只报一次 |

**★★ 加测：手动建 lock 文件 → 应只报事实，CALLS 长度 0。**

**★★★ 造超时数据必须用 `datetime.now() - timedelta(hours=5)`，
手写时间串会写成未来时间，测不出「卡住」（这个坑实际踩过）。**

### 外部改队列检测的三关（2026-11-15 新增，缺一不可）

| # | 造的场景 | 期望 |
|---|---|---|
| A | 正常完成（只追加 memory，不碰队列） | ✅ 打勾 + 出判断，CALLS 长度 **1** |
| B | 派两条待发 → 建基线（**什么都不做，空转一轮**） | **静默** —— ★ 这一关专门抓「自己打的勾被当成外部修改」 |
| C | 外部把一条 `- [ ]` 改成 `- [x]` 并贴报告，**不写 memory** | ⚠ 报「队列被外部改了」，CALLS 长度 **0** |

**★★★★ B 关是最容易被跳过的那一关，而它恰好抓的是实现 bug。**
第一版没有 B 关的话，场景 C 会「通过」，但线上每完成一次就会误报一次 ——
**因为 A 关打完勾后，那条在下一轮看起来就是「消失了」。**

**★★ 判定顺序很重要**：先跑 A（验证打勾链路），再跑 B（验证基线时机），
最后跑 C（验证报警）。**B 必须在 A 之后跑才有意义** —— 它测的就是 A 留下的状态。

**★★★ 造「外部修改」最省的办法：直接重写整个队列文件**，
不要用 `Q.tick_item` —— 那个函数会生成合法格式，测不出「格式不像 cron 打的」。
外部修改的特征是**续行是 ①②③ 报告，不是原指令**。

### ★★★★★ 两个「测试自己骗自己」的坑（2026-11-15 端到端实测）

**坑 ①：场景「完成」没打勾 —— 我第一反应是判据有 bug，其实是测试用例不真实。**

```
我造的 memory：已完成按钮改色，三个按钮都改了，自检通过。
真实的指令：  v9 测试任务：把按钮颜色改成红色

→ 完成信号 ✓，但中文短语重合只对上 1–2 个（阈值 ≥4）→ 匹配失败 → 静默
```

**★★ 判据是对的。要让完成场景真的触发打勾，memory 必须写成真 WB 的样子 —— 带指令里的词。**

```python
# ✗ 太简略，测不出打勾链路
"\\n## 11:00\\n\\n已完成按钮改色，三个按钮都改了，自检通过。\\n"

# ✓ 带任务名 + 动作 + 参数，重合度够
"\\n## 11:00\\n\\n已完成 v9 测试任务：把按钮颜色改成红色。"
"三个按钮都改成 #C4362F 了，自检通过。\\n"
```

**★★★★★ 这一条同时是【指令侧】的规则**：每份指令都必须要求执行方在 memory 里
写下「带本批任务关键词」的那句话。详见 SKILL.md §0.3.2。

**坑 ②：多场景用例不连贯 → 检测器正确报警，我当成 bug 去查代码。**

```
场景 5a：write_q(["v10", "v11"])      ← 基线有 v10 v11
场景 6a：write_q(["v12"])             ← 我本意是「再派一条」，实际把 v10 v11 全删了

```

**★★ 固定写法：每个场景只【增】不【替换】。**

```python
def add_items(*new):          # 比 write_q 安全
    q = Q.parse_queue(QP)
```

**★★★ 判据：沙盒里出现「意外报警」→ 先回看自己上一场景留下了什么，再怀疑代码。**

### 已实现（2026-11-15，沙盒三关通过）

**条目指纹**（`queue.py`）：

```python
def fp(item):
    """条目指纹：去日期前缀和 **，取前 24 字，用于跨轮对比。"""
    t = item["text"] if isinstance(item, dict) else str(item)
    t = re.sub(r"^\*\*[\d\-]+\*\*\s*", "", t).replace("**", "").strip()
    return t[:24]
```

**扫描早期：只读不写**

**第一版就是上面那个设计草图 —— 在扫描早期写 `__last_pending`。**

```
后果：本轮 tick 掉的条目，在下一轮对比时变成「消失」
   → 被判定成外部修改 → 误报

实测表现（沙盒场景 B）：

  → 报警「v9 测试任务从待发消失」   ← 那是我自己上一轮打的勾
```

**★★ 这就是「监测器自己的写入」污染了「监测器的判据」—— 跟持久化 baseline
必须写回（§六 项 1）是同一类错：内存里的旧值比磁盘上的新值晚一步。**

**★★★ 泛化判据：任何「diff 检测」都要问 —— 我用来对比的基线，是在我的写操作之前还是之后取的？**
**在之前 → 我自己的写会被当成外部变更。**
