# 项目组合监管

**用途**：一个账号下几十个项目目录（`Outputs/projects/`、任何 workspace 集合），用户想知道「哪些在动、哪些悬着、哪些其实已经死了」，还要每天/每周有人盯着。

**核心风险先说**：★★★ **每天把 29 个项目全报一遍 = 第二个待办清单**。用户看三天就忽略，第七天开始烦。这跟他已有的 Xboard 24 条待办、工作台 53 条待发，是同一个病。

```
★ 监管第一原则：默认不说话，只有异常才说。
```

---

## 0. 两层结构（照这个搭，别搭成一层）

| 层 | 频率 | 范围 | 目的 |
|---|---|---|---|
| **日监管** | 每天 **06:20** | ★ 只盯 3–5 个「主线项目」+ 新出现目录 | **昨天**有没有偏离 |
| **周监管** | 每周一 | 全量扫 | 哪些已经死了 |

**★★★ 时间是用户定的，不是我定的（2026-11-12 被他直接改掉）**：我建议 20:30（「晚上还能补救」），他一句话改成 **06:20**。
→ **不要再劝回晚上。** 他要的是「早上看昨天」，理由是他自己给的：**一天还没开始，不会被“今天又没做成”压着。**
→ **但代价要照实说一句**（说完就按他的来，不反复）：**早上报，有些事发现时已经晚了一天。**

## 1. 主线白名单（必须用户自己定，不许替他定）

```markdown
| # | 主线项目 | 为什么是它 |
|---|---|---|
| 1 | <客户项目 A> | 唯一的 B 端付费项目，正在跑 |
| 2 | <客户项目 B> | A 类客户，已停 26 天 |
| 3 | <内容/运营项目> | 内容出口 |
| 4 | <产品资产> | 等审核/等发布 |
| 5 | <本季收钱线> | 见 §3，通常需要单独建目录 |
```

**★★ 其余 20+ 个不进日监管** —— 周监管时看一眼，够。

## 2. 四档（不用 AI 判断，纯时间算）

```
0–2 天　　在动
3–7 天　　慢下来了
8–20 天　 悬着
21 天以上 ★ 事实上停了（不管他嘴上怎么说）
```

**★★ 第四档是关键**：**它不问“你的想法”，只看“你的行为”。** —— 这就是「暂停与结束清单」的自动化版本。

## 3. ★★★ 两个必踩的洞

### 洞① 主线没有目录 → 永远扫不到

```
「4 家诊断 + 2 家报价」在 Outputs/projects 下没有对应目录
→ 脚本永远看不见它 → 它的「悬了几天」永远是 0 ✓✓
```

**这是「没有形状的东西做不动」的技术版本。**

**修法**：先给它建一个目录 + 两个空表：

```
Outputs/projects/<本季主线>@Hermes/
├── 诊断记录.md    ← 每家三行（谁 / 卡在哪 / 我说了什么）
└── 报价记录.md    ← 每次开口一行（对谁 / 多少 / 结果）
```

**★★ 有了文件，“主线有没有在动”才变成可扫描的事实。**

### 洞② mtime ≠ 进度 —— ★★★ 已被要求升级，解法在 §3.1

一个项目改了很多文件，可能只是格式化、批量替换、或 Agent 的自检脚本刷了一遍。**mtime 只能证明“有人碰过”，证明不了“推进了”。**

- ★ 底线：**mtime 只用于报警，不用于评价**。报告只说「3 天没动」，不说「进度慢」
- **但如果用户嫌「只统计跑了几轮」太粗（他 2026-11-12 明确提了这个要求）** → 见 §3.1
- **★★★ 如果他进一步要「每个项目现在到哪了 + 接下来什么建议」（2026-11-13 就是这样）→ 必须跳到 §3.2，纯脚本到这一步就不够了**

### 3.1 ★★★★ 从「动没动」升级到「动到哪一步」（2026-11-12 落地）

**他的原话**：「要**精简补充每项任务的具体进度**，不仅是统计跑了几轮。」

**★★★★ 关键：这件事不需要 LLM。** 纯脚本就能说人话，**token 仍然 = 0**（`no_agent=True` 的 cron）。

**三层机制，缺一不可：**

| 层 | 做法 | 产出 |
|---|---|---|
| **① 文件级 diff** | state 里存每个项目的 `{相对路径: mtime}` 字典；每次跑算 **新增 / 修改 / 删除** | `新增 2 个（文件b.md、文件c.md）；改了 1 个（展示形式预览.html）` |
| **② 进度文件内容 diff** ★★★ | 文件名含 `版本记录 / 进度 / README / 工作记录 / 进展` 的 `.md`，取**最后 3 行非空文本**存进 state；下次跑只报**新增的那句** | `版本记录.md：25 处待补已降到 12 处` |
| **③ 阈值提醒** | 主线 3 天 / 客户 2 天 / 7 天建议暂停 / 21 天建议关闭 | `🔴 客户停滞：客户 B 已 28 天` |

**★ 第 ② 层是灵魂** —— 它让报告从「改了 1 个文件」变成「**25 处待补已降到 12 处**」，那才是他嘴里的“具体进度”。

**★★ 第 ② 层最容易写错：只报新增的行，不要报整个 tail。**
```python
old_set = set(x.strip() for x in old_tail.split(" / ") if x.strip())
new_lines = [x.strip() for x in new_tail.split(" / ")
             if x.strip() and x.strip() not in old_set]
```
✗ 报整个 tail → 输出变成 `进度记录.md：初始内容 / 第三轮：报价单已发出` ← 旧内容混进来了
✓ 只报差集 → `进度记录.md：第三轮：报价单已发出` ✓

**★ state 体积要设上限**：某小程序项目 **10,166 个文件** → 每项目只保留**最近修改的 N 个**（实测 `MAX_FILES_PER_PROJ = 400` 够用，state 仍很小）。

**成型脚本**：`templates/project_watch.py`（290 行，顶部一个 CONFIG 区改路径即可）

### 3.2 ★★★★★ v3：脚本采集事实 + agent 写判断（2026-11-13 他改口要的版本）

**§3.1 那版（纯脚本、token=0）不是终点。** 他第二天就升级了要求：

> 「**每一个项目的进度，都汇报** —— 这个项目现在什么进度了，**接下来你有什么建议？**」

**★★ 这已经是【判断】，纯脚本做不到。架构必须拆两层：**

| 层 | 谁 | 干什么 | token |
|---|---|---|---|
| **事实层** | 脚本 | 文件 diff + 进度文件 + **WB 工作日志** + 历史记录 | 0 |
| **判断层** | agent | 每个项目写「现在到哪了」+「下一步建议」 | ≈5k/次（月 ≈¥0.5） |

**★★★★ 分离的理由一句话：事实不能被 AI 编，判断不能被 diff 限制。**

**实现方式**：cron 用 `script` + `prompt`（**不要** `no_agent`）—— **script 的 stdout 自动注入 prompt。**

**⚠️ 必踩的坑：cron 的 `script` 字段不接受参数。**
```
script: "project_watch.py --evidence"  →  报 Script not found
```
→ **修法：脚本【无参数时默认】输出证据包**，`--init` / `--dry` / `--diff` 走别的分支。
→ ★ 症状：agent 会自己读文件硬撑出一条报告，看起来正常，**其实证据包根本没注入** —— 一定要 grep 输出文件确认 `项目证据包` 出现过。

**证据包的结构（顺序不能换）：**

```
1. 结论三件套：最后修改时间 / 停滞天数 / 文件总数
2. 今日变动：新增·修改·删除，带文件名（最多列 6 个）
3. 最近改动的 5 个文件（用来判断"在做什么"）
4. 进度类文件尾部原文（版本记录/README/进度）
5. ★★★ WB 的工作报告 .workbuddy/memory/<日期>.md —— 最权威，单独标出
6. 历史记录（总表里该项目最近 2 条 = 上次汇报过的）
7. 其余项目只给概览：7 天内在动 / 8–20 天 / 21 天以上名单
```

**★★★★ 第 5 层是整个方案的关键**（详 `wb-obsidian-deploy`）：**执行 Agent 一直在写工作日志，不读它等于白搭。**
**没有这份日志的项目，证据包要显式写一句「⚠️ 无 WB 工作日志，只能靠文件变动推断，判断要保守」** —— 否则 agent 会过度自信。

**prompt 五条硬规则（缺一条报告就废）：**

```
① 不许编 —— 证据里没有的，写「证据不足，需要看 <具体文件>」
② 不许重复 —— 和上次一样就写「同上次，还没动」，【不许换一种说法把同一件事再说一遍】
③ 建议必须是今天能做的动作
   ✗ 继续推进 / 加强跟进 / 完善内容 / 保持节奏
   ✓ 给客户 C发一条微信：小程序做下来大概 800，你看合不合适
④ 该停就直说，不为礼貌绕开
⑤ 在等外部的项目，明确说「在等 X 审核，不是停滞」
```

**输出格式**：每项目两行（现在 / 建议），**客户项目排最前**，停 21 天以上只列名单不逐个写。

**★★★★ 不要替用户收敛优先级 —— 但只禁一句话不够，见 §3.11 ②。**

```markdown
## ★★ 绝对不要替泽哥收敛优先级

**禁止出现的措辞（含任何同义变体）**：
「今天只做这一件」「今天只做一件事」「优先做…」「先做这个」「最该做的是…」
「建议你今天…」「唯一要做的…」

**理由**：他 2026-11-13 明确关掉了「今天只做这一件」模块。
2026-11-14 检查发现，写成「今天只做一件事：」等于换个字绕过规则 —— 性质没变，都是替他拍板。

**正确做法**：每个项目各给一条**平等的**建议，**哪件先做由他自己判断**。
你只负责说清「这个项目现在缺什么动作」，不负责排序、不负责收成一件。
```

**★★ 第 ② 条是他最在意的** —— 项目没动的时候，报告最容易变成「每天换句说法讲同一件事」，那比不报还烦。

##### ★★★★★ 致命坑：截断会漏掉 91%，而且会导致建议过时

```python
# ✗ 我最初的写法：取前 N 字
txt = txt[:900] + "…（已截断）"
```

**实测后果**（客户 A 11-13，报告含大量表格）：

```
原文 9,725 字 → 只读前 900 字 = 看到 9%
漏掉的那 8,825 字里，包含：
  ## 01:15 泽哥拍板，四条全部执行
  ## 泽哥「1、按A。2、报价公开」→ 报价按 PPT P34 原文公开
  ## 01:50 泽哥「可行。做到小程序中」→ 统一品牌分享图落地
→ ★★★★ 于是我在 _给WB.md 里写了「logo 待泽哥确认」
  而他凌晨 1:15 就拍完板、并且全部落地了 ✓✓
```

**★★★★ 泛化：报告长度不可预测（表格/代码块多的能到 1 万字）。按字数截断 = 内容随机丢失一半。要按【结构】压缩。**

```python
def condense(txt, maxchars=1800):
    """把报告压成骨架。★★ 保证【所有小节标题】都在 —— 进度全在标题里。

    ⚠️⚠️ 2026-11-20 事故（上一版害的）：上一版结尾是 `s[:maxchars]` 硬截，
       注释却写「★ 标题全留」—— 那句话是假的，预算用完就停。
       实测 24,268 字 → 1,212 字时只截到「## 01:20 B2 交付回报」，
       后面的 `## 01:30 B3 交付回报` / `## 01:35 B4+B5 交付回报` 整段消失
       → 判断层写出「B3 尚未接入 render」，而事实是 B3/B4/B5 早已交付、
         项目当天已推进到 v10。
    """
    # ① 先按 ## 分节
    sections, cur_t, cur_l, in_code = [], None, [], False
    def flush():
        if cur_t is not None:
            sections.append((cur_t, cur_l[:]))
    for raw in txt.split("\n"):
        s = raw.strip()
        if not s: continue
        if s.startswith("```"): in_code = not in_code; continue
        if in_code: continue
        if s.startswith("|"): continue
        if s.startswith("## "): flush(); cur_t, cur_l = s, []; continue
        if s.startswith("#") and cur_t is None: cur_t, cur_l = s, []; continue
        if cur_t is None: cur_t = "（开头）"
        cur_l.append("- " + s[2:][:46] if s.startswith(("- ", "* ")) else s[:66])
    flush()

    # ② 逐档降级：标题 + 每节 3行 / 2行 / 1行 / 0行 —— 第一个放得下的就用
    for keep in (3, 2, 1, 0):
        out = []
        for t, ls in sections:
            out.append(t)
            out.extend(ls[:keep])
        body = "\n".join(out)
        if len(body) <= maxchars:
            return body

    # ③ 连标题都放不下才硬截 —— 且必须明说被截了，不许让人以为读全了
    body = "\n".join(t for t, _ in sections)
    if len(body) > maxchars:
        body = body[:maxchars] + "\n…（★ 标题超预算已截断，后面还有 %d 节没读到）" % len(sections)
    return body
```

**实测效果**：9,723 字 → 约 1,800 字，**所有小节标题一个不少**；本次事故那份报告改完 1,212 字 → 约 4,500 字（预算同时从 2400 提到 9000，每份均分 4500），B3/B4/B5 全部回来了。

**★★★★★ 三条泛化（这一类 bug 的通则）：**

```
① 「先拼完再截尾」的压缩器，本质还是按字数截断 —— 只是把截断点挪到了后面。
   要按【结构】降级（标题优先、内容按预算减行），不是拼完再切。
② 注释里写「保留全部 X」而代码做不到，是最坏的一种注释：
   它会安抚你、让你不去测 —— 本次就是照着那句注释以为没问题。
③ 压缩器必须能自我报告「我截了」。截断而不说 = 让判断层以为自己读过全文。
```

**★★ 推论：任何「压缩/摘要/骨架化」函数，验收标准不是「体积变小」，是「最后一节的标题还在吗」。**
**小一大时的自查：`condense(txt, 1200)` 里 grep 一遍原文最后一个 `## ` 标题 —— 搜不到就是还在按字数截。**

##### ★★★ 读【最近 2 天】，不是只读最新一份

**用户的追问逼出来的**：「如果今天写了 3 段、昨天第 4 段有重要内容 —— 昨天的我读不到。」

```python
cands.sort(key=os.path.getmtime, reverse=True)
picks = cands[:2]                    # ★ 2 天
budget = maxchars // len(picks)      # ★ 预算均分，总量可控（2400 → 各 1200）
```

**★ 只读 1 天的失效场景**：执行 Agent 昨天干完一件大事、今天只做小修 → 我只看到小修，判断必错。
**★★ 实测**：某项目读了 11-13（9723 字）+ 11-12（7279 字），压成 2530 字，跨天不漏。
**★★★ 成本**：证据包约 1 万汉字 ≈ 16k tokens/次，月约 ¥1。**翻一倍换「不漏」，值。**

**★★ 证据包里要显式写出来源和压缩比**：`（文件 2026-11-13.md，原文 9723 字 → 压缩为 1812 字，保留全部小节标题）`
—— 让判断层知道「这是骨架，细节在原文里」，它就不会假装读过全文。

##### ★★★ 读完日志必须回写 `_给WB.md`

**日志是「已完成的事实」，队列是「待发的指令」—— 两者不对齐，队列第二天就过时。**

实测：读完发现 logo 已落地 → 立刻把 `_给WB.md` 里那条从「logo 待确认」挪到 `✅ 已完成`，待发只剩「占位符总清单」。
**★ 不做这一步，用户会照着过时的队列去催一件已经做完的事。**

### 3.2.2 ★★★★★ 证据链完整性：截断有【三层】，修一层等于没修（2026-11-20）

**背景**：§3.2.1 那个 `condense()` 硬截修完，判断还是错的 —— 因为**同一条链路上还有第二处截断**。

#### 三层，全都要查

```
① 压缩器内部    condense() 里的 s[:maxchars]          ← §3.2.1 修的那一层
② 调用方传参    judge_one() 里的 evidence[:6000]      ← 修完①之后它成了新瓶颈
③ LLM 读的顺序  报告是「按时间正序」的，最新状态在【最后几个小节】
                → 只看前面就下结论，等于主动忘掉后半段
```

**实测数字（这一次的完整经过）：**

```
原文 memory              24,269 字
condense 后（修①，预算 9000）18,836 字符   ← 修好了，B3/B4/B5 回来了
送进 prompt（② evidence[:6000]） 6,000 字符  ← 又砍回原点，前面的修复白做
→ 判断仍写着「B3 尚未接入 render」，而 B3/B4/B5 当天凌晨就交付了
```

**★★★★★ 判据：修完压缩器，必须回读【最终送进 prompt 的那段字符串】的长度，不是看中间产物。**
`print(len(ev))` 打在 `messages` 拼装的前一行 —— 这一行不打印，你就会一直以为修好了。

**★★ 泛化：一条「原始数据 → 压缩 → 拼进 prompt」的链路，每一处 `[:N]` / `[:N]字` 都是一个独立的静默截断点。**
修完一处必须 grep 整条链路还有没有别的切片，`grep -n "\[:[0-9]" <判据脚本>` 一条命令就能查完。

#### 全局审计：确认「别的项目没有同样问题」

用户当时的要求是「**确保以后不会在其他项目卡信息上出现这样的情况**」——
所以不能只修出事的那一个，要扫全部。

```
scripts/audit_memory.py  →  逐项目、逐 memory 文件：
   原文 ## 小节数  vs  condense(某预算) 之后剩几个
   丢了几节 / 有没有触发「标题超预算」分支
实测结果：131 份 memory，0 份丢小节，0 份硬截
         （最大的 56,915 字 / 23 节、35,840 字 / 45 节 全部完整）
```

**★ 这个脚本的价值不在这一次的结果，在「以后怀疑就可以再跑」。**
**★★ 判据：修完压缩类 bug，必须给出一句「全量扫过，N 份里 0 份有问题」—— 只说「那个项目好了」是不够的。**

#### ★★★★★ 第二课：把数据塞给它，不等于它会用（这条比截断更隐蔽）

截断修好、**「队列待发 2 条：…」也确实写进了证据包**，重判之后建议**还是没变**：

```
修之前：建议 先跑一次 build_board.py 与 selfcheck        ← 它自己想出来的动作
证据加了队列之后：建议 先跑一次 build_board.py 与 selfcheck  ← 一模一样
```

**根因：SYSTEM prompt 里只说了「一个具体动作」，没说什么优先。**

**★★★ 修法：把优先级写进 SYSTEM，而不是指望它从数据里悟出来。**

```
★ 关于「建议」怎么选，按这个顺序：
1. 证据里有「队列待发 N 条」且 N > 0 → 建议必须指向队列里的第一条（说清是哪一条），
   不要另起新活，也不要重复建议队列里已经列过的事。
2. 队列为空 → 看证据里最新动作，建议「验收 / 确认 / 收尾」类动作。
3. 证据明确写着「已收尾 / 已上线」→ 写「无动作，等新需求」。

★ 特别注意：证据里 WorkBuddy 的工作报告是按时间顺序列的小节标题，
  最新的状态在【最后几个小节】里。不要只看前面就下结论。
```

**改完实测（同一条项目，同一份证据，只改了 prompt）：**

```
建议 先清队列第一条「把 3 条未归位角度写成一页 未归位角度清单」，再处理 README 从 v5.1 重写到 v10。
```

**★★★★★ 泛化：给 LLM 加字段时，字段本身是中性的 —— 想让结论变，必须同时改「怎么用这个字段」那句。**
**这跟 §3.11 ①「禁一句话等于没禁」是同一类：规则必须写成「条件 + 动作」，不能只写一个名词。**

**★ 验收方式：改完 prompt 必须重判一次并**逐字对比**新旧建议。只看到 exit 0 或「完成：成功 1」，不代表建议变了。**
**★★ 而且对比要用同一个项目 —— 换项目对比等于没对比（不同项目的正确答案本来就不同）。**

### 3.3 看板：数据我出，界面交给执行 Agent

**★★★★ 单一真相源原则：被监管的执行 Agent 不能同时做数据源**（等于让运动员记分）。
它只能做皮肤 —— 读事实层给的数据，渲染成页面。

**位置**：`Outputs/projects/_看板/{_template.html, index.html}`
**★ 放库里**（数据源在旁边、跟库一起备份、换机器也在），**不放执行 Agent 的工作区** —— 那是工地，不是成品区。

**⚠️ 技术方案：单文件注入，不要外部 data.js（2026-11-13 实测推翻过一版）**

```
✗ 曾以为可行：HTML 里 <script src="data.js"> + 脚本每天只改 data.js
  → 实测：Edge 在 file:// 下【不加载】同目录的 data.js
  → 症状：页面全空（截图 ~18KB vs 正常 ~158KB），卡片 0 张
  → 而 raw-md 块内嵌内容时，同一个浏览器渲染完全正常 ✓

✓ 可行方案：留一个 _template.html（执行 Agent 的皮肤，一字不改），
  脚本每天把 _进度总表.md 注入它的 raw-md 块，生成新的 index.html
```

**★★ 一句话：宁可每天重写一次 14KB 的 HTML，也不要依赖第二个文件被加载。**

**注入的正确写法 —— 用 `re.subn` + lambda，不要手工拼字符串：**

```python
pattern = r'(<script type="text/plain" id="raw-md">)[\s\S]*?(</script>)'
new, n = re.subn(pattern, lambda m: m.group(1) + md + m.group(2), html, count=1)
assert n == 1, "模板里找不到 raw-md 块"
```

用 lambda 而不是 `r'\1' + md` —— 否则 MD 里的反斜杠会被 `re.sub` 当反向引用吃掉。

**⚠️ 三条实测踩过的坑：**

```
① 手工改内联 JS 会把正则改坏
   想插一行 BOARD_MD 进去，结果 `/\r\n/g` 被拆成真换行 → SyntaxError
   ✓ 修法：JS 一行都别碰，只做 raw-md 块的整体替换

② ★★★★★ 「今天只做这一件」这个模块 —— 别加，他已经关掉了
   2026-11-13 他先问「这个区域是做什么」，我解释完用途，他一句「关掉」。
   → ★★★★ **泛化信号：用户问「X 是做什么的」，通常不是在求知，是在考虑去掉 X。**
     正确反应：一句话答用途 + 一句「你是不是觉得它多余」。
     **不要花一整段论证它有价值** —— 我这次写了一整段「它解决 5→1 的收敛问题」，
     他看完只回两个字：关掉。
   → 教训：**不要给一个「AI 替你收敛成一件」的装置。**
     他要看的是【每个项目各自到哪】，做哪件由他自己定。
     ★ 我当时的理由是「你的问题是项目太多，不是建议不够」—— 话没说错，
     但**收敛的动作必须由他做，不能由页面替他做**。
   → 拆除三处（**JS 逻辑一行都不动**）：
     ① `<section id="focus">` 加 `style="display:none"`
        ★ 不能删元素 —— `renderFocus()` 拿到 null 会 `.innerHTML` 报错，整页 JS 崩
     ② CSS `.pin{display:none !important}` —— 「钉到今天」按钮没块了就没意义
     ③ **`<h1>` 也要改** —— 皮肤作者把这句当成了页面标题（`<h1>今天只做这一件</h1>`），
        只隐藏 section 的话大标题还挂在那儿（实测第一版就漏了这个）
   → ★★★ 还要清源头：MD 里那行删掉 + cron prompt 写明「不要写这类收敛语」。
     只遮页面不改 prompt，第二天它又长出来。

③ 无「N 天没动」的条目，皮肤会 fallback 显示「在动」（写死在 JS 里）
   → 会误导。★ 数据侧解决：MD 每条都带天数；不值得为它改 JS
```

**⚠️ 追加规则用「覆盖当天」，不要用「跳过」。**
实测：第一次跑（脚本失败、数据只有 4 条）先写了 `## 11-13 汇报`，第二次跑（5 条全的）按「已有就跳过」的规则跳了 —— **结果 MD 里永远缺一条，看板也永远少一张卡。**

### 3.4 ★★★★ 指令队列 `_给WB.md` —— 让「建议」变成「有人手上有活」

**问题**：看板上的「建议」只是文字。用户看完点头，然后什么都没发出去 —— 因为**发给执行 Agent 的那一步没有载体**。

**★★★★ 位置：每个项目根目录下一份 `_给WB.md`，不要搞全局一个。**
理由：**执行 Agent 的窗口是按项目开的** —— 他打开哪个项目，就该只看到那个项目待发的东西，不用在全局表里找「这条给哪个窗口」。

```
Outputs/projects/
├── <项目A>/_给WB.md      ← 只有有指令的项目才有这个文件
├── <项目B>/_给WB.md
└── <其它项目>/           ← 没有就没，不要建 30 个空文件
```

**四档结构（少一档就会烂）：**

```markdown
⏳ 待发          ← 他复制给执行 Agent 的
    每条：做什么 / 为什么 / ★ 做完请写什么进 memory
✅ 已完成        ← 从执行 Agent 的报告里确认过的（我不重复说）
⚠️ 卡在外部      ← 不是 Agent 能做的（要用户开口 / 要客户给素材 / 要登录后台）
📌 口径备忘      ← 数字和称呼，防止 Agent 下次重算重问
```

**★ 现成模板：`templates/instruction.md`** —— 带填充指引（四条铁律 + 选项目的判据 + 「卡在外部」的四类来源）和一条真实指令范例，直接复制改名改内容即可。

**★★★★ 最关键的一条设计：每条待发指令都必须写「做完请把 X 写进 memory」。**
因为快路监听（§3.5）读的就是 memory —— **这句约定是「自动标 ✅」的唯一钩子**。没有它，队列永远不会自己变绿。

**★★★ 维护归 AI，用户只做两个动作**：看有没有「⏳ 待发」→ 有就复制。**一旦需要他手动维护，这个文件必烂。**

**⚠️ 一个诚实的提醒（必须说给用户听）：**
> **这个队列不可能替他省掉粘贴** —— 执行 Agent 没有 API，那道门只能用手推。
> **它真正省的是记性**：他不会忘、我不会重复说。
> ★★★ **如果哪天它长到 10 条待发，那不是系统好，是他又开了太多线** —— 那时该看的是「为什么有 10 条」。

**选哪几个项目建队列：**

```
① 客户项目（在动 / 该动）— 优先
② 有外部时间压力的（审核中、要送人）
③ 有货可卖但没上架的
✗ 在等审核、Agent 动不了的 → 【不要建】队列是空的，只是多一个文件
```

**★★ 建之前必须先读该项目的 `.workbuddy/memory` 最新一份** —— 不读就只能编。实测读出来的信息密度极高：某个项目的日志直接写着「6 家里 5 家从官网拿到标志，均未写入包，等泽哥确认」，比任何文件 diff 都准。

### 3.5 ★★★★★ 快路监听：把「定时」变成「事件驱动」

**问题**：06:20 的日报太慢。执行 Agent 上午干完一件活，用户可能到第二天才知道。

**★ 这正是 SuperAgent 的 Fast Path / Slow Path**（详见 `SKILL.md`）：

| 层 | 谁 | 频率 | 干什么 | token |
|---|---|---|---|---|
| **快路** | 纯脚本 `no_agent=True` | 每 30 分钟 | ★ **只在「队列某条被完成」时**打勾 + 推下一条（见 §3.5.1） | **0** |
| **慢路** | agent（§3.2） | 每天 06:20 | 判断「该做什么」 | ≈5k/次 |

**⚠️ 下面这段「只通报发生了什么」是 v1，已被 §3.5.1 推翻 —— 先读 §3.5.1 再读实现细节。**

**核心实现（`scripts/wb_watch.py`）：**

```python
# state 里存 {项目: {memory文件名: md5前16位}}
# 每 30 分钟扫一遍，hash 变了 = 有新内容
if not fresh: return          # ★★ 静默：什么都没发生 → stdout 为空 → cron 不推任何消息
```

**★★ 摘要算法（这是好坏的分水岭）：不要截前 N 字，要抽「标题 + 结论首句」。**

```python
# 找第一个 "## " 小节 → 标题 + 该节第一段非空文本（跳过表格/列表/更小标题）
text = (title + "：" if title else "") + " ".join(body)
```

✗ 截前 150 字 → 常常切在表格中间，读不出重点
✓ 抽标题+结论 → `合作方 logo 官网溯源：6 家里 5 家从官网拿到可核验标准标志，中国科技发展院未取得`

**四条实测细节：**

```
① 同一项目只报最新一条 —— 半小时内改了 5 次，只报最后一次（附「另有 N 条已合并」）
② 时间窗限 8–22 点（`*/30 8-22 * * *`）——
   他凌晨 01:56 还在改小程序，那种时段不该半夜响；凌晨的活由 06:20 日报兜
③ 只监听 memory，不监听所有文件 —— 文件变动太频繁会变成刷屏
④ 没有 memory 的老项目就不报 —— 它们的进度归 06:20 日报
```

**★★★★ 顺带说清一个架构红利**：
这条快路**不经过 Router 判断，直接把执行 Agent 的进展推给用户** ——
正好对应 SuperAgent 的「**订阅直通（Thread 直通）**」：Worker 订阅后事件直达，省下 Router 的判断负载。
→ **不需要判断的通报，就别让 agent 过一遍。** 又快又省钱，而且不会编。

### 3.5.1 ★★★★★ 快路 v2：只在「队列某条被完成」时说话（2026-11-14，v1 被用户否了）

**用户原话**：「**现有这个半小时一次的频率，不合适。**改为你提出的 b 方案建议，**只会在完成了队列某一条时向我推荐/汇报**。」

**★ 病根不在「半小时」，在「说什么」**：

```
v1：WB 一写新 memory 就通报 → 实测 09:00–11:30 收到 6 条
    内容全是「WB 刚做了什么」，没有一条告诉他「所以下一步做什么」
→ 又吵、又没用
v2：只报「队列里某一条被做完了」→ 打勾 ✅ + 把【下一条】递到他手上
```

**★★ 关键契合点（§3.12 ①）：下一步不是新生成的，是队列里早就躺着的那一条。** 所以这一层**纯脚本、零 LLM、零成本**。

```
🎯 队列完成 · 11-14 12:41

✅ 示例新媒体运营@WorkBuddy
　给复盘表单加公众号口径：阅读次数／在看／转发／留言…

⏳ 下一条：修第三处硬冲突：每周选题会按「周更 7 条」配比写死，改成按「所属账号」取配比
　<完整可复制的指令>
```

**★★★★★ 匹配器：两个硬条件 + 三条保命规则 + ★★★ 两个已被实测证伪的旧参数（2026-11-20 修）**

```python
# 条件① 完成信号（缺一个都不算）
# ★★★ 「改完」必须写成「改完了」—— 见下面【证伪②】
DONE_SIGNALS = ("已修","已改","已完成","已上架","已交付","已发布","已上线",
                "已生成","已落地","自检通过","改完了","做完了","跑通","已补齐","已整理")

# 条件② 可辨识的重合（两条路，按任务类型走）
#   · 双方都有英文标识符（ideaToTopic / main.js / SKU1）→ ★ 重合 ≥2（原来是 ≥1，见【证伪①】）
#   · 纯中文任务 → 中文短语重合 ≥4 个
```

#### ★★★ 证伪①：「英文标识符重合 1 个就够」会误打勾 → 改成 ≥2

**2026-11-20 实测事故：一条「v8 第一批」被整条打勾，实际 4 件只做了 1 件。**

**根因不是匹配器笨，是阈值 1 挡不住 —— 那条队列和 memory 共享 `build_board.py` / `board.html` / `md5` / `py_compile` 好几个词，只要 1 个就命中。**

```python
if best is not None and best_score >= 2:      # ✓
    return best, "标识符重合 %d 个" % best_score
if best is not None:
    return None, "标识符重合不足（%d 个，需 ≥2）" % best_score
```

**★ 为什么 2 不是更高**：纯中文任务走下面那个分支（阈值 4）；能走到这里的都带英文标识，**2 个（任务名 + 文件名同时对上）已经是很强的一致性要求**。

#### ★★★ 证伪②：完成信号里的「改完」会误命中文档性的将来时 → 改成「改完了」

**实测那句被误判的文字是：**

```
「改前 md5 已记录…改完做 py_compile + node --check + md5 复核再汇报」
```

**语义是「改完之后要做什么」（还没做），但「改完」在词表里 → 直接算完成信号。**

**★ 修法：要求后面跟「了」，才表示已经发生。**
**★★★ 泛化：完成信号词表里不能放「动作名」，只能放「已发生的断言」。**
`改完` / `处理` / `调整` 这类都属于动作名 —— 它们在计划性描述里天天出现。

#### ★★★★★ 但更根本的修法：队列粒度 = 执行粒度（这条比上面两个阈值重要）

**同一次事故的真正病根：队列 1 条「v8 第一批」，而执行时是 4 件逐件汇报。**

```
队列　1 条「v8 第一批」（含 4 件）
汇报　「第 1 件完成」
匹配器　看到「完成」→ 打勾整条  → 计划里明明还有 3 件没做
```

**★ 阈值修好也救不了这个 —— 粒度不对，任何匹配都是在猜。**

```
✓ 执行方怎么拆，队列就怎么拆
  第 2 件 / 第 3 件 / 第 4 件 各一条，一件一个勾
```

**⚠️ 而拆完之后会出现新问题：`汇报格式「第 N 件完成」不含词表里的信号` → 漏打勾。**

```text
「第 2 件完成」  ← 「完成」不在 DONE_SIGNALS（只有「已完成」「做完了」「跑通」）
→ 不会自动打勾
```

**★★★ 两个选择，按阶段选：**

| 选 | 做法 | 代价 |
|---|---|---|
| **A（早期推荐）** | 让执行方写「第 N 件已完成」—— 多一个字就自动打勾 | 要改指令模板 |
| **B（保守）** | 接受漏打勾，人来看一眼补 | 每条要人工确认 |

**★ 判据：队列 ≤3 条时用 B（记得住，不值得为它改模板）；≥10 条或多项目并行时用 A。**
**★★ 但无论选哪个，都不要把「件完成」加进 DONE_SIGNALS —— 那会把「第 1 件完成」认成整批完成，绕回证伪①。**

#### ★★★ 队列长度的判据（什么时候才真的需要自动打勾）

```
1–3 条　→ 人看一眼就知道，自动打勾是多余动作
5–10 条 → 开始记不住，需要
10+ 条 + 多项目并行 → 非常需要，否则会重复派单、漏做
```

**★★★★ 而更根本的一句：如果队列长到需要机器打勾，那更该改的是「减少并行」，不是「让机器猜」。**

**★★★ 证伪①的真实事故发生前，那条队列只有 4 条 —— 也就是说当时根本不需要自动打勾。**
**这次事故的本质不是「匹配器不够聪明」，是「为一个不需要的自动化付了误判的代价」。**

**★★★★ 三条保命规则（每一条都是踩出来的，缺一条就会错打勾）：**

```
① 只看 memory 的【本次新增行】，不看整个文件      ← 最重要
② 首次运行只建基线、不打勾
③ 文件行数变少（被重写）→ 跳过，不匹配
```

**★★★ 第 ① 条的真实事故（必须记住）：**

```
队列两条：A「占位符总清单」  B「修 5 处代码缺口」
memory 写：「P0 #1-5 仍待泽哥提供」 ← A 明显没做完
但匹配器看整个文件 → 文件里出现过「占位符总清单」这几个字 → A 被打了勾
→ 客户 A队列从 2 条变 0 条，我第一版要是不复核就交出去了
```

**★★★★★ 一句话原则：队列撒谎比队列空更糟。**
**宁可漏打（用户说一句就能补），不要错打 —— 错一次，整条队列失去可信度。**

#### ★★★★★ 第四个失效路径：执行方自己打勾，匹配器根本没机会跑（2026-11-15）

**比误打勾更隐蔽 —— 误打勾至少有人看得见，这个是静默的。**

```

**★ 判据（看 ✅ 那条的续行）：**

```text

续行是「① …」「⚠ 一处按判断处理：…」这种报告体 → ★ 执行方自己改的
```

**★★ 理由：`tick_item` 会原样搬续行，绝不会生成 ①②③ 这种报告措辞。**

**两道修法（都要做，缺一不可）：**

```text

   > 不要修改这个文件 —— 包括打勾、包括把你的报告贴进来

② state diff 检测：上次的待发列表 vs 本次，消失的条目里「不是自己 tick 的」→ 报警
   ★★★ 破坏点：基线必须在【本轮所有 tick 结束后】才写入
       写在扫描早期 → 下一轮把自己打的勾当成外部修改（实测误报）
```

**★★★★ 泛化：除了监听器，还有谁会写这个状态文件？**
**只要存在第二个写入方，「监听器看不见事件」就是迟早的事 —— 而且它表现为静默，跟「一切正常」一模一样。**

**★ 阈值 4 是实测出来的，不是拍的**：

### 3.5.2 ★★★★★ 快路 v3：派单后的「三句话心跳」（2026-11-15）

**用户原话**：「我想中间可以加一个心跳机制，**在你给我指令之后，监测 wb 有没有更新项目的 memory**。」

**★ 病根：v2 只在「完成」时说话 → 派单到完成之间是黑箱。**
他不知道 WB 是「在做」还是「根本没收到」。

```
v2：改了 5 步，走完才吭声 → 中途卡住 3 小时，他完全不知道
v3：派单期间只说三句话 ↓
```

| # | 什么时候说 | 说什么 | 频率 |
|---|---|---|---|
| ① | memory 出现新内容 | `▶ <项目> WB 动了（队列还剩 N 条）` + 摘要 | **每个派单周期只报一次** |
| ② | 队列某条被打勾 | `✅ 完成了` + 推下一条（v2 逻辑不变） | 每条一次 |

**★★★★ 关键是①的克制度**：中间 WB 写 10 段 memory 也只报第一次。
否则退化成 v1（09:00–11:30 推 6 条），被用户否过一次的判断不能忘。

#### ★★★★★ 设计：派单状态不需要额外标记，队列本身就是状态

```
派单中 = 该项目 _给WB.md 里还有「⏳ 待发」
队列清空 → __pending_since / __notified_start / __notified_stall 三个标记全部重置
         → 下一单重新开始报
```

**★ 不要另建一个「我给了指令」的状态文件** —— 那必然和队列漂移（他手改了队列，状态文件不知道）。

#### ★★★★ state 里混装两类字段，必须能分开

```python
st[proj] = {
    "__pending_since": "2026-11-15 10:30",   # 元状态
    "__notified_start": True,
    "__notified_stall": False,
    "2026-11-15.md": {"hash": ..., "nlines": ...},   # 业务基线
}
```

**★ 遍历 memory 基线时一律 `if not k.startswith("__")` 过滤** ——
否则 `__pending_since` 会被当成一个 memory 文件参与 hash 比对。

#### ★★★★★ 五个 bug（全部是这一版新写出来的，静态读代码看不出来）

**① `--init` 走了完整流程 → 把「已报过动了」提前置 True**

```python
# ✗ 原来：init 只是跳过 print，逻辑照跑
if init: print("基线已建", file=sys.stderr); return   # ← beats 已经 append 过，state 已被污染
# ✓ 现在：init 在事件生成【之前】返回
if init:
    for proj, files in cur.items():      # 只写 memory 基线
        st.setdefault(proj, {}).update({f: {"hash": i["hash"], "nlines": i["nlines"]} for f, i in files.items()})
    save_state(st); return
```

**★★★ 泛化：任何「初始化」分支必须在产生副作用之前 return，不能跑完再 return。**
症状特别阴：init 之后第一次真实检测完全静默，你会以为功能没写对。

**② memory 基线 hash 没写回 state → 每轮都认为「又变了」**

v2 的写法是 `save_state({重建整个 state})`，我把 state 改成「只更新 __ 标记」，
**漏了把新 hash 写回** → 下一轮 hash 还是旧的 → **「动了」会每 30 分钟重复报一次。**

```python
# ★ 扫完必须回写基线，位置在 save_state 之前
for proj, files in cur.items():
    pst = st.setdefault(proj, {})
    for fname, info in files.items():
        pst[fname] = {"hash": info["hash"], "nlines": info["nlines"]}
save_state(st)
```

**③ 摘要抓成「2026-11-15」—— 抓到了日期行**

```python
# ✓ 跳过纯日期 / 纯时间 / 纯数字行
if re.fullmatch(r"[\d\-–/. :年月日]+", t): continue
if re.fullmatch(r"[\d\-–/. :年月日]+\s*[\u4e00-\u9fa5]{0,2}", t): continue
```
**★ 而且 `len(t) < 6` 要提到 `< 8`** —— 「10:30」这种也能过 6 字门槛。

**④ 我的测试数据把「5 小时前」写成了未来时间**

```python
# ✗ st["__pending_since"] = "2026-11-15 01:00"   # 当时是 00:35，这是未来
# ✓ _t = datetime.now() - timedelta(hours=5)
```
**★★ 测「超时」类逻辑必须用 `now - timedelta`，不要手写时间字面量 —— 会话跨天就直接失效。**

**⑤ 用例顺序会互相污染**

`--init` 建基线 → 追加 → 报「动了」 → 再追加 → 完成 → 换新队列……
**每步都改同一个 state，前一步的残留会让后一步测不准。**
★ 全套用例要一次跑完 7 项（动了/继续写静默/完成/队列空后静默/新派单静默/卡住/卡住不重复），
中途失败就先 `rm state` 重来。

#### ★ 沙盒 7 项回归（照这个清单验）

```
① 追加一段          → ▶ 报了，摘要取新增段第一句有内容的话
② 再追加一段        → 静默（一个派单周期只报一次）
③ 写「已完成…」      → ✅ 打勾 + 报
④ 队列空后再写      → 静默
⑤ 新派一单（刚派）  → 静默（刚开始等）
⑥ 伪造 5 小时前     → ⚠ 卡住了
⑦ 再跑一次          → 静默（卡住只报一次）
```

**★★★ 真实环境那次要单独验：队列无待发时 `--dry` 必须**完全静默**，
且 state 里**不许出现任何 `__` 字段**（否则就是清空重置没生效）。

#### 与 §3.9 的分工

```
§3.9 心跳（cron 的 cron）→ 监控「日报有没有跑」       ← 系统健康
§3.5.2 派单心跳          → 监控「那一单有没有人接」   ← 任务健康
两个都要，不重复：一个说「机器活着吗」，一个说「活有人干吗」。
```

**⚠️ 时间窗限制要主动说**：cron 是 `*/30 8-22`，**晚上 22 点后不跑** ——
他深夜派单的话，心跳要等第二天 8 点。要么改全天，要么先说清。

### 3.5.3 ★★★★★ 快路 v4：完成之后自动起一次判断（2026-11-15，第三层）

### 3.5.4 ★★★★★ 快路 v5：产物监控 —— 治「对话式改动」的盲区（2026-11-16~17）

**病根：用户在桌面 Agent 窗口里直接说「把标题字号改大」—— 这句话本身就是指令，
但没有我方派单 → 没有队列条目 → 没有「做完请报告」那句话 → memory 自然不写。**
**§3.5.1–3.5.3 全靠 memory 做信号源，所以这一整类改动【完全不可见】。**

**★★ 唯一拿得到信号的地方是文件本身：mtime + size。**

```python
scan_artifacts()  → {项目: {相对路径: [mtime, size]}}
diff_artifacts()  → 对比两轮，返回 [(文件, 旧size, 新size, mtime)]
```

**三类组合怎么报：**

| 产物 | memory | 报什么 |
|---|---|---|
| 变了 | 有新行 | `▶ 动了：<memory 内容>`（老逻辑） |
| **变了** | **没新行** | **`⚠ 产物变了（memory 最后一次写入 HH:MM，之后又改了 N 个文件）`** |
| 没变 | 有新行 | `▶ 动了`（它在想，没动手） |

#### ★★★★★ 报警文案必须区分「没记过」和「记过又改了」

**真实场景（2026-11-17 中午实测）：**

```
12:07  WB 写了 memory：新增法语课系列 + 首张海报（很详细）
12:15  又改一版海报，没写 memory  → 触发产物报警
12:21  又改一版，没写 memory
```

**旧文案写的是「产物变了，但 memory 没记录」—— 这句话是错的，12:07 明明记过。**

**★★★★ 后果是实的：用户看到「没记录」，就让执行方「补上 memory」，
于是它把 12:07 那段整段重写一遍 → 两份互相打架的记录。**

**✓ 修法：state 里带 `mem_mtime`（该项目 memory 目录下最新日志的 mtime），
不为 0 报「最后一次写入 HH:MM」，为 0 才报「还没有 memory 日志」。**

```python
mm = 0
for fmeta in (cur.get(proj) or {}).values():
    mm = max(mm, fmeta.get("mtime") or 0)
art_changes.append({..., "mem_mtime": mm})
```

**★★★ 这是 §3.13「新状态被旧流水盖住」的同一条原则，也是 `skill-publishing` §7.5
「没配≠坏了」的同一条：同一个症状有两个不同原因时，报警必须能区分 ——
否则它会让人做出错的动作，比不报警更糟。**

#### ★★★★★ 对话式改动的最后一步：一个动作，不是一套规则

**不要试图纠正用户的工作方式。** 对话式改小东西（颜色 / 字号 / 间距 / 文案）
比走队列快十倍，**这是对的**。要纠正的是「改完不留痕」，不是「改」。

**也不要试图自动补上** —— 拿不到对话内容，自动化成本比人工收尾高。

**✓ 唯一的办法：把留痕固定成对话的最后一句话。**

```
改完 → 「把刚才这次改动加到 memory 末尾，说清改了什么、为什么」
```

**★★ 措辞很重要（实测会踩）：**

| 说 | 结果 |
|---|---|
| 「补上 memory」 | 可能整段重写 → **两份打架的记录** |
| 「加到 memory 末尾」 | 只追加 → 一条干净时间线 |

**★★★ 一次对话改了三轮以上：**

```
✗ 每轮都补一句 —— 太烦，人会放弃
✓ 只在最后一轮补，写「本轮共改 3 次：①字号 ②位置 ③颜色」
```

**★ 判据：留痕的成本必须是一句话。超过一句话就没人会做。**

**★★★★ 可泛化到一切「没有系统指令的动作」：不要指望自动化，
只给它一个收尾动作，而且那个动作必须小到不需要意志力。**

#### 四个实现坑（都踩过）

```
① 必须排除 .bak 备份文件
   实测：内容看板目录里 14 个 board.v*.bak.html —— 不排就一直误报
   复用 SKIP_FILE_HINTS（.bak / _bak_ / .pyc / .lock）
② 必须排除 .workbuddy/
   memory 归 scan_memory 管，混进产物监控会重复报
③ 必须排除队列文件（_给WB.md 等别名）
   那是我们自己写的，每轮都在变
④ 深度限制 2 层就够
   maxdepth=1 → 240 文件/15ms；=2 → 1137/30ms；不限 → 12,212（全是 node_modules）

**★★ 它治「失明」，不治「失察」**：只知道「哪个文件、何时、从多大变到多大」，
「改成什么样」只能靠 memory 或 LLM 读 diff。**不是自动化验收，是自动化报警。**

**★★★ 而且它第一次真实生效就抓出了自己的文案 bug（上面那条）——
监控上线后要盯着它报的前几条，别假设它说的话是对的。**

### 3.6 ★★★★ 把指令队列接进看板（2026-11-13 收尾做的最后一步）

**他的原话**：「我要把『打开某个项目 → 看待发』这个动作**并到看板中**，所以你把项目的建议和给 wb 的指令，整合到看板中。」

第二次：入队：新增 0 条，已存在跳过 1 条   ← 正确
```

**★★ 队列腐烂必须可视化。** 脚本从 `**MM-DD**` 前缀算天数，≥2 天就缀在动作后面：

```
▸ 占位符总清单：把小程序包内所有待填的占位内容列成一张表…（挂 3 天）
```

**★★★ 当时这是「✅ 自动标记」做不了时的替代品** —— 我最初判断语义匹配太容易误标，**选择不做**；只做「挂了几天」这种纯算术、零风险的近似版。
→ **遇到「能自动化但风险高」的一步，先找它的零风险近似版，不要硬上。**

**★★★★ 后来（2026-11-14）还是做了自动打勾 —— 但只在快路（§3.5.1）里、且带三道保险。**
判断改变的原因：**「挂了 N 天」只能让人知道「躺久了」，不能把队列推进下去；而用户的真实动作是「发完一条 → 要下一条」。**
→ **教训：零风险近似版是「先不阻塞」的过渡手段，不是终点。** 条件成熟（能可靠匹配）时该把它替换掉，而不是一直停在近似版。
→ ★ 但替换的前提是**先证明能可靠匹配**：5 条回归用例 + 首次只建基线 + 只看新增行，三条缺一不可。没有这三条，误打勾比不做更糟。

**⚠️ cron prompt 必须是四步，少一步闭环就断：**

```
第一步：写 ## <月-日> 汇报 段（覆盖当天，不跳过）
第二步：写 ## 入队（给WB） 段（整段替换）
第三步：python project_watch.py --sync     ← 少了这步，队列永不更新
第四步：python project_watch.py --board    ← 少了这步，看板永不更新
```

**★ 每一步都要求 agent 把脚本回显写进汇报末尾**（「入队：新增 N 条」「✅ 看板已更新」）—— 否则它跳过了你也不知道。

### 3.9 ★★★★ 心跳：用高频任务监控低频任务（cron 的 cron）

**问题**：06:20 的日报如果**根本没跑**（机器关着 / Hermes 没起 / 调度丢了），`last_status` 帮不了你 —— **因为那是一个「没发生的事件」，它没有状态。**

**★ 做法：让每 30 分钟那个任务去检查每天那个任务。**

```python
# 日报侧：每次跑完写心跳（--sync / --board / evidence 每条路径都写）
def heartbeat(note=""):
    open(r"...\cache\project_watch_heartbeat.txt", "w", encoding="utf-8").write(
        datetime.datetime.now().strftime("%Y-%m-%d %H:%M:%S") + " " + note + "\n")

# 快路侧：超过阈值就报警
def check_heartbeat(max_hours=26):
    ts = datetime.datetime.strptime(open(HEARTBEAT).read().strip()[:19], "%Y-%m-%d %H:%M:%S")
    hours = (datetime.datetime.now() - ts).total_seconds() / 3600
    if hours > max_hours:
        return f"🔴 项目日报已 {hours:.0f} 小时没跑（上次 {ts:%m-%d %H:%M}）\n　→ 检查 cron <job_id>"
```

**★ 阈值 26 小时**（日报是日更的，留 2 小时缓冲）。**宁可晚报一次，不要天天误报。**

**★★ 关键：报警要能和无事可报共存**，否则要么漏报、要么硬凑内容：
```python
if not fresh and not hb_warn: return     # 都正常 → 静默
if hb_warn: print(hb_warn)               # 有问题 → 报（即便 WB 没事）
if not fresh: return                     # 只报警，不硬凑内容
```

**① 实测三种状态都要过一遍：**
```
心跳正常 + 无新动作 → 完全静默 ✓
伪造 31 小时前心跳  → 🔴 已 31 小时没跑… ✓
恢复心跳            → 静默 ✓
```

**★★★ 泛化**：任何「**低频关键任务 + 高频轻任务**」的组合，都让高频那个当监工。
**这比单独加一个 watchdog cron 更省 —— 因为那个高频任务反正已经在跑了。**

### 3.10 ★★★★★ 首次真实运行必抓的两个「自我污染」bug

**用户不会等到明天 6:20 —— 他说的是「不用等明天 6:20 跑，现在跑一轮，看看有没有 bug」。** 一轮就抓出两个，**静态读代码两个都看不出来**。

#### ① ★★★★ 监管脚本读自己写的文件 → 全部项目显示「停滞 0 天」

队列 `_给WB.md` 是**我**写进每个项目根的。`scan()` 算 `max(mtime)` 时把它算成了项目活动：

```
项目真实最后活动 11-09 / 11-10，我写 _给WB.md 是 11-13
→ max(mtime) = 11-13 → 五份报告里四份「停滞 0 天」，其中一份实际停了 28 天
```

```python
for f in fs:
    if f == "_给WB.md":      # ★ 跳过我自己写的元数据
        continue
```

**★★★ 判据：任何「扫目录 → 算活动 → 报警」的脚本，动手前先问「这个目录里哪些文件是我或兄弟 cron 写的」** —— 日志、队列、缓存、状态文件全部要排除。只精确排除自己那一个，别顺手排所有 `_` 开头（项目里可能有真实的 `_index.md`）。

**★★★★ 这个 bug 特别危险：它不是崩溃，是「输出看起来很正常」。** 一份写着「停滞 0 天」的报告读起来像「一切在推进」，用户会因此**不去碰任何一个真正停了的项目**。

#### ② ★★★ 汇报段里的「汇总行」被当成第 7 个项目

prompt 要求末尾写概括行 `- 另有 17 个项目已停 21 天以上：<名单>` —— 它**也以 `- ` 开头、也含 `：`**，于是变成一张假卡片（看板顶部写「7 张卡」，实际只有 6 个项目）。

```js
// ✓ 用结构判据，不用排除措辞
if (!/｜\s*建议/.test(body)) continue;   // 真正的项目行一定有「｜ 建议」
```

**★★ 别写「排除含『另有』的行」** —— 措辞会变（其余 / 还有 / 未列的），而**结构特征不变**。

这是 §3.6 那个「段边界」教训的**第二例**，合起来的完整规则：

```
往按「段 + 行」解析的文本格式里加内容时，要同时守住两层边界：
  ① 段边界 —— 每个解析器读到不属于自己的 ## 段就 break
  ② 行边界 —— 每个解析器用【结构特征】认自己那行，不靠措辞或位置
本项目同时有三个解析器（reports / rawFor / todosFor），
加一种新内容要回头查另外两个会不会吃进来。
```

#### ③ 修完必须重跑，一轮只能暴露一部分

```
第 1 轮 → 发现「停滞 0 天」+「7 张卡」
修 Bug A → 第 2 轮 → 停滞天数对了，但卡还是 7 张（Bug B 没修）
修 Bug B → 第 3 轮 → 6 张卡 ✓
```

**★★ 修一个就重跑一次，别攒着一起验。**

回归测试的正确姿势：`tempfile.mkdtemp()` 建真实临时目录 + monkeypatch 模块级 `ROOT`，**并加一条对照组**（无队列文件的项目照常扫到，防矫枉过正把整个项目漏掉）。

📎 完整症状、修法、验证输出、以及「跑完之后该看什么」→ `references/04-打勾与队列.md`

### 3.11 ★★★★★ 上线之后才暴露的两件事：措辞逃逸、以及「刷新」的两种含义

#### ① ★★★★★ 措辞逃逸：禁一句话 = 没禁

**2026-11-14 首次真实调度跑完，回读输出发现它在自己违反 prompt。**

prompt 里写着：

```
★ 不要写「今天只做这一件」这类收敛语（2026-11-13 明确关掉）
```

它当天写的是：

```
今天只做一件事：给宗总发约 30 分钟诊断的微信，发出后在「诊断记录」补上第一行
```

**★★★★ 「一件」→「一件事」，换了一个字就绕过了。**

**★★ 而且它绕得挺合理** —— 那句话确实是当天最该做的。**所以纯看输出不会觉得有问题，只有对着 prompt 逐条核才发现。**

**修法：禁令要禁【行为】，并【列举同义变体】。**

```markdown
✗ 不要写「今天只做这一件」这类收敛语
✓ 禁止出现的措辞（含任何同义变体）：
   「今天只做这一件」「今天只做一件事」「优先做…」「先做这个」
   「最该做的是…」「建议你今天…」「唯一要做的…」
   正确做法：每个项目各给一条【平等的】建议，哪件先做由他自己判断。
```

**★★★★ 泛化（所有给 agent 写规则的地方都适用）：**

> **用「具体措辞」写禁令，一定会被同义变体绕过。**
> 要写 **「禁止这个行为」+「列举 5–7 个变体」+「那该怎么做」** 三段。
> 只写第一句，等于给模型留了一个「换个说法就算合规」的后门。

**★ 检查方法：每次回读 cron 输出时，对着 prompt 的每条规则逐条核一遍「有没有被绕」。**
**★ 这一步很容易漏 —— 因为输出读起来往往都"挺合理"。**

#### ② ★★★★ 「刷新看板」有两种，成本差 30 倍

**用户会直接问**（原话）：「**项目进度看板，是每天只会 cron 一次吗？如果进度已经做完，是否需要设置手动更新的动作？**」

**★ 这个问题暴露了一个我没说清的区别 —— 也是所有「定时生成 X」的系统都有的问题：**

```
轻刷（¥0）　　 打勾 + 重新渲染模板
　　　　　　　→ ⏳ 待发消失、✅ 出现、徽章时间更新
　　　　　　　→ 「现在到哪 / 建议」那句话不变（还是今早的）

重刷（≈¥0.05）重新让 LLM 读证据包、重写判断
　　　　　　　→ 所有项目的「现在+建议」都更新
```

**⚠️ 这里我第一次把成本算大了 10 倍（说 ¥0.5/次），被自己后来的实测推翻。**
```
证据包 ≈ 1 万汉字 ≈ 16k tokens × ¥2/百万 = ¥0.032
输出   ≈ 2k tokens × ¥8/百万        = ¥0.016
合计 ≈ ¥0.05/次　→ 一天 10 次 = ¥15/月，不是 ¥150/月
```
**★★★ 教训：用「token 数 × 单价」算，不要凭感觉给一个数。**
**一旦用错的成本数字去否决一个方案，等于用一个假前提做了判断** —— 这次差点因此否掉「按项目刷新」。

**★★★ 为什么有这个区别**：看板的数据源是 `_进度总表.md`，里面「现在/建议」是 06:20 那次 LLM 写的。
**跑 `--board` 只是重新渲染同一个文件 —— 内容不会变。** 要更新内容 = 要重新判断 = 要花钱。

**★★★★ 用户的真实需求几乎都是「轻刷」**：

```
他看板主要是为了知道「还有哪些待发指令没发出去」
→ 打勾之后 ⏳ 消失，他就知道不用再发了
→ 「现在到哪」旧几个小时，不影响决策
```

**★ 所以正确的产品形态是「你说一句，我做三步」，不是加定时器：**

```
用户：「客户 A那条做完了」
我　：① 在该项目 _给WB.md 里把那条从 ⏳ 移到 ✅
　　　② 跑 --board 重新渲染（零成本）
　　　③ 回一句「已标记，看板刷新了」
```

**★★★ 而且这个动作的价值不只是刷新 ——「这件事算不算做完了」本来就得人判断。**
执行 Agent 写「已改 detail.js」，不等于「这个项目推进了」，它可能只改了一行。

**⚠️ 三个不要做的：**

```
✗ 每天多加一次定时（比如 18:00）—— 时机永远对不上他做事的节奏
✗ Agent 一写日志就自动重判断 —— 一天触发 5–10 次，¥5/天，而且吵
✗ 桌面放个双击 .bat —— 他不会去点，而且它也只能轻刷
```

**★★★★ 泛化**：**定时器解决不了「时机」问题，只有用户的嘴能。**
凡是「用户做完某件事想让系统知道」的场景，**入口应该是对话，不是日程表。**

### 3.12 ★★★★★ 按项目刷新：**下一步不需要重新生成，队列里就有**

**用户 2026-11-14 的原话（把整件事说清楚了）：**

> 「比如示例新媒体运营这个项目，在 09:43 就做了灵感转选题，那么接下来怎样推进，**是否可以更新你对这个项目的下一步建议？**……按我理解的 super agent 逻辑，WB 做完一个步骤会在 memory 写入进度，此时你作为主 agent，应该根据新的进度**再更新一遍下一步的工作，由我复制给 WB**，是应该这样的流程对吗？」

**★ 他的流程理解是对的，而且他当场指出了真缺口**：快路（§3.5）只通报「WB 做了什么」，**没接上「下一步做什么」** —— 拿到进展却拿不到建议。

#### ① ★★★★★ 最关键的一句：下一步不必重新想

**第一反应会是「那每次都重跑一遍判断」。错的。**

```
他的队列里本来就躺着「下一步」：
  客户 A 2 条 / 新媒体 3 条 / 小店 1 条 / 客户 B 1 条
→ WB 做完一条 = 打勾 ✅ → 队列里的【下一条】就是下一步
```

**★★★ 所以 80% 的情况根本不需要 LLM。** 需要重新判断的只有两种：
```
① 队列空了（做完就没下一条）
② WB 做的事不在队列里（跑偏了）
```

**★★★★ 推论（反直觉但重要）：队列"积压"其实是好事 —— 说明下一步早就备好了。**
真正该警惕的不是积压，是**队列空着但项目还在动** —— 那说明没计划。

#### ② 两个命令（解决「等第二天」）

```bash
# 只拿这一个项目的证据（实测 11,496 → 3,235 字符，省 72%）
python project_watch.py --only "示例新媒体运营"

# 只改日志里那一行，其余项目原样不动，并自动刷看板
python project_watch.py --set "示例新媒体运营" \
  --now "ideaToTopic 已修（29 行，自检通过）" \
  --advice "队列还剩 2 条；先发三篇比修工具见效快"
```

**`--set` 的实现要点（三条都会咬人）：**

```python
# ① 找「最后一个 ## … 汇报 段」——"11-14 汇报" 中间有空格，\S* 匹配不到
if re.fullmatch(r"##\s+.*汇报\s*", l): idx = i     # ✓ 用 .*

# ② 段内按「：」前半段匹配项目名，并去掉 @后缀
pname = re.sub(r"@\S+$", "", l[2:].split("：", 1)[0].strip())

# ③ 改完顺手调 --board（subprocess），但失败不能冒充主结果
_bo = subprocess.run([... "--board"], capture_output=True, text=True).stdout.strip()
if _bo.startswith("ERROR"): print("⚠️ 已改日志，但看板没刷新：" + _bo)
else: print(_bo)
```

**★★ 第 ③ 条实测踩过**：模板不存在时 `--set` 会打印 ERROR，看起来像「替换失败」，其实日志已经改好了。**主结果和副作用结果必须在输出上分开。**

**⚠️ 新增项目时 `--set` 会追加到段末 —— 位置是错的**

**实测**：给一个还不存在的项目写第一行（`--set "内容看板"`），它会打印 `新增：<项目名>` 并追加到「## MM-DD 汇报」段的**最末**。
而段末通常就是那行汇总 `- 另有 N 个项目已停 21 天以上：…` → **新项目排在汇总行后面，看板顺序乱。**

**★ 手动挪的时候还有一个更隐蔽的坑**：先 `pop` 再 `insert`，插入索引若用 pop **之前**算的值，会差一位 ——
实测差一位把新行插进了**前一天的汇报段**（`## 11-13 汇报`），于是它在当天的看板上**直接消失**。

**正确做法：按段落边界精确插，索引在 pop 之后重算**

```python
# ① 先摘掉（不管它现在在哪一段、哪一行）
row = None
for k in range(len(lines) - 1, -1, -1):
    if lines[k].startswith(f"- {name}："):
        row = lines.pop(k); break
assert row, "没找到这一行"

# ② 再定位【目标段】的起止 —— ★ 必须在 pop 之后重新算
start = next(k for k, l in enumerate(lines) if l.strip() == f"## {day} 汇报")
end   = next(k for k in range(start + 1, len(lines)) if lines[k].startswith("## "))
ins   = next((k for k in range(start + 1, end) if lines[k].startswith("- 另有 ")), end)
lines.insert(ins, row)
```

**★★★ 泛化：「按行号做两次结构性改动」时，第二次的索引必须在第一次之后重新计算。**
`pop` / `insert` 之后所有旧索引全部失效 —— 这是同一个操作上连错两次的根因。

**验证方式：`grep -n` 看那一行落在哪个 `##` 段里，不要只看「插入成功」的打印。**

**★★★ 验证方法：`diff` 只应显示一行变化。** 实测对照（备份 → 改 → diff）：
```
5c5
< - 示例新媒体运营：现在 工作台停 11-10 第 4 天，ideaToTopic 形态仍写死…
---
> - 示例新媒体运营：现在 ideaToTopic 形态已修（29 行，自检通过）…
```
其余 5 行、汇总行必须原样不动。

#### ③ ⚠️ 但全量判断必须保留每天一次

**★ 单项判断做不出跨项目的话。** 实测它当天写出的最有价值的一句是：

> 「示例新媒体四个号只有一个在发 —— **修工具不如先发三篇**。」

**这句是「新媒体 × 内容节奏 × 小店上架」放在一起才看出来的。单项判断永远给不出。**

```
全量（每天 1 次）→ 跨项目关联、优先级、该不该停
单项（事件触发）→ 那个项目现在缺什么动作
```

#### ④ ★★★ 为什么不做「看板上的刷新按钮」

**用户提过**：「每个项目在看板中有一个独立的刷新机制（或者一个独立的刷新按钮）」。

**★ 方向对，形态不对。**

```
看板是 file:// 单文件 → 点按钮发不了后台请求（同源策略 + 没后端）
要做成真按钮 = 起一个常驻 HTTP 服务 → 为一个按钮多一个「死了没人知道」的进程
```

**★★★★ 更根本的一点：按钮是退步。**

```
按钮 = 他想起要刷的时候才刷 → 他得先知道"该刷了"
      但看板就是为了知道"有没有新进展" → 循环依赖
事件 = WB 一完成就自动判断 → 不需要他想起来
```

**实测：26 个 → 8 个，正好等于卡片数。**

**③ 老判断的时间戳补不回来 —— 只能重判一次**

`judge_times.json` 是这次才加的，之前所有判断都没记录时间 → 全部显示「指令时间未知」。
**✓ 唯一干净的办法是跑一次 `--all`（8 个项目 / 44 秒 / 几分钱）。**
**⚠️ 代价要主动说：`--all` 会把这 8 条判断全部重写，措辞会变** —— 用户会以为「你改了规则」，其实是它重读了一遍证据。**不说这句，他会怀疑数据被动过。**

**★★★★ 泛化：任何「后加的时间戳／来源／版本字段」，历史数据一律补不回来。**
要么显示「未知」（诚实），要么整体重算一次（准确但内容会变）。**不要拿当前时间冒充历史时间 —— 那比不显示更糟。**

**④ ★★★★ 手工改过 `_进度总表.md` 之后，「有变动的项目」永远为空 → 判断永久卡在旧版本**

**这是「增量判断」这条设计的自伤：** 判据是 `项目最新文件 mtime > 总表 mtime`，
而**只要我手工改一行总表**（比如把「停滞 7 天」改成「已结束」），总表 mtime 就跳到当前
→ 之后所有项目的文件都比它旧 → **永远不判 → 判断冻在那一刻，而看板看起来完全正常。**

```
实测：12:22 判完 → 修了队列指令里的版本号（改了总表一行，mtime → 23:00）
     → 之后再跑 judge_lite 都说「没有需要重新判断的项目」
     → 卡片上还是 12:22 那句旧判断
```

```python
# ✓ judge_lite.py 加一个强制入口，绕过 mtime 判据
if "--force" in sys.argv:
    i = sys.argv.index("--force")
    names = [a for a in sys.argv[i+1:] if not a.startswith("--")]
    todo = [(n, 0.0) for n in names if os.path.isdir(os.path.join(ROOT, n))]
```

**⚠️ `todo` 的元素是 `(名字, mtime)` 元组** —— `--force` 只 append 字符串会炸
`ValueError: too many values to unpack`。**加参数时要顺着既有数据结构走，别只看变量名。**

**★★ 泛化：任何「用文件 mtime 当水位线」的增量机制，都必须配一个「手工改过水位线文件」时的逃生口。**
否则它不会报错，只会安静地停止工作 —— 而「安静地停止工作」和「一切正常」在界面上长得一模一样。
**★ 顺带：改完 `--force` 必须回读那句判断，确认措辞真的变了**（不是只看 exit 0）。

#### ★★★★★ 怎么证明「刷新真的会更新判断」—— 用 touch 造一次真变动

### 3.13 ★★★★★ 第三个状态：做完了 ≠ 停滞（2026-11-14，本轮最后一条）

**用户原话**：「某本地地图项目，**已发布，进入正常运作阶段，可以视为阶段性结束**，下次更新大概率是版本更新迭代。」

**★ 这句话暴露的不是一个显示问题，是一个建模缺陷：**

```
系统只有两个状态：在动 / 停滞
没有第三个：做完了
```

**★★★ 后果**：地图不再出现在日报里 → 它掉进「21 天以上已停」那一堆 → **和 17 个半途而废的项目并排** → **把成绩记成了失败。**

> **「完成」比「停滞」更需要一个明确的名字。**
> 停滞会自动出现在「已停」列表里被当成垃圾；完成的项目被归到那里，就是把成绩记成失败。

#### 做法：CONFIG 加一个 dict，三处联动

```python
# CONFIG
PAUSED_PROJECTS = {
    "某本地地图项目": "已发布 · 正常运作 · 等版本迭代（2026-11-14 收尾）",
}
```

| 位置 | 之前 | 现在 |
|---|---|---|
| 证据包 | 混在 focus 里，等它停 21 天后归入"已停" | **单独「## 三、已收尾」一节**，并明写「不要写「现在/建议」」 |
| 看板标签 | 「原文无状态标记」（灰） | **`✅ 已收尾`（绿，`statusOf` 加一条 `if (text.includes('✅'))`）** |
| 看板右上角 | 「6 天没动」 | **`— 已收尾`**（`isDone` 时短路，不走天数分支） |
| 每日日报 | 每天问「要不要催审核」 | 一行带过，不进「21 天以上」名单 |

**★ 复活方式**：从 `PAUSED_PROJECTS` 删掉那一行即可，不用改别的。
**★ 判断层见「三、已收尾」时仍然能看到它** —— 不是隐藏，是**改了它对判断层的意义**。

#### ★★★★★ 附带踩到的一个坑：新状态被旧流水盖住

**改完之后，地图卡还是显示「6 天没动」，✅ 没出来。**

```
根因：卡片的「状态 / 天数」优先读 flowFor()（历史流水行），
　　 而不是刚写的【汇报行】
→ 汇报行里写了 ✅，却被一条旧的「- 11-13 — 6 天没动」盖住
```

**⚠️ §3.7 ③ 那个 fallback（`flowFor(...) || {text: r.line}`）救不了这个** ——
因为 `flowFor` **找到东西了**（找到的是旧的），所以根本不会回退到汇报行。

```js
// ✗ 旧：优先流水行，汇报行只当兜底
const days = f ? (f.text.match(/(\d+)\s*天没动/)||[])[1] : null;
const st   = f ? statusOf(f.text) : null;

// ✓ 新：状态优先读【汇报行】（判断层刚写的），流水行只兜底
const days = (r.line.match(/(\d+)\s*天没动/) || f.text.match(/(\d+)\s*天没动/) || [])[1] || null;
const st   = statusOf(r.line) || statusOf(f.text);
```

**★★★★ 这和「匹配器看整个文件」（§3.5.1 ①）是同一个病：新判断被旧数据压住。**
**凡是「历史流水 + 当期判断」并存的界面，都要明确谁优先 —— 答案永远是当期判断。**

#### 泛化

> **两态模型（有/没有）在「完成」这件事上一定出错。**
> 任何「进度 / 状态 / 健康度」系统，最少需要三态：**在动 / 停了 / 做完了**。
> 前两态靠时间算，第三态只能人给 —— **所以它必须是一个需要用户开口才能设置的状态，不能靠推断。**
> ★ 推论：**别试图从「N 天没动 + 有没有交付物」自动推断「已完成」** —— 那正是本次没做的事，也是对的。

#### 3.13.1 ★★★★★ 第四态：暂停 ≠ 已收尾（2026-11-15，三态还不够）

**三态刚上线第二天就发现不够。** 他一天之内给出四个项目决策，其中三个要标「暂停」。

```python

    "客户 B":       "暂停中 · 只有 2 个文件、0 次执行",
    "示例新媒体运营": "暂停 · 工作台并入内容看板",
}
```

**★★★ 为什么不能复用「已收尾」**：
```text
标成 ✅ 已收尾 → 撒谎（它没做完），而且下次真做完时状态已经用掉了
不标          → 显示「28 天没动」，像是在催他 —— 但他已经决定停了
```

**做法：在 §3.13 那套机制上加两处，共三处联动。**

| 位置 | 改什么 |
|---|---|
| `statusOf()` | 加 `if (text.includes('⏸')) return {key:'pause', color:'var(--mut)', label:'⏸ 暂停'};` |
| 卡片天数 | `isFrozen`（pause 或 done）时 `days = null` —— 不让「⏸ 暂停」和「28 天没动」同屏 |
| MD 汇报行 | 「现在 ⏸ **暂停**。实况…」—— 符号必须写在**现在**字段里 |

**★★★★ 三个坑，一个比一个隐蔽：**

**① `statusOf` 的符号判断有【顺序】，而且顺序错了全盘皆错**

```js
// ★ 顺序：🔴 > ⚠️ > ⏸ > ✅ > ▸
if (text.includes('⚠️')) return {... label:'⚠️ 建议标 ⏸ 暂停'};   // ← 这条 label 里就含 ⏸！
if (text.includes('⏸'))  return {... label:'⏸ 暂停'};
```

**把 ⏸ 放在 ⚠️ 前面 → 所有带 ⚠️ 的卡全部变成「暂停」。**
根因：`⚠️` 那条的标签文案是「建议标 ⏸ 暂停」，作者为了说清建议，把目标状态写进了文案里。
**★ 泛化：状态翻译函数里，标签文案自身含状态符号是常见陷阱 —— 判断顺序要按「多具体」排，不是按代码里出现的先后。**

**② 必须传 `r.now`，不是 `r.line`**

```js
const st = statusOf(r.now) || statusOf(f.text);    // ✓
const st = statusOf(r.line) || statusOf(f.text);   // ✗
```

**「建议」里写「做不到就诚实标 ⏸」是给用户的话，不是当天状态。**
传整行 → 任何建议里提到 ⏸ 的项目都会被判成暂停。
**★ 这是 §3.13「新判断被旧流水压住」的镜像版：这次是「建议污染状态」。**

**③ 暂停/已收尾必须短路天数**

```js
const isFrozen = st && (st.key === 'pause' || st.key === 'done');
const days = isFrozen ? null : (r.line.match(/(\d+)\s*天没动/) || ...);
```

实测：客户 B右上角原本显示「28 天没动」，下面又挂一个「⏸ 暂停」—— **两句话互相打脸，用户不知道该信哪个。**

**★★★★ 收尾时顺手做的一致性问题：`**` 残留**

`**准备暂停**` 在 HTML 纯文本里不产生加粗，只是脏字（同 `workbuddy-brief-writing` 验收节 Ⅱ）。
→ 加 `stripMd()` 套在 `esc(c.now)` / `esc(c.advice)` / `esc(f.advice)` 上。
**★ 但「原文照录」区要保留原样** —— 那是原文，改了就违反「原文照录」这个承诺本身。

#### 设计五条（每一条第一版都踩过）

**① ``` 块 = 重点卡，不是代码块**

聚焦页里 **36 个 ```** —— 那是他的「重点框」习惯（圈要点），不是代码。
✗ 直接 `markdown.markdown()` → 满屏 `<pre>` 等宽代码，读者以为是技术文档
✓ **预处理**：``` 块换 `<div class="pt">`，保留内部行、转义 HTML、`<br>` 连行

```python
def preprocess(md_text):
    blocks = []
    def repl(m):
        inner = m.group(1).strip("\n")
        blocks.append("\n".join(esc(l) for l in inner.split("\n")))
        return "\n\n@@PT%d@@\n\n" % (len(blocks) - 1)
    out = re.sub(r"```[a-zA-Z]*\n(.*?)```", repl, md_text, flags=re.S)
    return out, blocks          # ★ 占位符，渲染完再换回 <div class="pt">
```

**② 顶部只放「本周三件」，不要放「三层排序」**

第一版顶部放了三层三张卡 + 正文又有三层表格 → **同一件事出现两次，看的人会犹豫「以哪个为准」。**

**★★★ 但正文那一段不能整段跳掉** —— 里面除了表格还有「一条纪律」和「26 天实际教训」两行。
所以：**顶部 = 本周三件（最高频）；正文 = 三层排序（含那两行要点）**。

**★ 判据（可泛化）：顶部和正文重复时，先算「哪边少了东西」再决定删哪边。**
这次正文那边多了两行，所以删的是顶部。

**③ 正文跳过「方向定案」段**

方向已在大字标题 + 副标题；**理由那句搬到副标题**（`extract_direction_sub()` 抽 `理由：` 那行）。
→ 正文从第一个 `##` 开始，否则一级标题和「> 更新时间…」引用块会再出现一遍。

**④ 卡片单元格是【原始 md】，要自己转粗体**

表格抽出来的是 `**示例小店 SKU1 上架**` —— markdown 还没渲染过这一格。

```python
def md_inline(s):                      # 不给卡片用 esc()，要用这个
    s = esc(s)
    s = re.sub(r"`([^`]+)`", r'<code>\1</code>', s)
    s = re.sub(r"\*\*([^*]+)\*\*", r"<b>\1</b>", s)
    s = re.sub(r"\[([^\]]+)\]\(([^)]+)\)", r'<a href="\2">\1</a>', s)
    return s
```

**★ 症状很扎眼**：卡片上直接显示 `**示例小店 SKU1 上架**` 两个星号 —— 一眼就看出是没渲染。

**⑤ 配色复用同一组 CSS 变量**

`:root{--bg:#f6f7f5; --accent:#2f6b58; …}` 跟项目看板同一套。
**★★ 两个页面看起来像一个系统，不是两个工具** —— 这比任何视觉设计都重要。

---

#### 三个技术坑

**① ★★★ CSS 里的 `100%` 会把 `%` 字符串格式化搞崩**

```python
html = """... .body table{width:100%;} ...""" % (title, body)
# ValueError: unsupported format character ';' (0x3b) at index 2848
```

→ **模板一律改用 `@@PLACEHOLDER@@` + `.replace()`**，不要用 `%` 或 f-string（f-string 会撞 CSS 的 `{}`）。
**★ 泛化：往 HTML/CSS 模板里做变量替换，三种格式化方式里只有 `.replace()` 是安全的。**

**② 导航标题不能只去符号，要去括号内容 + 截断**

```python
# ✗ 只去 ★ 和空格 → 「判断标准（筛子 · 2026-10-」「①收入线 · 11-20 重排：只剩小」
t = re.sub(r"[★☆\s]+", "", title)[:16]

# ✓ 去括号 + 去修饰 + 截 12 字
t = re.sub(r"[（(][^）)]*[）)]", "", t).strip()
t = t.replace("·", " ").replace("形态已定：", "").strip()[:12]
```

**★ 而且正文里删掉的段（方向定案）要从导航里一起删** —— 否则点过去是空白。

**③ 锚点 id 的顺序必须和导航一致**

`build_nav()` 遍历 `##` 时的序号，必须等于正文渲染后 `<h2>` 的序号。
本次能对上是因为「方向定案」在**两边都被跳过**（导航 `continue` 在 append 之前，正文 `re.sub` 删掉），
所以第一个留下来的都是「三层排序」→ 同为 `s0`。
**★ 只要一边跳过、一边不跳，全部锚点就会错位一格 —— 点了跳到隔壁段，而且不报错。**

#### 双向入口 + 一次刷新全重建

```
index.html 右下角　→「聚焦看板 →」（fixed 定位，inline style，别动 CSS 块）
focus.html 右下角　→「← 项目进度看板」
```

**★★★★ `/refresh` 里在 `--board` 之后追加 `build_focus.py`，失败不影响主看板：**

```python
focus_ok = False
try:
    fb = subprocess.run([sys.executable, BF], cwd=SCRIPTS, capture_output=True,
                        text=True, encoding="utf-8", errors="replace", timeout=120)
    focus_ok = fb.returncode == 0 and os.path.exists(FOCUS)
except Exception:
    focus_ok = False
return {..., "focus": focus_ok}
```

**静默版 `.cmd`（refresh_board.py）也照做** —— 两个入口行为必须一致，否则「双击 .cmd 时聚焦页更新、点按钮时不更新」这种半更新最难查。

**★ 判据：任何一个「源在库外、成品在库内」的看板，刷新按钮必须一次重建全部。**
只重建一半时，用户改了源、点了刷新、看到旧页面 → 结论只有一个：「按钮坏了」。
这和 §3.12「第五类自我污染」是同一个病：**用户不区分「哪一半没更新」，他只看「有没有变」。**

### 3.16 ★★★★ 第三块：单页外壳，两个看板用标签页切换（2026-11-20）

**他的原话**：「**项目进度看板和聚焦看板，能不能放在同一个网页中，用标签页的方式切换**」
后一句要求：「**把切换的标签放在中间**」

**★★★ 判据：第二个看板做出来之后，「两个页面互相跳」一定会被要求合并成一个。** 提前知道结论就不必先做跳转按钮再返工。

#### 用 iframe，不要把两个看板合成一个文件

```
两个看板各有一套 h1/h2/table/.wrap 样式 → 合并会互相污染
项目看板还有 36KB 渲染逻辑（卡片/剪贴板/刷新按钮） → 搬过去等于重写
→ iframe 完全隔离：两个看板【一个字节都不用改】= 零回归
```

```
_看板/
├── home.html   ← 外壳（标签页），serve 的 "/" 指向它
├── index.html  ← 项目看板（不变），"/project"
└── focus.html  ← 聚焦看板（不变），"/focus"
```

**★★★ 关键：外壳用新文件名，不要覆盖 index.html。** 覆盖了之后 `--board` 每次重新生成又会把它冲掉；而且双击 `index.html` 的老习惯会被打断。**新增一个入口，比改掉一个旧入口安全。**

#### 布局：grid 三栏做真居中

```css
.bar{display:grid;grid-template-columns:1fr auto 1fr;align-items:center}
.left{justify-self:start} .tabs{justify-self:center} .right{justify-self:end}
```

**★ 不要用 `position:absolute;left:50%` 居中** —— 刷新提示变长时会跟标签重叠。grid 的 `1fr auto 1fr` 是「左右等宽、中间固定」，永远不会撞。

**★★ 提示文字必须限宽**：`.hint{max-width:340px;overflow:hidden;text-overflow:ellipsis;white-space:nowrap}`
不加这条，一句「✓ 已刷新 18:32（重写了 2 个判断），重新加载…」就会把中间的标签挤歪 —— 而他刚要求标签居中。

#### iframe 高度的写法（不写对就是双滚动条）

```css
html,body{height:100%;margin:0}
body{display:flex;flex-direction:column;overflow:hidden}
.stage{flex:1 1 auto;position:relative;min-height:0}   /* ★ min-height:0 是关键 */
iframe{position:absolute;inset:0;width:100%;height:100%;border:0}
iframe[hidden]{display:none}
```

**★ 漏了 `min-height:0`，flex 子项的最小高度会撑成内容高度 → 双滚动条。**

#### 三处交互，缺一个就难受

```js
// ① 切标签时 reload —— 另一个标签里可能刚点过刷新，不 reload 会看到旧缓存
try { frames[which].contentWindow.location.reload(); } catch(e){}

// ② 全局刷新：POST /refresh（它已经重建两个看板）→ 两个 iframe 都 reload
['project','focus'].forEach(k => frames[k].contentWindow.location.reload());

// ③ 支持 ?tab=focus 深链，方便从别处直接打开聚焦页
```

#### ★★★ 子页面自己的「跳到另一个看板」按钮，在 iframe 里要自动隐藏

```js
// index.html 与 focus.html 各加一段
if (window.self !== window.top) {
  document.getElementById('toFocus').style.display = 'none';   // 或 .back
}
```

**★★★★ 理由：顶部已经有标签可切，右下角再挂一个浮动按钮 = 同一件事两个入口，用户会犹豫该点哪个。**
**★ 反过来也要保留：单独打开 index.html / focus.html 时，那个按钮还是有用的 —— 所以是「条件隐藏」，不是「删掉」。**

**★★ 判据（可泛化）：任何「页面内跳转」的控件，在被嵌入到带导航的外壳里时都该隐藏。** 用 `window.self !== window.top` 一句话判断，不要为它加配置。

**★ 实测：`file://` 双击 home.html 也完全可用**（iframe 加载同目录 file:// 不受 CORS 限制，只有 fetch 受限 —— 而 fetch 打的是 `http://127.0.0.1:8765`，服务端已开 CORS）。所以不必逼用户记地址，双击和地址两条路都通。

### 3.17 ★★★★★ 队列状态不是事实，产物才是事实 —— 「指令与进度不符」的唯一诊断顺序

**他的原话（配截图）**：「我刚刷新了看板，但现在这个指令明显与项目的进度不符。你检查下哪里出了问题」

**截图上的矛盾长这样：**

```
现在到哪：v9 大幅重构，B1/B2 已交付，B3 尚未接入 render     ← 进度说做到了 B3
⚠ 待发给 WB（3）：
   · 写作区加两个写作法按钮                                   ← 三条看着都像"还没做"
   · 顺带一件事：未归位角度清单
   · README 从 v5.1 重写到 v9
```

#### ★★★★★ 第一件事：不要先怀疑判断层

**判断来自 WB 的工作报告（24,268 字压成 1,212 字），它说 B1/B2 交付、B3 未接入 —— 这是准确的。**
**错的是队列：第一条早就做完了，只是没打勾。**

#### 诊断顺序（照这个走，不要跳）

```bash
# ① 队列里到底挂着什么
sed -n '/## ⏳ 待发/,/^## /p' _给WB.md | grep -E "^- \[ \]"

# ② ★ 去【产物】里找实现证据 —— 这一步才是判据
grep -oE "ww-[a-z-]{2,20}" board.html | sort | uniq -c
#   → ww-close / ww-copy / ww-err / ww-inst / ww-mat / ww-txt 全在 = 弹层做完了
grep -nE "WRITER_DIR|WRITER_KHZ|WRITER_MARK" build_board.py
#   → 三条路径 + 提取标记都在 = 我要求的读文件不硬编码也做到了

# ③ 对照另一条真没做的
grep -oE "v[0-9]+\.[0-9]+" README.md | head -3   # 还是 v5.1，mtime 停在 11-15 → 确实没做
```

**★★★★★ 判据一句话：队列是「我以为的状态」，产物是「实际的状态」。冲突时永远信产物。**

**★ 而且验证要落到**具体函数名/元素名**上，不要停在「board.html 里有『写作法』10 次」——
那 10 次里大部分是素材正文里凑巧出现的词。**先看上下文再下结论**（我第一次就差点被这个数字骗了）。

#### ★★★★ 根因：打勾是隐性劳动，停掉自动化不会有报错，只会让队列慢慢变脏

```
当天早上：用户说「wb 监听不需要每 15 分钟跑一次」→ 停掉 wb_watch cron
我当时说：「手动反而更准，我在场能拦住误判」
下午：WB 做完了写作法按钮 → 没人打勾 → 队列显示 [ ] → 他以为不符
```

**★★★★ 我那句「手动更准」只对了一半：准是准，但前提是「有人跑」。**
**停掉一个自动化之前，先列出「它原来在替谁干活」—— 打勾是零报错的活，所以它消失时你听不见。**

**★★ 泛化：任何「人不在场就跑不了」的机制，都会在忙的时候第一个被跳过。**
它不会失败，只会积累 —— 而积累的表现是「数据看起来没错，但其实过期了」。

#### 修法与两个选项（给他选，不要替他定）

```
① 手动补一次打勾：把那条从 ⏳ 移到 ✅，并在行尾标交付证据
   （备份 → 改 → 验证待发条数 N→N-1、✅ 段新增 1 条、其余项目一行没动）

② 恢复低频 cron：每天 12:00 + 21:00 各一次
   ★ 纯脚本、零 token，只做「比对 + 打勾」，不派单（派单仍归人）
   ★ 理由：打勾本质是「比对文件状态」，不需要 LLM，所以低频足够
```

**★★★ 推荐 ②**：一天两次足够，成本几乎为零；而且它只打勾不派单，比原来那个「自己打勾 + 自己派单」的版本边界更清楚。

**★ 但无论选哪个，都要把这句话说给用户听：**
> **「判断没错，错的是队列 —— 它停在你停 cron 的那一刻。」**
> 不要含糊成「数据有不同步」，那会让他怀疑整套数据。

#### ★★★★★ 第四层：指令【正文里的目标版本 / 条数】也会过期 —— 而且比「没打勾」更贵

**同一次核对里，两条待发指令都是「状态对、参数错」：**

| 指令原文 | 实测 | 后果 |
|---|---|---|
| README 从 v5.1 重写到 **v9** | 看板已是 **v10**（14:58 升的） | 做完了也是过期的文档 |
| 把 **2 条**未归位角度写成清单 | 实际 **3 条**（母素材含全角 `／` 的有 L156/L161/L162） | 漏一条，清单不完整 |

**★★★★★ 关键区别：** 打勾漏了只是「看板显示不对」（可逆）；
**目标版本写错是「做出来的东西本身是旧的」** —— 执行 Agent 会老老实实按 v9 写完，
然后那篇 README 从生成那一刻起就是错的，而且**没人会回头重写第二遍**。

**判据（动手派单前的小检查）：**

```
指令里凡出现 版本号 / N 条 / N 个 / N 处 —— 都要当场重新数一遍，不要信写指令时的数
① 版本号 → grep 产物里的当前版本（grep -oE "v[0-9]+\.[0-9]+" board.html | head -2）
② 条数   → 用生成这些数的同一条命令重跑（如 grep '／' 角度-账号对照.md | wc -l）
③ 如果数不出来 → 指令里改成「以实际为准，先数再写」，不要写死数字
```

**★★ 根因：队列是「写指令那一刻的快照」，而项目一直在动。**
所以**队列的正确写法是「目标状态」而不是「目标版本号」**：
```text
✗ README 从 v5.1 重写到 v9
✓ README 重写到与 board.html 当前版本一致（先 grep 确认版本号，不要照抄这条里的数字）
```

**★★★★ 泛化：任何「写死的具体数字/版本」的指令，都会在执行前失效一次。**
要么派单时重算，要么把指令改成「以当前状态为准」的相对表述。

### 3.18 ★★★★★ 「刷新时检查打勾」—— 但机器只能提示，人点确认才动手（2026-11-20）

**他的原话**：「**打勾能不能做成手动版？刷新的时候就检查打勾？**」

**★ 这句话把 §3.17 的「没人打勾」补上了闭环：他不想记着跑脚本，也不想机器自己勾 —— 要的是「刷新时机器帮我看一眼，但最后的勾由我点」。**

#### ★★★★★ 第一版做了全自动，实测当场推翻

**先写的 `tick_queue.py` 是「扫 memory → match_done → 直接 tick_item」，干跑第一条就露馅：**

```
[tick·干跑] 内容看板@WorkBuddy ← 「11-20 README 从 v5.1 重写到 v9…」（标识符重合 10 个）
```

**而 README 当时还是 v5.1（mtime 停在 11-15），这件事根本没做。**

**★★★★★ 为什么阈值 ≥2 也挡不住（这比 §3.5.1 证伪① 更根本）：**

```
WB 的 memory 里【到处是】「已完成 / 已交付 / 跑通」
WB 的 memory 里【也会】提到 README（它是项目说明，天天被引用）
→ 完成信号 ✓ + 标识符 ✓ + 重合 10 个 ✓ → 判「做完了」
```

**★ 这不是阈值不够高，是判据本身缺少「这件事」的语义。** 调阈值只会让它更漏，不会让它更准。

**★★★ 结论：`match_done` 只能当【怀疑】，不能当【判决】。**

#### 形态：机器提示 → 卡片上出现确认条 → 人点了才写

```
刷新（页面加载 / 点 ⟳）
   → GET /suspects  → 扫各项目队列 + 最近 2 天 memory → 疑似清单
   → 卡片在「⏳ 待发给 WB」上方插一条米黄色：
      ⚠ 疑似已完成　11-20 README 从 v5.1 重写到 v9（只改 `README.md`…　
                                    标识符重合 10 个　[✓ 确认完成]
   → 点「确认完成」→ POST /tick {project, fp} → 打勾 → 700ms 后 reload
```

**三个文件，各管一段（互不侵入）：**

| 文件 | 职责 | 关键点 |
|---|---|---|
| `check_queue.py` | `suspects()` 只读检查 + `do_tick(proj, fp)` 打勾 | ★ 独立于 `wb_watch.py`：不写 state、不派单、不心跳 → **零副作用，可以随便跑** |
| `serve_board.py` | `GET /suspects` / `POST /tick` | 直接 `import check_queue` 调函数，不起 subprocess |
| `_template.html` | 插提示条 + 确认按钮 | `boardAPI` 绝对地址（同 §3.12 ④再续） |

#### 两个实现细节（都会咬人）

**① ★★★★ 打勾要用「条目指纹」，不能用索引**

```python
# ✗ 索引会在 tick_item 之后失效；而且队列被别人改过就勾错
# ✓ 用 queue.py 的 fp(item)，前端把它原样回传
for i, it in enumerate(q["items"]):
    if Q.fp(it) == fp:
        return Q.tick_item(qf, q, i, stamp)
return {"ok": False, "out": "队列里找不到这条（可能已经打过了）"}
```

**★ 「可能已经打过了」这句要留着** —— 双击两次、或者另一处刚勾过，都会走到这里，不能报「失败」。

**② ★★★ 干跑时不要循环 —— 但【检查】必须逐条判断，这两件事别搞混**

第一版干跑输出了 **6 条一模一样的** —— 因为它 `while ticks < MAX_TICKS` 循环，而干跑不真打勾、索引不变，同一轮反复命中同一条。
→ **修对了：干跑不循环。**

**★★★★★ 但同一句「只取第一条」被我顺手也写进了 `suspects()` —— 于是漏报（2026-11-20 当晚实测）：**

```
队列 2 条，WB 两条都做完了
check_queue 只报 1 条（match_done 一次调用只返回分数最高的那一条）
→ 卡片上只出现「疑似已完成 1 条」→ 另一条永远等不到确认 → 用户看队列没变，以为看板坏了
```

**★★ 这违反 §3.5.1 已写死的原则：漏打勾只是显示不对，漏【报】是让那一环永远断掉。**

```python
# ✓ 检查路径：逐条独立判断（队列切成单条再问 match_done），用【指纹】去重
seen = set()
for i, it in enumerate(q["items"]):
    f = Q.fp(it)
    if f in seen: continue
    idx, why = Q.match_done(mem, [it])      # ★ 只传这一条
    if idx is None: continue
    seen.add(f)
    out.append({..., "idx": i, "fp": f, "why": why})
```

**★★★ 三条判据（可泛化到一切「批量判定 → 逐项提示」的界面）：**

```
① 干跑 / 只读模式：禁止 while 循环（没有副作用推进，必然死循环刷屏）
② 检查 / 列举模式：必须逐项独立判定，禁止「只取 Top1」
③ 去重键用稳定指纹，不用索引 —— 索引在别人改过队列后就失效
```

**★ 症状特别阴**：只报 Top1 时页面看起来完全正常（有提示条、有按钮），你只会觉得「怎么这么少」。

**★★ 泛化：任何「干跑模式」都要保证和真跑走【不同的控制流】** —— 真跑靠副作用推进，干跑没有副作用，同一个 while 循环就变成死循环。
**但「控制流不同」不等于「判据不同」** —— 干跑可以少做事，检查可以多做事，两者都不能偏离「哪些条目算命中」这个判据本身。

**③ ★★★ 一个项目多条 → 合并成一条提示 + 一个「全部确认」**

**实测：两条都做完了，却要一条条点 —— 太碎。**

```
⚠ 疑似已完成 2 条        中文短语重合 7 个
 · 11-19 顺带一件事：把 3 条未归位角度…
 · 11-20 README 从 v5.1 重写到 v10…
 [✓ 全部确认（2）]  [先不管]
```

**按 `project` 分组，一次点按顺序 POST 打完，逐条标 ✓/✗，全成功才 reload。**
**★ 必须加「先不管」** —— 假阳性时他要能把这条黄条按掉，否则它一直挡在「待发给 WB」上方。

**④ ★★★★★ 队列「0 条」必须写明语义，否则判断层会幻影出一个动作**

**实测：两条打勾完之后重判，建议写的是 ——**

```
建议 打开 board.html 实机验收…，确认后把 README 重写和索引修复在 _给WB.md 里打勾收尾
                                                              ↑ 已经打过了
```

**根因：证据里只写「队列待发 0 条」，模型读到 0 会自己脑补「那还没打勾」。**

```python
return "0 条（已全部打勾完毕 —— ★ 不要再建议「去打勾收尾」，已经打过了）"
```

**★★★★ 泛化：给 LLM 报「零值」时，必须同时说清「零意味着什么」。**
`0` 在不同业务里含义可以完全相反（「还没开始」vs「已经全部完成」），模型不知道你在哪个语境里。

**⑤ ★★★★★ 队列挂着 ≠ 没做 —— 这条必须写进 evidence，不能只改 prompt**

**实测：队列两条都做完了但没打勾 → judge 看到「队列待发 2 条」→ 建议「先清队列」→ 让他去做已经做完的事。**

**光在 SYSTEM 里写「优先指向队列第一条」不够（§3.2.2 已证）—— 那条规则本身没错，错的是它不知道这些条目已经完成。**

```python
blocks.append(f"- **队列待发（`_给WB.md` 的「⏳ 待发」）**：{qp}")
blocks.append(
    "  > ★ 写「建议」时的三条规则：\n"
    "  > ① **先对照下面 memory 的最后几个小节**：如果某条待发已在 memory 里"
    "写了「已完成/已交付/已重写」，说明它**做完了只是没打勾** —— 建议要写"
    "「先确认打勾，不要重做」，绝对不能建议重做一遍。\n"
    "  > ② 确实还没做的 → 建议指向第一条没做的那条，说清是哪一条。\n"
    "  > ③ 队列全空 → 才建议「验收/确认/收尾」类动作。\n"
    "  > ★ 队列和判断是两套数据，队列不会自动打勾，所以「挂着」不等于「没做」。")
```

**改完实测（同一项目、同一份证据，只加这段）：**

```
现在 队列里两条待发都已在 11-21 凌晨的日志里做完：README 已从 v5.1 整篇重写到 v10，
     未归位角度索引错位也已修，只是队列没打勾。
建议 先核对 _给WB.md 里这两条待发并打勾收尾，不要重做 README 重写和未归位角度修复。
```

**★★★★ 从「去做已经做完的事」变成「确认打勾，别重做」—— 这才是对的。**

**⚠️ 这是 §3.2.2「把数据塞给它 ≠ 它会用」的第二次发作：字段给了，没给这个字段的【上下文含义】。**
**判据：任何「状态类」字段进 prompt，必须同时给「这个值意味着什么 + 该怎么用它」。**

**⑥ ★★★ 跨天：00:0x 时 memory 还是昨天那个文件名**

**实测：11-21 00:01 刷新，WB 的新记录（`## 00:0x（11-21 凌晨）README 重写`）写在 `2026-11-20.md` 里。**
→ 按「文件名 ∈ 最近 2 天」筛选仍能读到（11-20 在窗口内）；**但若写成「文件名 == 今天」就会全部读不到，而且不报错。**
**★ 所以 `LOOKBACK_DAYS` 至少 2，且不要用「文件名 == 今天」这种写法。**

**⑦ ★★★★★ 派单文件 ≠ 执行成果 —— 判断层会把「我写的指令」当成「它干完的活」**

**实测：刚写完 `WB指令-空本子v1.1三件（2026-11-21）.md`（派单说明书），重判立刻写出**

```
现在 空本子 v1.1 三件（删排期/实时字数/翻月）已产出 WB指令文件与配套文档，但无 WorkBuddy 工作日志…
                                                                        ↑ 一个字活都没干
```

**根因：证据包里的「最近改动的文件」列出了这个文件名，而它带着「WB」两个字 + 任务全名**
→ 模型看到「文件已存在 + 名字就是那个任务」→ 直接当成进展。

**★★★★ 这是通用陷阱：每个项目的 `WB指令-*.md` 都由我（或用户）写，名字里必然带任务描述。**
只要它出现在「今日新增」里，判断层就可能把它读成成果。

**修法：在证据包里加一条硬提示（不是改 prompt 里的规则，是加在数据旁边）：**

```python
if any("WB指令" in os.path.basename(f) for f in list(info.get("files") or {})[:40]):
    blocks.append("- ★ **注意**：上面出现的 `WB指令-*.md` 是**派单文件**（由泽哥或 Hermes 写的执行说明书），"
                  "**不是 WorkBuddy 的产出**。看到它只能说明「活派出去了」，不能说明「活干完了」。"
                  "判断进度只能看 WorkBuddy 的 memory 和实际产物文件。")
```

**改完实测：**

```
现在 空本子.html 等 8 个文件今日新建、README 已写明 v2 候选和 7 步验证法，但无 WorkBuddy 工作日志，看不出做到哪一步。
```

**★★★ 泛化（和 §3.17「队列状态不是事实，产物才是事实」是同一条的下半句）：**
**「输入侧的文件」和「输出侧的文件」必须能被区分开。**
项目目录里同时住着「我要它做什么」（`WB指令-*.md` / `_给WB.md`）和「它做成了什么」（产物 / memory）——
**任何按「最近改动」取信号的逻辑，都会把前者当成后者。**

**★ 判据：给判断层看的文件清单，凡是「我们自己写的」都要么排除、要么标注来源。**
排除不了（它的存在本身就是信息）→ 就必须标注，不能让它裸着出现。

📎 这五轮的完整经过（5 个 bug 的实测数据、修前修后判断对照、队列与 memory 的时间线）→ `references/04-打勾与队列.md`

#### 必须主动交代的一件事：假阳性比例

**实测 2 条待发里 1 条是假阳性（50%）。**

**★★★ 这个比例要如实说，并给期限：**

> 「现在是 1/2 假阳性，偏高。用一周 —— 如果假阳性超过一半，我收紧判据
> （从「全文都有」改成「完成信号和任务词在同一段」）。」

**★★★★ 不说这句的后果是实的**：假阳性多了，用户会开始忽略那条黄条，于是这个功能就等于不存在 —— 而且比没有更糟，因为他会以为自己漏看了。

#### ★★★★★ 泛化：这一类自动化只有三种形态，按风险选

```
① 全自动（机器判 → 直接写）　　 风险最高，只在「判据是事实不是语义」时用
   例：文件存在 / 校验通过 / 端口能连 —— 判错了也只有一种解读
② 机器提示 + 人确认（本次选的）  语义判断类的默认形态
   例：这件事做完了没有 —— 判错了有两种解读，必须有人兜
③ 不做，只显示原始事实　　　　 连「疑似」都不敢报的时候
   例：项目「够不够好」
```

**★ 判据一句话：判据带语义 → 必须有人确认；判据是事实 → 可以全自动。**
**「完成」是语义（它取决于「哪一件事」），不是事实 —— 所以它永远落在 ②。**

### ★★★★ 6.1 这个脚本自己会咬人 —— 六条实测踩过的坑

```bash
python project_watch.py --init    # 建基线：不报警、不写总表
python project_watch.py --dry     # 只看会输出什么：不写总表、不改 state
python project_watch.py           # 正常跑
```

| # | 坑 | 后果 | 修法 |
|---|---|---|---|
| ① | `--dry` 也写 state | 测试一次就把提醒标成「已报」，真跑静默了 | 保存前判 `if not dry:` |
| ② | `--init` 也往总表写 | 跑两次初始化 → 总表里同一项目**重复三段** | append 前判 `if not init` |
| ③ | **init 不预标已达阈值的档位** | 第二次跑**一次性报 15 条「建议关闭」** → 用户从此不看 | init 时把 `c21/m3/m7/c2` 预标为已报；**但主线和客户项目不预标**（它们重要，必须报） |
| ④ | 想靠改 state 模拟变化来测试 | 脚本会把 state 全量写回，模拟无效 | **建真实临时目录**（如 `zz测试项目-勿动/`）端到端测，测完删目录 + `rm state` + 重新 `--init` |
| ⑤ | 不设文件数上限 | 万文件项目的 state 撑爆 | 每项目只留最近修改的 400 个 |
| ⑥ | 进度文件报整个 tail | 旧内容混进「新增」里 | 只报 tail 的**差集**（见 §3.1） |
| ⑦ | **用 bash heredoc 写带反斜杠的补丁脚本** | `\\n` 被层层转义吃掉，写进文件变成真换行 → `SyntaxError: unterminated string literal`；而且**前面已成功的替换也一起没落盘**（因为 `open(P,"w")` 在最后一行） | 修 Python 源码不要用 heredoc 拼字符串：① 用 `write_file` 把片段写到临时文件再读进来插入 ② 或全程用 `chr(10)` 代替 `\n` ③ 或直接用 patch 工具（它不走转义） |
| ⑧ | **一个脚本里做多处替换，中途 assert 失败** | 前几处「✓」都打印了，但文件没变 —— 看日志以为成功了 | 每处替换**先全部算出、最后一次性写**；或者每处替换后立刻落盘。**看到「✓」不等于文件已改，必须回读验证** |

**★★★ 第 ③ 条最要紧**：一个每天推 15 条的报告，等于没有报告。**"初始化时预标"是让这个工具能活过第一周的开关。**

## 7. ★★★ 实测发现（这类监管真正会照出来的东西）

2026-11-11 泽哥库实测（29 个项目）：

```
一天 5,592 条操作，6 个项目在跑，其中跟客户有关的：0
★★★ 客户 B（A 类客户，最该做的）停了 26 天
★★★ 下单小程序（10,166 文件）当天还在改
```

**结论不是「他在偷懒」，是**：

> **改工具的反馈快，做客户的反馈慢，人都会往快的那边跑。**
> **产品改一行就看见变化；客户要开口、要等回话、要报价。**

**★ 所以监管的落点永远是「哪一摊在偷偷停」，不是「你今天做了多少」。** —— 后者只会变成表扬或指责，前者才能改行为。

### 7.1 ★★★★ 读报告时的三个前提（2026-11-13 巡检地图时全部命中）

**报告只给「多久没动」，它不知道「为什么没动」。** 下面三条必须由人补上，否则结论会错。

#### ① 「N 天没动」可能不是停滞，是**等外部**

```
实测：地图项目「6 天没动」
真相：小程序 1.0.2301 已于 11-08 提审，在等微信审核
→ ★ 不是停，是卡在他控制不了的地方
```

**★ 发现方法**：查项目里的 `.workbuddy/memory/YYYY-MM-DD.md` —— WB 的每日记忆会写「第 N 轮进展：X 已提审」「等 XX key」这种**外部阻塞**。脚本永远读不出这个。

**★★ 说话口径**：「这不是停滞，是卡在审核 —— 这一点它报不出来，我知道。」**先替他分清「可控的停」和「不可控的等」，再谈建议。**

#### ② ★★★ 旧记录里的数字会过期 —— 必须**重新实测**，不许引用自己的存档

同日实测，两处记录全错：

| 存档里写的 | 重新实测 |
|---|---|
| 空壳 16 家 | **75 家（56%）** |
| 网页三处改动「未发布」 | **已发布**（`PICK_SHELL_P = 0`、「摇一下」、「N 条点评」都在线上） |

**★ 判据**：只要这次要基于某个数字下结论，就**当场跑一遍**，不引用上次的结论。
**★★ 网页类项目最快的核法**：`curl` 线上 → 比 bytes + grep 关键参数，30 秒。

#### ③ ★★★★ 数据类项目的建议顺序：**先减量，再补量**

```
总 135 家（hidden 9 → 展示 126 家）
内容丰度（有图 + 有招牌 + 描述≥12字，满分 3）：
  0 分 75 家（56%）· 1 分 35 · 2 分 24 · 3 分 1
→ 能用的只有 25 家，而展示 126 家
```

**★★ 结论：不是「补 75 家内容」，是「先把展示门槛提上来」。**

```
补内容：100+ 家的工程，不是一周的事
减店：只展示 ≥2 分 + 精选 → 约 45 家，★ 半小时能做完
```

**★★★ 判据（可泛化到所有"内容池"类产品）**：
> **展示 N 个半成品，不如展示 N/3 个完整的 —— 前者的每一次点开都在消耗信任。**

**★★★★ 而他自己的产品定位正好证明这一点**：他卖的是「**别白跑**」—— 一家空店点进去，就是白跑一趟。

## 8. 报告口径（对他说话的方式）

- ★ **说事不说人**：报「客户 B 3 天没动」，不报「你又没做客户」
- ★★ **停 ≠ 错**：有些项目停了是对的（已交付、已关闭）→ 提议「标结束」，不提议「赶紧做」
- ★★★ **一次只提一个动作**：报告末尾最多一个「下一步」，不要列待办
- ★ 他说「我在补功能/调试」时，别直接说「你在逃避」→ 给判据让他自己量：
  > **「补功能的当天，有没有一条内容/一次报价因此发生？」**

### ★★★★ 他问「拉一遍 X 之后的所有动作」时：读【已经写好的判断】，不要数文件

**原话**：「你尝试拉一遍 10 月 25 号之后所有的动作，**但我想要的只是精简版，不要把琐碎事情都全部拉进来。**」

**✗ 第一版做错了：按项目统计 10-25 之后的文件数 → 输出里冒出 8658 / 7171 这种数字**，
全是 `node_modules`、构建产物、预览缓存。**一条能用的信息都没有**，而且看起来"很努力"。

**✓ 正解：直接读 `_进度总表.md` 里该时段之后的「## MM-DD 汇报」段。**
那本来就是 LLM 提炼过的「现在 / 建议」，每项目两行 —— **天然就是精简版，不用我再统一次。**

**★★★ 判据：「精简版」的准确含义不是「少写点」，是只留三类 ——**

```
① 改变了方向的       （拍了板：收手 / 授权 / 换方案）
② 产生了成果的       （交付物真的落地了，有文件名/上线/自检通过）
③ 揭示了问题的异常   （8 天 0 动作 / 停滞 35 天 / 队列挂着已完成的事）
```

**其余一律不进**：改了几行代码、跑了几个脚本、生成几个文件 —— 这些是过程，不是动作。

**★★ 输出形状（他认这个）：分「做成的 N 件 / 没动的 N 件」两栏，每件一行带数字。**

```
真正做成的（5 件）
① 内容看板 v3 → v10　← 20 轮改造，selfcheck 26/26
② 空本子　　　　　　← 写作法 ×2 + 五套预设
...
真正没动的（3 件，全是①）
① 11月-收钱线：诊断 0/4 · 报价 0/2 · 收入 0/1，连续 8 天 0 动作
```

**★★★ 两栏比一栏有用得多** —— 单看「做成了 5 件」是表扬，加上「没动 3 件全是①」才是判断。
**而且第二栏必须点出它们属于同一层**（本次全是①收入线）—— 那是唯一能改行为的信息。

### ★★★★ 当他问「现在我实操流程是怎样」—— 给四步卡，不要写文档

**实际问过一次**：「精要简单说下现在我的实操流程是怎样。」

**★ 这类问题的正确答案是「他每天要做的动作」，不是「系统怎么运作」：**

```
① 早上看一眼（3 分钟）→ 飞书那条消息 + 双击看板
② 复制粘贴　　　　　　→ 点卡片上的「复制」→ 粘给执行 Agent
③ 想主动问就说话　　　→ 「刷新 <项目名>」/「<项目> 做完了」
④ 系统会主动找你的只有三种：队列完成 / 日报没跑 / 队列空了
```

**★★ 判据：他问「流程」时想要的是「我要做什么」，不是「你做了什么」。**
一屏之内，四个动作，每条一句话 —— 超过了就是文档，不是回答。

### ★★★★ 他只给一个名词短语时：给现状 + 异常，不要列选项（2026-11-15）

**实际发生的一次：** 他发来的全部内容是 —— **「关于项目进度的看板」**。六个字，没有问号。

**我当时做了三步：**

```text
① 给现状快照（7 张卡、无重复、数据更新于 06:22）
② ★ 主动说一件他没问的异常（队列 12 条「待发」里混了等外部/阻塞项）
③ 用 clarify 列了 4 个选项问他指哪件
```

**★★★ 他回的是四条完整的项目决策 —— 完全不在我列的选项里。**

```text
客户 A → 暂停，但可以当小案例
客户 B → 停了，忘了进度，可当案例客户
内容看板 → 继续推进 + 做成能上传 GitHub 的 skill
示例小店 → 重要性提高
```

**★★★★ 教训：一个名词短语 = 一个话题，不是一个选择题。**

```text
✗ 用 clarify 列选项 → 选项是我脑内的三种可能，他的真实需求在选项之外
✓ 给【现状】+【我发现的异常】+ 留白
  「上面是我看到的。你想说的是哪件？」
```

**★ 因为选项一旦列出来，他会先做「选择」这个动作，而不是说清他真正在想什么。**
**而他说出来的第一句，往往比我的三个选项加起来信息量大。**

**★★ 配套：说现状要带数字和具体异常，不要概括。**
「7 张卡、数据更新于 06:22、无重复」比「看板状态正常」有用 —— 因为后者他不知道我看了什么。
**主动端出异常（哪怕他没问）是他最认可的动作**：那次他直接接着我端出的问题往下走了。
