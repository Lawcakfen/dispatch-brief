# 检验标准（自用版 + 公开版，两套判据）

> **这份是「标准」。`audit_deep.py` 是「执行」。**
>
> ★★ 标准里列了哪几条，脚本就必须跑哪几条 —— 由 `audit_deep.py` 的 S 轨自动比对，
> 不一致就报错。**否则文档会变成下一个「两处真相」。**
>
> ★ 这里**不写总条数** —— 条数会变，写死就会过期（同 B5 那条教训）。

## 为什么必须两套

自用版和公开版的判据是**相反**的，合成一套必然有一半规则失效：

| | 自用版 | 公开版 |
|---|---|---|
| 私有词 | **必须存在**（否则认不出是哪个客户） | **必须 0** |
| 本机路径 | 允许 | 必须收敛到配置 |
| 脚本 | 要能真跑 | 不跑（读者自己装） |
| 内容完整性 | 不能比旧版少 | 不适用（已脱敏） |

## A · 自用版（`skills/productivity/dispatch-brief`）

| # | 判据（怎么算过） | 为什么有这条 | 不过怎么办 |
|---|---|---|---|
| **A1** | `SKILL.md` frontmatter 的 `name` 匹配 `[a-z0-9][a-z0-9-_]{1,63}` | name 不合法 → skill 加载器可能整个不认，且只有换会话才发现 | 改名，别用中文/空格 |
| **A1b** | description 非空且含 `Use when` | 这是触发条件。写空的 → 该用的时候不会加载 | 补一句「Use when …」 |
| **A2b** | 每份 reference ≥ 1000 字符 | **实测踩过**：删了源之后重跑生成器，10 份全被写成空壳，脚本还「成功」退出 | 同上；先看 `git log` 找回上一版 |
| **A4** | 主干 ≤ 400 行 | 超过说明它在偷干 references 的活 → 上下文吃满、定位变慢 | 把细节挪进 references |
| **A5** | SKILL.md 声称「二十条硬判据」→ 实际编号条目数 == 20 | **实测踩过**：写「20 条」但只有 17 条，没人会重数 | 补到 20 条或改标题 |
| **A6** | 声称「N 条坑」→ `06-坑清单.md` 实际行数 == N | 同上，数字会随去重变化 | 改数字，或干脆不写数字（更好） |
| **A7** | 无 `TODO:` / `FIXME:` / `【待补】` / `<占位>`（表格行不算 —— 那里在引述案例） | 留个 TODO 就等于留个洞，而且一个月后自己都不记得 | 补完或删掉那句 |
| **A8** | `git status --porcelain` 为空 | 有未提交改动 = 这次的改动还没进备份，机器一坏就丢 | 跑 `backup_skill.py` |

## C · 交叉逆推（两套之间的一致性）

| # | 判据 | 为什么有这条 | 不过怎么办 |
|---|---|---|---|
| **C1** | repo 里**每一个**生成文件 == `build_plan(自用版)` | **这是最狠的一条。** 它同时抓三种病：①有人手改 repo（下次 build 静默冲掉）②改了源但没重跑生成 ③生成器漏了某个变换 | 跑 `build_public.py`；若不解决，说明有人手改过，用 `git diff` 找出来 |
| **C1b** | 计划里的文件在 repo 里都存在 | 缺文件 = 读者拿到残包 | 同上 |
| **C2** | repo 的 `references/` 里没有计划外的文件 | 多出文件 = 手放的，脱敏没走过门禁 | 删掉或纳入生成 |
| **C3** | `repo/scripts/*.py` 与本地 `scripts/` 逐字节一致 | **scripts 不在生成范围，是手工同步的** —— 改了本地忘了 cp，读者拿到的是旧版，而 B 轨只查语法对不对，查不出「跟本地不一样」 | `cp 本地 scripts → repo/scripts/` 再提交 |

## 什么时候跑哪一层（重要：不是所有检查都该每天跑）

**★★★★ 结构审计（A/B/C）查的是「自洽」。内容不变时它永远绿。**
**每天早上推一条「全部通过」，两周后你就不看了 —— 这是监控最经典的死法。**

```
改完内容 / 发布前  →  python verify_all.py
                      （结构审计 + 4 份单测 + 服务探活，全量）

每天 09:00（cron）  →  check_drift.py
                      只查四件会随时间自己变坏的事：
                        ① 源改了但没发布（repo 落后于自用版）
                        ② 本地与远端分叉
                        ③ 看板服务死了
                        ④ 备份超过 7 天没更新
                      ★ 全正常时【一个字都不输出】—— 没消息就是好消息

每周一 09:30（cron） →  weekly_audit.py
                      跑一次完整结构审计，只输出一行结论。
                      ★ 它的价值不是「再查一遍」，而是发现【检查器自己坏了】
                        （文件被挪走、路径变了 → 审计跑不起来）
```

**★★ 分层的理由：会自己变坏的东西才值得定时查；结构自洽只有「你动了」才会变。**

**★ cron id：`e273ecac3e99`（每天漂移）、`6743703e02f5`（每周审计）。**

## 检查器自己会撒谎（同一天实测四次）

**★★★★ 这四条全是「检查跑了，结论错了」。比没有检查更糟 —— 因为它给你假的安心。**

```
① shell 里比中文文件名的 md5
   git ls-files 把中文名转义成 \346\226\207 → bash 读不到 → 两边都读成空
   → 空 == 空 判「一致」→ 输出「17 个一致 / 0 个不同」
   ★ 其实 11 个中文文件根本没比。改用 Python 读字节才看出真相。

② 改名脚本连「来源标记」一起改
   build_public 靠 <!-- 来源 2/3：xxx --> 决定跳过哪段
   标记里的文件名被改名脚本改掉 → 标记失效 → 内部账本被发到公开仓库
   ★ 而私有词检查是【绿】的（它确实不含私有词，只是「不该公开」）

③ 我自己在 README 里写「Files: 18」当历史引用
   本意是说明「删除旧角标」，结果等于自己留了个假数字
   ★ 被 B5 门禁抓到 —— 这条是门禁干活，不是我聪明

④ py_compile(cfile=os.devnull) 在 Windows 上
   os.devnull = 'nul'，不是普通文件 → 7 个脚本全被判「编译失败」
   ★ 假红和假绿一样有害：假红会让你习惯性忽略红的
```

**★★★ 所以这份标准本身也要被检验：S 轨就是干这个的 ——
文档里列了几条，代码就必须真跑几条（第一次跑就抓到 2 条口头不一致）。**

**★ 判据：一条检查如果从来没红过，要么它没用，要么它坏了。定期故意制造一次失败，看它响不响。**

## 失败的优先级（不是所有红都一样急）

```
立刻修   B9（key 泄漏）· B1（私有词）· A8（未提交）
今天修   C1 / C2（逆推失败）· A2b / A3（内容丢了）· B5（假数字）
可以拖   A5 / A6（声称的数字）· B8（路径没收敛）
```

**★★★ 最重要的一句：门禁全绿 ≠ 内容正确。**
2026-11-21 实测过 —— 私有词 0、死链 0、旧名 0，全绿，
但内部账本（publishing-status）照样被发到了公开仓库上。
**所以 B 轨之外必须有人看一眼 diff。这一条没法自动化。**
