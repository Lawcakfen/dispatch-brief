## 0.3 ★★★★★ 派单之后怎么盯：三句话心跳 + 队列必须分两段

**2026-11-15 他的原话：「我想中间可以加一个心跳机制，在你给我指令之后监测 wb 有没有更新项目的 memory。」**

背景：旧版只在「队列某条被完成」时说话 → **派单之后到完成之间是黑箱**，
他不知道对方收到没有、在不在做、还是卡住了。

### 三句话，不是心跳包

```
① ▶ 它动了    —— 该项目 <工作日志目录> 出现新内容（每个派单周期只报一次）
② ✅ 完成了    —— 队列某条被打勾 + 推荐下一条
③ ⚠ 卡住了    —— 派单满 4 小时 memory 一个字没动（只报一次）

中间它写 10 段 memory 都不报。队列清空 → 三个标记全部重置，下一单重新开始。
```

**★★★ 为什么不做「每 30 分钟报一次」**：他之前嫌过 ——
旧版 09:00–11:30 推了 6 条，直接说「太吵」。**监管必须能闭嘴。**

**★ 「动了」和「完成」必须分开报** —— 这是整个机制的价值所在：
只有 ✅ 一个信号时，你分不清「它在做」和「它没收到」。

### ★★★★ 队列必须分两段，否则心跳会误报

### ★★★★ 队列要分段 —— 但「分没分段」不能用 `grep` 判断

**这是今天最典型的一次「我冤枉了系统」。** 完整经过值得记住，因为它的形状会重演：

```
我用 grep -c "^- \[ \]" 扫 5 个队列 → 得出「合计 12 条待发，只有 2 条是真指令」
据此判定：队列语义混乱，心跳明天会连报四条误报 → 还给用户发了警告

后来用 queue.py 逐个 parse_queue：
  客户 A 1 条 / 项目 B 1 条 —— 真实待发合计 2 条
  其余 10 条全在「## ⚠️ 卡在外部」段
```

**★★★★ 队列本来就是分段的，是 `grep` 不分段。** `parse_queue` 只解析
`^##\s*⏳?\s*待发` 这一段 —— 它一直是对的，心跳从来不会误报。

**★★★ 而那 10 条「等外部」也没问题** —— `## ⚠️ 卡在外部` 段用同样的 `- [ ]` 格式，
是给人看的待办，本来就不该被心跳读到。

**所以正确的判断方式是：**

```python
import queue as Q
q = Q.parse_queue(qpath)
n = len(q["items"])          # ← 唯一可信的数字

✗ grep -c "^- \[ \]"         # 数到所有段的复选框
✗ 目测文件里有多少个 - [ ]   # 同上
```

**判别式（任何「清单 / 队列 / 待办」文件的计数）：**
> 这个数字是**解析器给**的，还是我**自己数文本**数出来的？
> 后者一律不算 —— 同类事故这一晚犯了四次（见验收节：验别人的东西之前，先验自己的验证器）。

**这四种东西长得一模一样（都是 `- [ ]`），但只该有一种进待发段：**

```
客户 A · 出一页客户清单              → 真的给出的指令 ✓ 进 ⏳ 待发
客户 A · 16 条视频源全空，等 mp4     → 等合作方 ✗ 进 ⏸ 等外部
哀歌 · 19 vs 18 个意象需确认       → 等用户确认 ✗ 进 ⏸ 等外部
项目 B · 需要客户 B给 5-10 张成品照  → 等外部 ✗ 进 ⏸ 等外部
新媒体 · 6 篇后台数据没回填，要你抄 → 等用户 ✗ 进 ⏸ 等外部
```

**★ 「等外部」照旧用 `- [ ]` 是**对的**（它是用户的待办，要能勾），
关键是**别放在待发段里** —— 放进去，自动化就会把它们当派单。

**新建项目的固定格式：**

```markdown
## ⏳ 待发（给执行方的指令）
- [ ] 客户 A · 出一页客户清单

## ⏸ 等外部 / 阻塞（不是派单，不触发心跳）
- [ ] 客户 A · 16 条视频源，等合作方给 mp4
- [ ] 项目 B · 等客户 B给 5-10 张成品照
- [ ] 新媒体 · 6 篇后台数据要用户手抄
```

**★★ 因为 `queue.py` 本来就只解析 `^##\s*⏳?\s*待发` 这一段** ——
拆完心跳立刻准确，一个字的代码都不用改。**改前先确认解析器只认这一段，再动手。**

**★★★ 而且「等外部」那几条反而更醒目：它们是用户的待办，不是执行方的。**

**★★★★ 判据（任何「队列 / 待办清单」都要问一句）**：
**谁在等这件事？** 等执行方 / 等用户 / 等客户 / 等一个不会来的资源 ——
**四种混在一个列表里，任何自动化都会误报。**

### 实现这个机制时踩的 5 个 bug（全被沙盒抓出来）

```
① --init 那次把「已报过动了」提前设成 True → 之后第一次真检测静默
   → init 必须只建基线，不产生任何事件、不碰标记

② memory 基线 hash 没写回 state → 每轮都认为「又变了」→ 重复报「动了」
   → 每轮结束必须把新 hash / nlines 写回

③ 摘要抓成「2026-11-15」（日期行）→ 跳过纯日期 / 纯数字行

④ 测试数据把「5 小时前」写成未来时间 → 测不出卡住
   → 造超时数据用 now - timedelta(hours=5)，别手写时间串

⑤ ★★★ 「上次待发列表」基线写在打勾【之前】→ 下一轮把自己 tick 掉的条目
   当成「外部修改」，误报警
   → 基线必须在【本轮所有 tick 结束之后】再重读队列写入，不能提前记
```

**★★★★ ⑤ 值得单独记：它是「基线」和「变更」两个概念撞在一起。**
凡是有「记住上次状态 → 和这次比 → 报差异」的机制，都要问一句：
**「这一轮我自己也会改这个状态吗？」** 会 → 基线必须记「我自己改完之后」的样子。

**★★★★★ 顺带一个测试方法的坑：多场景沙盒【用例必须连贯】。**
我写 8 场景测试时，两次把上一场景的条目换掉（`write_q(["v12"])` 覆盖了 v11），
结果检测器正确报出「v11 从待发消失」—— **我一度以为是误报，其实是用例错了。**

```
✗ write_q(["v12"])                  → v11 消失 → 报警（对）→ 我当成 bug 去查
✓ write_q(["v11", "v12"])           → 保留上场景条目，只加新的
```
**判据：沙盒里出现「意外报警」时，先检查自己上一场景留下了什么，再怀疑代码。**
（这跟「验别人的东西之前先验自己的验证器」是同一个形状 —— 第四次栽在这上面。）

**★★★ 沙盒 8 项全过再上**（2026-11-15 端到端实测版本）：
队列空基线 / 空且无动静静默 / WB 动了一下只报「动了」不判断 / 完成则打勾+判断 /
队列空后又写仍静默 / 派两条静默 / **执行方抢打勾则报警且不跑 judge** / 派单 5 小时报卡住。

**★ 前 6 项验证「该响的响、该静的静」，最后 2 项验证「两个反向信号」——
一个不能误响（抢打勾要报警但不能白跑 judge），一个必须响（卡住）。
★★ 每跑一项都断言 judge 调用次数，不看输出猜 —— mock 掉 judge 记次数，是真便宜又真可靠的探针。**

**★★★★ 泛化：给「监测」加功能，比给「功能」加监测更容易出错** ——
因为它只在事件发生时才跑，事件不发生的时候你看不出它坏了。
**所以监测类改动必须用沙盒把「该响的」和「该静的」都跑一遍，缺一不可。**

### 0.3.1 ★★★★★ 最大的敌人不是 bug，是**执行方自己把队列打了勾**

**2026-11-15 实测，这是整套自动验收失效的唯一原因，而且我误判了两天才发现。**

```
现象：cron 每 15 分钟跑，输出全是 silent，一条判断都没有
我以为：队列是空的，所以静默 —— 正常
真相：队列被执行方自己打了勾，cron 根本看不到「⏳ 待发」
```

**怎么认出来的（这个判别式要背下来）：**

```
看队列里 ✅ 那条的【续行】是什么——

是我的指令原文（「为什么：…」「做完请：…」）  → 是 tick_item 打的，正常
是它自己的报告（「① 周口径：…」「✅ 客户 A那篇…」「⚠ 一处按判断处理：…」）→ ★ 它自己改的
```

**★★ 因为 `queue.py` 的 `tick_item` 打勾时会**保留原条目续行**，绝不会生成 ①②③ 这种报告措辞。**

**★★★ 连带教训：我昨天还跟用户说「wb_watch 第一次真跑通，自动打勾了」—— 那也是它干的。**
**也就是说自动打勾从来没工作过，我一直以为是它。** 只要自动化「看起来在工作」，
就不要下「它在工作」的结论 —— **去查那条记录是谁写的。**

**根因是我的指令缺陷，不是它的错：**

```
我从没跟它说过「不许动 _给WB.md」
而 _给WB.md 长得就像任务清单 —— 做完打勾是自然行为
它甚至不觉得自己越界（memory 里一个字都没提改过队列）
```

**★ 所以每份指令都必须带这三句（写进「不许做」那一节）：**

```
★ 你只写 <工作日志目录>/YYYY-MM-DD.md
★ 不许修改 _给WB.md（那是队列，打勾由 cron 负责）
★ 做完就停，等 cron 在 5 分钟内自动验收
```

**★★★★ 但「写进每份指令」是不够的 —— 要写进【队列文件自己的开头】。**

**这是 2026-11-15 的改进，两者差别很大：**

```
写在【指令】里 → 只在那一条指令生效；他下一轮不重读指令，就失效了
写在【队列头】→ 他一打开那个文件就看见，对每一次交付都生效
```

**实测做法（一次批量加到全部队列，改前备份）：**

```python
RULE = """> **★★ WB 注意（起算日）**
> 你只写 `<工作日志目录>/YYYY-MM-DD.md`。
> **不要修改这个文件** —— 包括打勾、包括把你的报告贴进来。
> 打勾和验收由 Hermes 的 cron 自动完成（每 5 分钟扫一次）。你做完就停，等结果。
"""
# 插在最后一个 > 引用行之后；已有「★★ WB 注意」的跳过（幂等）
```

**★ 泛化：约束一个 Agent 不要碰某个文件时，把禁令写在【那个文件里】，不是写在任务书里。**
**任务书是一次性的，文件是长期的 —— 人会忘，文件不会。**

**★★ 配套：把这两句 + 八节骨架沉成 `Outputs/drafts/_WB指令模板.md`，
下次出指令照抄 —— 否则「漏写边界」会以同样的方式重演。**

**★★★ 光靠约定不够 —— 再加一道检测，因为约定会被忘、会被更新掉：**

```
cron 在 state 里记住上次扫到的「待发」列表
下次发现某条从待发消失、但不是自己 tick 的
→ 报「⚠ 队列被外部修改了：xxx 从待发消失」，并补一次判断
```

**★★★★ 泛化判据（任何「Agent 执行 + 系统监听」的架构都要问）：**
> **除了监听器，还有谁会写这个状态文件？**
> 只要存在第二个写入方，「监听器看不见事件」就是迟早的事 ——
> 而且它的表现恰好是**静默**，看起来跟「一切正常」一模一样。

### 0.3.2 ★★★★★ 「做完请在 memory 里写 X」不是客套 —— 它是匹配器的燃料

**2026-11-15 端到端测试跑出来的：场景「WB 报完成」第一次【没打勾、没判断、静默】。**

```
指令：v9 测试任务：把按钮颜色改成红色
memory：已完成按钮改色，三个按钮都改了，自检通过。

→ 判据：完成信号 ✓（有「已完成」）
        中文短语重合 ✗（只对上「按钮」1–2 个，阈值是 ≥4）
→ match_done 返回 None → 静默
```

**★★ 我第一反应是「判据有 bug」，其实判据是对的。真正的问题是我造的 memory 不像真 WB。**

**★★★★★ 关键机理（写指令时必须知道）：**

```
匹配 = ① 有完成信号词  ② 英文标识符重合 ≥1  或  中文短语重合 ≥4
                                    ↑
                        这个数字靠【它的报告用词】撑起来
```

**★★ 所以每份指令里那句「做完请：在 memory 里写「…」」的真实作用是：**

```markdown
✗ 客套写法：「做完请在 memory 里简单记录一下」
   → 它写「已完成按钮改色」，跟「把按钮颜色改成红色」重合不足 → 漏打勾

✓ 有效写法：「做完请在 memory 里写「已完成 v9 测试任务：把按钮颜色改成红色，
   三个按钮都改成 #C4362F」」
   → 把【指令自己的关键词】塞进那句话里，重合度自然够
```

**★★★ 判据：那句话里的「…」，必须包含本批任务的名字 + 关键动作词 + 关键参数。**
不要写「记录完成情况」这种放之四海皆准的话 —— 它在匹配器眼里等于零信息。

**★★★★ 反过来也成立：漏打勾时，第一件事不是改阈值，是查【它到底写了什么措辞】。**
阈值 4 是从实测来的（真命中重合 10、无关完成重合 3），改小会把无关完成也放进来，
那比漏打勾更糟（§队列铁律：宁漏不可错）。

**★ 泛化：任何「用文本相似度把 A 的通知匹配到 B 的任务」的机制，
都需要在 A 那一侧【约定通知的措辞】。** 约定写在任务书里，比调阈值可靠得多。

### 0.3.3 ★★★★★ 「动手前先写一行」—— 补上心跳的语义缺口（2026-11-16 补）

**这是「扫描式感知」最实质的缺口。一次外部评审（2026-11-15）唯一命中我的批评就是它：**

> 「扫描只能告诉你『什么变了』，无法可靠地告诉你『这意味着什么状态』。
> 一个文件被修改了，可能意味着任务推进，也可能意味着返工或废弃；
> 一个文件长时间未变，可能是正常运行中，也可能是已经卡死。」

**★★ 实测的三种情况：**

| 现象 | 没有声明时我判断不了 | 有「我要做 X」之后 |
|---|---|---|
| 文件变了 | 在推进？在返工？在乱改？ | 在推进，正做 X |
| 文件半天没变 | 在想？在跑长任务？死了？ | 能对照声明估时间 |
| memory 说有完成，但文件没变 | 它在撒谎？ | 立刻可疑 |

**做法：每份指令加一句**

```
★ 开始改任何文件之前，先在 memory 里写一行：
    ## HH:MM 我要做：<一句话说清这次要动什么>
  然后再动手。
```

**★★★ 为什么不用「协议化替代扫描」（外部评审的另一个建议）：**

```
评审建议 FCoP：目录定义状态 + frontmatter 里记 transitions，用 mv 迁移目录

不采用，三个原因：
① 执行方写得了 md，但 mv 目录在 Windows 上要处理文件占用
   （2026-11-16 实测：一个 .git 对象被锁，move 复制成功但删除失败）
② 我们已经有状态声明 —— 队列四段（待发/已完成/等外部/口径备忘）
   + 内容 md 的 status frontmatter。缺的不是「状态写在哪」，
   是「动工那一刻它在做什么」
③ 一行字的成本，比一次目录迁移低两个数量级
```

**★★★★ 判据：如果某次「▶ 动了」之后，你说不出一句话「它在做什么」，就说明这句声明没写。**

**★ 这条改动把心跳从「有心跳但不知道在跳什么」升级成「知道它在做哪一步」——
成本只有一行字，而它补的是这套系统最贵的那类信息：语义。**

#### ✅ 2026-11-16 首次实测：生效了

```
02:51  入队 v7
02:54  执行方自己写下（一字未改）：
       「我要做：把「全部素材」改成素材池（素材为父、角度为子、账号/类型筛选），
         并在读取层统一状态词（待写→已定选题）＋排期行加来源标签。」
08:00  心跳输出：▶ WB 动了 —— 直接把上面那句话贴出来
```

**★★ 对比之前：`▶ WB 动了（队列还剩 1 条）`，只有「有动静」，没有「动静是什么」。**

**★★★ 判据坐实：它确实肯写，一句指令就够，不需要任何 SDK 或协议。**

### 0.3.4 ★★★★★ 队列只能有一个写入口（2026-11-16 实盘撞出来的）

**这个系统里有两个 cron，都碰同一个队列文件：**

```
wb_watch.py　　　*/5 8-22　no_agent:true　→ 监听 + 打勾 + 触发判断
project_watch.py　每日 06:20　no_agent:false → LLM 驱动，写项目进度汇报
```

**★★ 06:20 那个是 LLM 驱动的，它读到「v7 做完了但队列还没打勾」，于是做了两件事：**

```
✅ 对的那一半：
   「内容看板『⏳ 待发』里那条 v7，WB 已在 11-16 03:04 跑完 → 已移到『✅ 已完成』。
     你如果按昨天的队列照抄，等于让它重做一遍。」

⚠ 越权的那一半：
   「…v7.1 小修已入队，等它改完再看」
   —— 它自己拟了三条小修，自己写进了「⏳ 待发」。
```

**★★★ 连带后果（实测）：**

```
06:21  队列被改（打勾 v7 + 新增 v7.1），mtime 06:21:40
08:00  wb_watch 第一次跑 → 报「⚠ 队列被外部改了：v7 从待发消失」
       → 这一轮不触发验收判断
       → v7 的「自动判断」被整轮跳过
```

**★★★★ 三条判断：**

| 行为 | 该不该 | 理由 |
|---|---|---|
| 打勾 | ✅ 该 | 不打勾，用户早上会照旧队列让执行方重做一遍 —— 真浪费 |
| 派下一批 | ❌ 不该 | 「要不要继续、下一步做什么」是人的决定。写进「等你看」的建议里，不要直接入队 |
| 改队列文件 | ❌ 不该 | 触发 `wb_watch` 的外部变更检测，白吞一轮自动验收 |

**★★★★★ 修法（三选一，推荐 C）：**

```
A. 让 06:20 完全不碰队列
   → 但「防止用户白干」的保护也没了

B. 只打勾、不派单
   → 折中，但改队列仍会触发外部变更报警

C. ★ 唯一写入口：wb_watch 是唯一能改队列的进程
   06:20 照常读 memory、写进度汇报，
   「建议派 X」只写在汇报末尾，等用户看完再入队
```

**★★ 注意这和 §0.3.1（执行方自己打勾）是同一类病的两个变种：**
都是「有第二个写者」，只是一个是人形 Agent、一个是自己的另一个 cron。
**§0.3.1 的检测抓到了 §0.3.4 的变更 —— 说明检测是对的，只是它猜错了写者身份**（报「是 WB 打的」，实际是 06:20 cron）。

**★ 通用原则（不只这个系统）：**

> **任何「状态文件 + 多个自动进程」的组合，先问一句：谁能写？**
> **一旦有两个写者，变更检测 / 审计 / 幂等这三样都得同时伺候两个，复杂度翻倍。**

**★★ 判据：如果系统里出现「A 改了 B 也会报错」的现象，那不是 bug，是写入口没收口。**

#### ★ 附带发现：夜间派单是监控盲区

```
cron 时间窗 */5 8-22
用户 02:51 派单 → 08:00 才开始盯，中间 5 小时完全静默
08:00 第一次跑，把「动过」和「已完成」全当成刚刚发生的，一次报三条互相矛盾的警报
```

**★ 排 cron 时间窗时要问「他会不会在窗外派单」。会 → 要么放宽窗口，要么在派单那一刻手动跑一次建基线（`python wb_watch.py`，静默即正常），并**在跟他说话时明说窗口**：「夜里派单它是事后补报的」。**

## 0.4 ★★★★★ 派单之后的第二层：自动验收判断（不等用户开口）

**2026-11-15 他的原话：「我想达到你能自动监测到 wb 完成的情况并向我反馈，给出下一步任务的建议，那么我就不需要监管 wb 的情况，进一步强化主 agent + 工具型 agent 的模式。」**

§0.3 的三句话心跳只解决「它动了 / 完成了 / 卡住了」——
**但「完成」之后没人判断「做得对不对、下一步干什么」，用户还是得自己看。这一节补的是后半段。**

### ★★ 2026-11-16 变更：检测频率 15 分钟 → 5 分钟

**2026-11-16 的要求：「按你的建议，提高检测的频率至 5 分钟一次」。**

```
检测（有没有变化）　　token = 0，毫秒级　　→ 该提频，提到 5 分钟几乎免费
判断（变化意味着什么）15–20k token，2 分钟　→ 不该提频，只在真有事时跑一次
```

**★ 这不是「更快等于更好」，是把两件事分开：**

| | 改之前 | 改之后 |
|---|---|---|
| 扫描频率 | 56 次/天 | **168 次/天** |
| 扫描成本 | 0 | **0**（不变） |
| 判断次数 | 3–5 次/天 | **3–5 次/天**（不变） |
| 判断成本 | ¥0.4/天 | **¥0.4/天**（不变） |
| 发现延迟 | 最长 15 分钟 | **最长 5 分钟** |

**★★ 安全性：judge 最长 190 秒（3.2 分钟）< 5 分钟窗口，且有锁（10 分钟僵死自动清），不会重叠。**

**★★★ 副作用（已知，可接受）：静默也会写一个空输出文件，一天 168 个。**
**　　要治就加清理（保留最近 N 天），不急。**

**★★★★ 反例保留在下面：不要「每 15 分钟起一个 LLM agent」—— 那是 32 次/天空跑，成本涨 20 倍、收益接近 0。**

### 架构：快路零成本 + 事件触发才烧 token

```
cron 每 5 分钟（no_agent=true，token=0）
  └─ wb_watch.py
       · 无「⏳ 待发」→ 完全静默，耗时 0.5s
       · 有完成 → 打勾（现有）+ subprocess 调 judge.py
            └─ hermes -z "<判断prompt>" -t file,terminal
                 · 实测 164s，它会自己跑脚本复核
                 · 只在有事件时才烧 LLM
```

**★ 为什么不是「每 15 分钟起一个 agent cron」**：空跑也要 3–5k token，
一天 32 次里 30 次白烧。**按需触发才对。**

**★★ 不需要为每个项目建一个 cron** —— 全局扫一遍，只有「有待发的队列」才会触发，
逻辑与「针对某个文件夹」等价，但少维护 N 个任务。

### ★★★★★ 核心设计：只给三段事实，不给结论

prompt 里写死的硬约束：

```
【看起来完成了什么】  ← 用自己的话说，并指出 memory 和文件变化对不上的地方
【你该自己核这几点】  ← 2–4 条具体可执行（查哪个文件、看哪个字段、跑哪个命令）
【下一步建议】        ← 一句话

★ 不要给「通过 / 不通过」的结论 —— 结论归用户
```

**★★★ 理由（从自己的错误里学到的）**：
一晚人工核交付误报了 4 次（见 §0.2），**全是我的验证工具错**。
自动化以后没人复核，误报会直接推到用户面前。
**所以让 judge 只干「列清楚该核什么」这件它擅长的事，判断权留在人手上。**

**★ 反直觉但重要：judge 的价值不在「替你下结论」，在「替你跑一遍你懒得跑的命令」。**
实测那次它自己做了：跑 `build_board.py` 看退出码 / 重跑比对 md5 验幂等 /
复现日志里的 4 个数字 / `node --check` 查 JS 语法 / 数外链 ——
**然后指出 3 个我没发现的问题（两个"本周"口径不一致、复制全文会盖内容、
「定这个选题」的 plan_date 写死 today+3 会覆盖已有状态）。**

### ★★★★★ 但第一版 prompt 让它「猜」了一整轮：**只给相对路径 = 它读不到文件**

```
第一版：传「· build_board.py（88,156 bytes，改于 13:02）」
它的回答：「我在本机找不到项目的实际目录，全盘搜索 build_board.py 也没有结果
          文件内容我一个字都没有读过，以下只根据时间戳反推……」
```

**★★ 它只能靠文件大小和时间戳编故事 —— 虽然它诚实说了「没读到」，但这一轮判断是废的。**

**修法两件事，缺一不可：**

```
① 每个文件都给【绝对路径】（os.path.abspath），并单列一行「## 项目绝对路径」
② prompt 里明确写「你有 file 和 terminal 工具，请真的去读、真的跑验证命令」，
   并给出三个具体的必做动作（读声称改过的文件 / 跑生成脚本 / 读产物关键段落）
```

**★★★ 改完效果：从 190s 降到 104s（不再盲搜盘），而且它开始真跑脚本、真用 Node DOM 桩执行页面 JS。**
**「耗时变短但质量变高」是个好信号 —— 说明之前的时间都花在瞎找上了。**

**★★★★ 泛化：给子 agent 的子进程传上下文，「路径」和「内容」是两回事。**
给了路径不等于它能找到（cwd 不同、盘符不同、它不知道自己在哪）；
**要给绝对路径，还要明说「你可以去读」** —— 否则它宁可编也不动。


### 四层防护（缺一层就出事）

```
① 锁文件 —— 判断要跑 2–3 分钟，期间下次扫到不重叠、只报事实
② 10 分钟僵死自动清锁
③ 判断失败/超时 → 降级只报「完成了什么」，绝不阻塞主流程
④ 同轮既有「动了」又有「完成」→ 省掉「动了」那句（噪音）
```

**★ 降级文案要给用户看懂**：「这轮判断没跑起来 —— 可能上一轮还在跑。事实已报，判断下次补。」
不要静默吞掉，否则他会以为判断功能坏了。
