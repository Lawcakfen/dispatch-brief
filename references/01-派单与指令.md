# 五条铁律 · 指令骨架 · 三个高频产物类型

> 从 `SKILL.md` 拆出（2026-11-15）。这是写指令时最常翻的一页。
>
> **★ 先记住速查版，要例子再往下读。**

## 速查（30 秒）

| # | 铁律 | 反例 → 正例 |
|---|---|---|
| ① | **内容来源唯一且写死路径** | ✗「把之前的资料整理一下」→ ✓ 唯一路径 + 「文件里没有的留空」 |
| ② | **「不许编」写成可执行的核对细则** | ✗「不要编造」→ ✓ 列清哪些字段不许碰、哪些标记要跳过 |

| ⑤ | **验收清单 + 单一文件交付 + 回报三件事** | ✗ 多文件多路径 → ✓ 砍到一个文件、一个路径 |

## 五条铁律

### ① 内容来源必须唯一且写死路径

```
✗ 「把之前的资料整理一下」        → WB 会自己找、自己理解、自己编
✓ 「唯一内容来源：<库根>\...\<诗名>.md（约 623 行）」+ 「该文件里没有的，留空，不要填」
```

**★★ WB 的头号毛病是「编得很顺、但没真发生」。** 不给唯一来源，它就会用「合理」补「真实」。

#### ★★★★ 延伸：内容「给路径」比「嵌进指令」好，但要附一张地图（2026-11-18 实战）

**几千字的素材不要塞进指令里** —— 整理成一个 md，指令只写路径。好处：不丢格式、不撑爆指令、素材能单独复核。

**★ 但它有唯一的失败形态：只读开头就动手。**

```
指令：读 <路径>，照里面整份执行
它做到的：读了第一节（硬规矩），漏了第三节（结构）和第六节（验收）
结果：做出来的东西"看起来像"，但缺内容
```

**✓ 修法：把该文件的章节清单写进指令。**

```
读 <绝对路径>

★ 整份读完再动手，不要只读开头。
里面第一节是三条硬规矩，第二节是内容来源，
第三节是八块结构，第六节是 14 条验收 —— 少读一节就会做错。
```

**★★ 判据：凡是「读某个文件然后照它做」的指令，都要附这张地图。** 它不是防偷懒，是给它方向感 —— 它不知道后面还有什么，就会以为读到的就是全部。

**★★★ 配套（同一份指令里用的）：把「不许编」写成字段级表格** —— 哪个字段不许加人、不许改数字、不许补空白，比一句「不许编造」有效十倍：

```
| 不许做 | 原因 |
|---|---|
| 不许加文件里没有的人 | 六个人是实际人数，多一个少一个都是假的 |
| 不许给"说得最少那位"编身份 | 素材里写了未知，就写"一位参与者" |
| 不许改任何数字 | 47%、91 分钟 —— 全部照抄 |
```

### ② 「不许编」要写成可执行的核对细则，不是一句口号

```
只搬运该文件里已有的内容，一个字都不许新增解读、不许润色得更文学
该文件里标了「⚠️/待确认/存疑」的内容，一律不搬
不许凭记忆补诗句/数据 —— 文件里没有就只留标题
```

**★ 抽象禁令无效，要列「哪些字段不许碰」「哪些标记要跳过」。**

### ③ 形状要「可判定」，不要给自由

```
✗ 「20 分钟或者 2 小时都可以」 → 他听到的是「随便准备点」
✓ 「十来分钟就够 —— 说清三件事：它是什么、你在什么场景用它、它哪里还不够」
```

**★ 给自由不是给形状。** 你自己就是「没有形状的东西做不动」的人，写给执行方的 Agent 同理。

### ④ 视觉/审美要给「禁止清单」，不只给「要什么」

**★★★★ 这一条最容易被漏，也最容易毁掉一个交付物。**

写「干净、可读、有秩序感」没用 —— WB 会理解成「做得高级一点」，然后交出深色背景 + 大字居中 + 缓慢淡入。

必须逐条禁止：

```
✗ 深色背景 / 黑底金字
✗ 缓慢淡入、视差、粒子、飘动
✗ 手写体、书法字体、宣纸纹理
✗ 大字号居中占满整屏
✗ 渐变背景、玻璃拟态、发光文字
✗ 动画超过 0.3 秒
```

**★ 并且把「为什么禁」写进指令** —— 例：收件人是「反对把诗神秘化」的老师，所以这份页面的审美方向必须是「能逐字读」，不是「让人不敢读」。

**★★ 有了理由，WB 在边界情况才判得对；只给清单，它会在清单外发明。**

### ⑤ 验收清单 + 交付单一化

```
□ 双击 index.html 能打开，断网也完整
□ 文件里搜不到 http://（除注释）
□ 手机竖屏 375px 能读，无横向滚动
□ 打印预览：各节另起一页，无按钮
□ 没有任何一句是你自己加的解释
```

**★ 一次只交一个文件、一个路径。** 多文件交付他没法「粘一下就完事」。

**★ 结尾要求 WB 回报三件事**（本次用的）：① 各节数量 ② 收了几个条目 ③ **哪些地方你留了「待补」** —— 第 ③ 项是「不许编」的可验证出口。

## 指令骨架（八节，照填）

```
一、产物        —— 一个文件 + 绝对路径 + 技术规格（单文件/无外链/响应式/打印）
二、内容来源    —— ★ 唯一来源路径 + 「不许编」的执行细则
三、结构        —— 逐屏/逐节写清，标出哪一屏最重要
四、视觉要求    —— 要做 / ★ 不要做（逐条禁止 + 理由）
五、交互        —— 只列允许的，并明写「以下一律不做」
六、验收清单    —— WB 自己逐条过
七、出错时的处理 —— 缺内容怎么办（留空 + 灰字「待整理」）、不确定怎么办（宁可多不可少）
八、交付        —— 回报哪三件事
```

**★★ 第七节是绝大多数指令漏掉的** —— 不写「出错时怎么办」，WB 就会自己发挥，而它发挥的方向永远是「补全」。

## 三个高频产物类型

### A. 单文件 HTML「礼物页 / 纪念页」

场景：送给老师、送给客户、给参与者留档。
**★ 关键判断：这是礼物不是作品集 —— 第一屏应该是一封短信，不是标题。**

模板：`templates/gift-webpage-brief.md`（本次实战 7.9 KB 指令的骨架，可直接改）

### B. 视觉产物（海报 / 长图 / 预览页）

- 给**参考图 + 设计规范**，不要用语言描述风格
- **先出一张样板 → 确认 → 再批量**（这条省下的返工最多）
- 尺寸/DPI/命名规则写死（例：`720×1080`、`MMDD-系列名.png`）

### C. ★★★★★ 改造一个已有的代码文件（不是从零生成）
**→ 详见 `references/07-评审与改造.md`**　先读后改、锚点选择、删嵌套块、改完必验语法、截图必看。

## ★★★★★ 七轮实测出来的四条（内容看板 v1–v7，2026-11-14 → 11-16）

**这不是理论，是七轮派单里量出来的。每一轮都有具体的数字。**

### ① 指令长 ≠ 做得慢。模糊才慢

```
v7：424 行 / 14.9KB　→　WB 02:54 开始，03:05 收工，11 分钟
改的是：素材池重构（数据层 + HTML + CSS + JS 三层）+ 状态词统一
```

**★ 反直觉：直觉是「给这么多要求，它得做很久」。**

**★★ 实际是「不用猜，所以做得快」—— 它不需要来回问，也不需要自己发明做法。**

**★★★ 对照：早期 v1/v2 指令 200 行左右，反而来回改了 4 次。**
**差别不在长度，在「有没有把判断留白」。**

**★★★★ 所以：宁可写长，不要留白。留白的地方它一定会填，而且填的是它的假设，不是你的意思。**

### ② 可勾选的验收清单，它会逐条报 —— 连「部分通过」都报

**v7 的清单 22 条，它的回报长这样：**

```
| 条 | 结果 |
|---|---|
| 1/2/3/5 | ✅ 标题与 114·150 与脚本打印一致；DOM 桩 114 卡 / 148 角度 |
| 4 | ✅ 真机 Edge headless + CDP：点第一张卡 → open: false→true，.po-body 高度 >0 |
| 12 | ⚠ 部分：全文连续 ** = 0（真机 innerText 实测）；半角 | = 2 处，见③ |
| 21 | ✅ 真机 Edge：Runtime.exceptionThrown / Log error / console.error 全为 [] |
```

**★★ 关键：它没有把「⚠ 部分」糊成「全部通过」。**

**★★★ 为什么能这样：因为每条都写成「能动手验的动作」，不是「请检查页面」。**

```
✗ 请检查筛选功能是否正常
✓ 点「我是示例·小红书」+「讲述型」→ 页面显示「这个组合暂时没有素材」，0 张卡，★ 不许退回全部
```

**★★★★ 差别的本质：前者要它「评价」，后者只要它「执行并观测」。评价可以糊，观测不能糊。**

### ③ ★★★★★ 但它不报你没列的东西 —— 这是自动化验收的根本局限

**v7 的 22 条全绿。但我扫一眼截图就发现：素材卡标题太长，标题和来源糊成一行。**

**★★ 那条我没写进清单，它就没报。不是它偷懒 —— 它按清单逐条验完了，清单之外它没理由去看。**

**★★★ 结论：**

> **验收清单不能替代人看一遍。**
> **它的价值是「把该核的事变成可核的」，不是「替你核完」。**

**★★★★ 所以流程必须是：它报清单 → 人扫一眼产物 → 人补上清单的盲区 → 下一轮把盲区写进清单。**

**★★★★★ 这个循环转三轮，清单才接近完整。第一轮的清单一定不全，别指望。**

### ④ 「超过 N 就停，不许凑」—— 防呆条款要写成「数量阈值 + 禁止动作」

**v7 里我写了：**

```
如果归位失败超过 10 个，停下来，把失败清单写进 memory，不要硬塞
★ 不要改匹配规则去凑，那会让错的也匹配上
```

**它的实际做法：**

```
归位成功 148 个，失败 2 个（#139 #140）
母素材写「／」、素材标题用「|」，全角半角不同
按指令「不改匹配规则去凑 / 不硬塞」，这 2 个没挂进任何卡片
页面加了一行灰字说明，标题仍写真实的 150
```

**★★ 它没有偷偷改规则把 2 个塞进去 —— 这正是这条防呆的价值。**

**★★★ 写法对照：**

```
✗ 请谨慎处理异常情况            ← 它不知道「谨慎」是什么
✗ 尽量保证数据准确              ← 无法判定
✓ 失败超过 10 个就停，写清单，不许改规则去凑   ← 有阈值、有动作、有禁令
```

**★★★★ 通用句式：「超过 <可数阈值> 就 <停下做什么>，不许 <某个具体动作>」。**

### ⑤ 「冲突时怎么办」让执行方自己解 —— 矛盾一定有，别指望写出无矛盾的指令

**v7 的三句话②要求「按带理由、更具体的那条执行，并在 memory 说明」。**

**它主动列了三条取舍：**

```
① A4 示例卡片头写「6 个角度」，A6③ 要求「符合的 / 总数」
   → 按更具体、带理由的 A6③，统一显示 X / Y 个角度

② A4 示例按钮数字口径混用（账号 22 = 主号角度数、类型 93 = 类型角度数、all 分别 114/150）
   → 按示例实现，并让筛选按【主号】判定（不查「可兼」），这样按钮数字 = 筛出的角度数

③ 验收清单「临时把 11-18 改 11-19 再改回」与「不许改 Outputs\drafts\」冲突
   → 按更严的边界，只在临时目录副本上改 PLAN_PATH，Vault 原文没动
```

**★★ 三条都是真冲突，三条都选对了。**

**★★★ 这说明：与其追求「写出一份没有矛盾的指令」（做不到），不如给一条「冲突时怎么办」的规则。**

**★★★★ 而且要求它「把取舍列出来」—— 这样你能复核它选得对不对。**

**★★★★★ 反例：如果你不写这条，它遇到矛盾会二选一，而且不说 —— 你事后才发现方向错了。**

---

## ★ 一句话总括

> **指令的质量不在「写得多全」，在「它不用猜、也不会偷偷凑、遇到矛盾会说」。**
>
> **清单管住「它不用猜」，防呆管住「它不偷偷凑」，冲突规则管住「它会说」。**

# WB 指令模板（每次出指令照这个写）

> 2026-11-15 建。**模板本身不是指令，别整篇发给 WB。**
> 用途：我（Hermes）出下一批指令时照这个骨架写，保证不遗漏。
> 来源：2026-11-14/15 两天从 v1 到 v5.1 共 6 轮迭代，踩过 4 次坑。

---

## ★★★★ 0. 交付形态：他说「给我指令」时，只给那一段

**触发（2026-11-19）**：改一句文案这种事，我给了分节标题 + 三处错误对照表 + 验收清单 + 「一个提醒」。
他回四个字：**「所以指令是什么?」**

**★★★★ 信号很明确：他要的是【能立刻复制的东西】，不是【理解这件事】。**

```
✓ 一个代码块 —— 第一行到最后一行都能直接粘进 WB 窗口
✗ 前面解释「为什么这么改」
✗ 分节标题、对照表格、验收清单
✗ 后面「★ 一句话」总结
```

**★★ 那些解释不是废话 —— 但它们属于上一个回合（商量的时候）。**
一旦他说「给我指令」，讨论就结束了，剩下的只有交付。

**★★★ 自检一句话：如果他看完还要再问「所以指令是什么」，就是我给多了。**

**★ 反过来也成立**：他还在问「这样行不行」「你觉得呢」→ 那时他要判断，不是代码块。
**判据：「所以……是什么?」这种句式出现 = 我绕了，他只要结果。**

**★ 唯一该保留在指令块里的解释，是「不这么改会怎样」那一句**
（例：「必须改 py 不能改 html —— 直接改 html 下次生成会静默变回旧的」）。
**它属于指令本身，因为它改变了他/执行方的动作。**

---

## ★★★ 每一份指令必须包含的三句话

### ① 边界：WB 只写 memory

```
★★ WB 注意
你只写 <工作日志目录>/YYYY-MM-DD.md。
**不要修改 _给WB.md** —— 包括打勾、包括把你的完成报告贴进去。
打勾和验收由 Hermes 的 cron 自动完成（每 5 分钟扫一次）。
你做完就停，等结果。
```

**★ 为什么必须写：**

```
2026-11-15 实测：WB 把 _给WB.md 的条目自己打勾、还把报告贴进去
→ cron 只看「⏳ 待发」段，条目被移走 = 永远不触发验收判断
→ 连跑 6 次全静默，而它其实做完了两次
→ 我还一度以为是「自动打勾跑通了」，其实是它抢在我前面
```

### ② 冲突时怎么办

```
★ 指令内部如有冲突（比如「只改文案」和「日期按实际算」），
  按**带理由、更具体**的那条执行，并在 memory 里写一行说明你选了哪个、为什么。
```

**★ 为什么必须写：** WB 两次遇到冲突，两次都主动报出来并做了合理选择。写上这句，它就不会卡住。

### ③ ★★★★★ 动手前先写一行 memory

```
★ 开始改任何文件之前，先在 memory 里写一行：
    ## HH:MM 我要做：<一句话说清这次要动什么>
  然后再动手。

不要等做完才写 —— 做完才写，我只能看到「文件变了」，看不出你在做什么。
```

**★★★ 为什么必须写（这条补的是监控系统最大的语义缺口）：**

```
cron 只能感知「文件变了」，感知不到「这意味着什么」：

· 文件变了 + memory 有「我要做 X」　→ 正常推进，我知道它在做哪一步
· 文件变了 + memory 一个字没写　　　→ 可能是返工、可能是在乱改，我分不出
· 文件半天没变 + 没有任何声明　　　　→ 分不清它是在想、在跑长任务、还是死了
```

**★★ 加这一行等于给它一个「现在进行时」。成本：一行字。**

**★ 这也解释了为什么「心跳」本身不够：心跳只能说明「有动静」，不能说明「动静是什么」。**

## 八节骨架

```
一、动手前　　　备份哪个文件（build_board.py → build_board.vN.bak.py）
二、改动范围　　做什么 + ✗ 不做什么（逐条列，防扩展）
三、具体改法　　正则怎么匹配、字段怎么取、代码长什么样
四、视觉要求　　✅ 允许 + ✗ 禁止清单，且每条禁止都要给理由
五、交互　　　　只做这些 + 不做哪些
六、验收清单　　可勾选的方框，每条都能动手验
七、出错时　　　每种异常怎么处理（★ 优先「显示空状态」不要「显示假数据」）
八、交付回报　　三件事，其中至少一件要求「必须实测，不要写应该正常」
```

## 五种好用的句式（实测有效）

```
① 「必须正好 150 行，对不上就退出码 1，不许猜」
   —— 给它一个可验证的数字，它就会去验

② 「宁可显示「待补」，不要显示一个假数字。进度条撒谎，比空着更糟」
   —— 明确告诉它降级怎么做

③ 「交集为空要显示「没有候选」，不许退回全部」
   —— 防止它用「兜底」把筛选做成假的

④ 「★ 只清首尾，中间不动」这类边界要写死
   —— 我写过一次「中间的 ** 保留」，结果纯文本渲染里全是脏字

⑤ 「这一项必须实测，不要写应该正常」
   —— 它真的会去跑，还会把输出贴回来
```

## ★ 三件我一直犯的错（写进模板防再犯）

### ① 先验自己的验证器

```
2026-11-14 一天里，我核 WB 交付误报了三次：
· 说「对照表只有 131 行」→ 是我的脚本被换行撑断
· 说「账号绑错 4 个」→ 我的正则跨了对象边界
· 说「标题框是空的」→ 我用 textContent 读 <input>
三次全是我的工具错，不是它的代码错。
```

**★ 结论：验别人的东西之前，先跑一遍自己的验证脚本看它是不是可信。**

### ② 不要用「往往/通常」的直觉写判据

**★★ 我写过 `has_self` 匹配「自己」，结果「他自己写的那一版」被当成第一人称。**

**★★★ 判据要能举出反例后还能站住才算数。**

### ③ 数据结构写进约定，别写进代码

**★★★★ `角度-账号对照.md`、`角度-类型对照.md`、`内容/*.md` 的 frontmatter —— 都是「人能改的约定」。**

**★★★★★ 一旦写死在代码里，你想改就得找我，那是失败的设计。**

# 交接指令：我自己做完一版，交给执行方接着做

> 2026-11-21 空本子 v1 → v1.1 的完整实践。
> **与本 skill 其他部分的前提不同**：那些是「我干不了的活交给它」（改 1.3MB HTML、出视觉产物）；
> 这一份是「**我能干、已经干了一版，然后主动交出去**」——约束完全不同。

---

## 0. 为什么要把「我能干的」交出去

```
自己做的部分：架构、视觉、核心逻辑 —— 这些要一次做对，来回沟通成本高于自己做
交出去的部分：一版做完之后「用起来硌手」的那些小修 —— 位置清楚、验收清楚、量也不小
```

**★ 判据：一件事如果你能给出「三条可判定的验收条件」，它就可以交出去。**
给不出 = 需求还没定清，交出去会来回。

**★★ 而且交接本身有额外收益：指令写清的过程，等于把这一版的隐性假设摊开了。**

---

## 1. ★★★★★ 三条新边界（「别人在用」带来的，之前没有）

这次交接的东西和前几次有个根本区别：**它已经被给别人用了**（AI 共学小组）。
于是多了三条「他做不了的活」里不会有的边界：

### ① 不改数据结构 / 不改存储 key

```
✓ S 的数据结构只能【加字段】，不能改名、不能删字段
✓ localStorage 的 key（如 'kongbenzi.v1'）一个字符都不改
```

**★★★★ 理由（指令里必须原样写出来，否则它不当回事）：**
> **一改名，别人本子里已有的数据就全丢了。这是给外人用的工具，数据丢了没法救。**

**★ 这一条比任何代码规范都硬** —— 因为它不是「会不好看」，是「会毁掉别人的东西」。

### ② 不引依赖、不建构建步骤

```
✗ 不新建文件、不引 npm、不引第三方库、不加 build
✓ 保持单文件、双击即用
```

**★★ 理由：单文件双击即用是这个工具的全部优势。一旦要 build，共学小组一半人就用不了了。**
**判据：任何「别人已经在用」的产物，加依赖不是技术选择，是用户流失。**

### ③ 视觉风格不改

```
✓ 三栏 / 黑白 / 细线 —— 已经是确认过的样子
✗ 不顺手「优化一下视觉」
```

**★ 这条要单独写，否则它会把你定的设计当成「待改进项」。**

---

## 2. 七节结构（照这个写，实测可用）

```
一、硬规矩（三句话）          只写 memory / 冲突时怎么办 / 动手前先写一行 memory
二、边界（比任务本身重要）    改哪个文件 / 不改什么 / 改完必须跑什么自检
三、第 N 件：<名字>           每件：现在什么状态 → 要做什么 → 验收 N 条
四、验收方式（全做完一起跑）  命令 + 手点清单 + 「有红的先修到全绿再交」
五、交付回报（写进 memory）   交付 / 改了什么 / 踩坑 / 验收 / 不确定 / 停
六、如果你觉得指令本身有问题   ★ 这条最值钱，见下
七、这一批不做（别顺手做）    列 5 项 + 理由 + 什么时候做
```

---

## 3. ★★★★★ 第六节：「如果你觉得指令有问题，不要硬做」

**这是这次新加的，也是七节里最值钱的一节。**

```markdown
## 六、如果你发现指令本身有问题

**★★ 这条最重要：如果你觉得某一件事写错了、或者做不了，不要硬做，也不要自己改需求。**

**在 memory 里写：**
```
## HH:MM 指令疑点：<哪一件> —— <为什么有问题>
建议：<你认为应该怎么做>
```
**然后停，等泽哥或 Hermes 回话。**
```

**★★★ 为什么必须有这一节：**

```
没有这一节 → 它会把「做不了」翻译成「用别的办法做到」，而那个办法往往是你不想要的
有这一节   → 它停下来报告，你补一句就齐了
```

**★ 而且它和「冲突时按带理由更具体的那条执行」是**互补**的，不是重复：**
- 冲突（两条要求打架）→ 它自己按理由选，事后说明
- **疑点（这条要求本身可能是错的）→ 停下来问，不许自己决定**

**★★ 判据：把「能自己判断的」和「不许自己判断的」分开写。
只写「你可以自己判断」，它会把需求也一起改了。**

---

## 4. 第七节：「这一批不做」为什么不能省

**指令里给了三件活，它做完三件之后会「顺手」做第四件** —— 因为你的任务描述里提过那个概念。

```
✗ 不做「已发数据趋势图」
✗ 不做「素材池搜索」
✗ 不做手机端重排
✗ 不加任何新板块
✗ 不改视觉风格
```

**★ 每一条都要带一句「什么时候做」**（「在 README 的 v2 候选里，等这一批验收完再说」），
否则它会认为你在否定那个需求，而不是延后。

---

## 5. 每件的验收条件：要写成「能照着点的动作」

**✓ 实测好用的写法（第 1 件：删周历条目）：**

```
① 排一条 → 删掉 → 格子回到「+」空状态
② 排一条 → 存进待发 → 删周历那条 → 弹出「已存进待发，一起删吗」→ 选一起删 → 待发里也没了
③ 删完刷新页面，被删的没回来（说明真写进 localStorage 了）
```

**✗ 坏写法：**
```
· 删除功能正常工作
· 边界情况处理正确
```

**★★★★ 判据：验收条件必须能回答「谁、做什么动作、看到什么」。**
写不出动作 = 这件事还没想清，不要交出去。

**★ 第 ③ 条专门验「真的落盘了」—— 凡是有持久化的功能，验收里必须有一条「刷新后还在」。**
这条最容易漏，也最容易在真用的时候翻车。

## 6. 每件的「要做什么」怎么描述数据/格式

**当改动涉及解析已有数据时，把「格式陷阱」直接写进指令** —— 因为它会踩你踩过的坑。

**实测例子（第 2 件：写作区实时字数）：**

```markdown
**上限怎么取：** 从 PRESETS[S.preset].words 里解析。那个字符串长这样
'300–600' 或 '3000–6000（用户指定时听用户的）'，也有 '200–400（信息为主，不写散文）'。

**★ 解析要点：**
· 用的是 en dash「–」不是连字符「-」（这是我自己踩过的坑）
· 建议正则：/(\d+)\s*[–\-]\s*(\d+)/
· 解析不出来就不要显示上限判断，只显示字数 —— 别猜
```

**★★ 三个要点各治一件事：**
```
① 「我踩过的坑」直接说 —— 省它一次返工，也让它知道这不是随便写的
② 给建议正则 —— 不给的话它会自己发明一个更脆的
③ 「解析不出来就别猜」 —— 兜底行为也要指定，否则它会在失败时编一个
```

## 7. 状态变量不许加新的

**第 3 件（周历翻月）里的一句：**

```
★ 要求：weekOffset 还是唯一的状态变量，不要新加 month 之类的状态。
　 翻月只是把 offset 换算成对应的周数。
```

**★★★★ 理由：交接时最容易被「顺手重构」的就是状态管理。**
它看到「要翻月」会自然地加一个 `currentMonth` —— 然后 `weekOffset` 和 `currentMonth` 就开始漂移。

**★ 判据：凡是有既存状态变量的模块，指令里必须点名「不许加新的，只能换算」。
否则你会在验收时发现「翻月对了，但『本周』按钮失效了」。**

## 8. 指令里明写「自检命令」，把它变成硬门槛

**这次有个天然优势：v1 自己带了 `?selftest=1`（6 项断言）。**

③ 改完必须跑 ?selftest=1，6/6 全绿
★★ 如果第 ② 步有红的：先修到全绿再交，不要交半成品。

**★ 而且「不要交半成品」这句要写** —— 否则它会交付 5/6，然后说「第 6 项需要泽哥确认」。

# 接一批「这个工具不顺手」的改造需求：怎么归因、怎么分批

> 2026-11-16 实测。用户连着提了 5 条关于内容看板的问题，5 条听着都要修，
> 归完只 3 类根因，最终 v7 只做了其中 2 类。
>
> 这份文件解决的是：**N 条抱怨 → 做哪几件 → 怎么跟他交代其余没做的。**

---

## 一、第一步永远是归因，不是排优先级

**★★★★ 直接把 5 条摊成 5 项任务，一定会发生两件事：**

```
① 改动面过大 —— 5 个模块同时动，回归面覆盖不了，哪层都没真跑通
② 做错顺序 —— 先做的那些，之后会被后做的推翻（实测：先加"流转按钮"，
   后来发现底下有两套状态机，按钮做完了也要拆掉重来）
```

**★★★ 正确动作：先问「这 5 条背后有几类原因」，再谈做什么。**

### 四类根因（覆盖大多数「工具不顺手」）

| 根因 | 识别信号 | 能不能改 | 卡在哪 |
|---|---|---|---|
| **A. 数据源没覆盖** | 某个维度恒为 0；分布完全均匀；用户说「明明有」但显示空 | ✅ 能 | 卡在「数据从哪来」——往往要用户提供，或另起抓取通道 |
| **B. 写不回文件** | 用户要「可调整 / 可编辑 / 可流转」，而页面是 `file://` 打开的单文件 | ⚠️ 要升级架构 | 卡在浏览器能力（File System Access API 或本地服务），是架构级改造 |
| **C. 信息架构乱** | 「罗列了但用不上」「看不出来源」「两块之间串不起来」 | ✅ 能，且便宜 | 纯前端重排，不动数据模型 |
| **D. 状态模型冲突** | 同一个概念在两处有不同词表 / 两份文件都能表示同一条 | ✅ 能，但必须先做 | 不修它，任何「流转」都建在沙地上 |

**★★ 一个关键判断：B 类通常会把 A、C、D 全部拖下水。**
因为「可调整」意味着「写回」，而写回要先有「写到哪、写成什么格式」——
那就是 D 类。**所以 B 不能和 C、D 同时做。**

---

## 二、排序判据：按「不修就没法真写」，不按工作量

**★★★★ 用户报问题的顺序、和修问题的顺序，几乎总是不同的。**

**★ 实测的排序方法：问「哪几条是他真用的时候撞上的？」**

```
真写的时候撞上的 → 必须修，否则工具继续空转
看数据的时候发现的 → 不急，而且没数据也照样能写
听起来最严重的 → 常常是最不急的
```

**★★ 实测那 5 条的真实排序：**

```
用户报的顺序：① 数据不对 ② 排期不可调 ③ 缺流转 ④ 素材用不上 ⑤ 复盘怎么录
真该做的顺序：④（素材选不出来 → 不修就选不出题）
　　　　　　　→ ③ 的根（两套状态机 → 不合并，流转无从谈起）
　　　　　　　→ ②（排期可调，需要架构升级）
　　　　　　　→ ①⑤（数据源，没数据也能先写）
```

**★ 判据一句话：能让他今晚就开始写的那几条，排最前。**

---

## 三、指令里必须有一节「这批不做」

**★★★ 不做的那几条，如果不写清理由和时限，用户会以为你漏了 —— 而他会憋着不问，下次一起算账。**

**写法（三列，缺一列都不行）：**

```markdown
## 附：这一批刻意不做的事（下一批再说）

| 你提的问题 | 为什么这批不做 | 什么时候做 |
|---|---|---|
| 四个账号数据不对 | 根因是数据源缺（库里只有 1 个号的文章），不是看板算错。要等你给数据 | v8 |
| 排期不可调整 | 需要 File System Access API（页面直接写库），是架构升级，要单独一批真测 | v8 主改造 |
```

**★ 三列的各自作用：**

```
第一列 = 承认我听见了（否则他觉得被忽略）
第二列 = 说明不是我偷懒（给根因，不给「优先级不高」这种空话）
第三列 = 给他一个可预期的位置（不是「以后」，是「v8」）
```

**★★ 反例：「这个优先级不高」「后面再优化」—— 这两句等于没答，而且会让他再问一遍。**

---

## 四、★★★ 技术技巧：截断列能当父子关系的钥匙

**场景**：一张 150 行的「角度对照表」，加一列叫「母素材」，存的是父素材标题的截断版（结尾带 `…`）。
需求是「把角度按素材分组」，但不能重建数据、不能新增字段。

**★★ 不用重建 —— 用归一化 + 前缀匹配就能归位：**

```python
def norm(s):
    """去掉 markdown 标记、引号、省略号、所有空白"""
    s = re.sub(r'[*`?""「」『』]', '', s)
    s = re.sub(r'[…\.]{1,}', '', s)
    s = re.sub(r'\s+', '', s)
    return s

def attach(sucai_list, jiaodu):
    """角度的「母素材」norm 后，是某条素材标题 norm 后的前缀 → 归位"""
    k = norm(jiaodu["母素材"])
    for sc in sucai_list:
        if len(k) >= 8 and norm(sc["标题"]).startswith(k):
            return sc
    return None
```

**★★★ 三条配套纪律（缺一条就会出错）：**

```
① 长度下限 8 —— 太短的前缀会误配（「开书店」能配上十几条）
② 必须打印归位失败的清单（失败角度的「母素材」原文 + 前 3 个候选）
   失败超过 10 个 → 停下来写清单，不许改匹配规则去凑
   （改规则会让错的也匹配上，比归位失败更糟）
③ 父子的显示要能看出「符合的 / 总数」，例如「1 / 6 个角度」——
   筛选之后如果只显示总数，用户会以为筛选没生效
```

**★ 泛化：凡是「子表有一列存了父表标题的截断版」，都可以这么归位。**
先做前缀匹配，匹配不上再谈改数据 —— **重建数据的成本比匹配高一个数量级，而且会引入两份不同步的数据。**

---

## 五、先数数据源的覆盖面，再怀疑代码

**★★★★ 实测：四个号全显示 0 篇，用户说「每个号都发过」。**
第一反应是「统计逻辑错了」，查了半天脚本 —— **实际是库里只有一个号的目录、7 篇存档。**

**★ 「数据不对」的第一嫌疑永远是源缺，不是算错。**

```bash
# 三十秒能跑完的覆盖面检查
find <数据根> -maxdepth 2 -type d | sed 's/^/  /'
for d in $(find <数据根> -maxdepth 2 -type d); do
  echo "  $d: $(find "$d" -maxdepth 1 -name '*.md' | wc -l) 个"
done
```

**★★ 判据：**

```
某个维度恒为 0，且分布完全均匀　→ 没数据，不是算错
分布有高有低，只是某些值不对　　→ 才是算错 / 解析错
```

**★★★ 找到源缺之后，不要立刻说「做不到」。**
给分层方案：**哪部分能自动（公开数据）、哪部分只能人工（后台数据）**。
「做不到」会让对话停住；「这两层，第一层我能做，第二层要你给」会让对话继续。

---

## 六、一句话

> **N 条抱怨先归成 2–3 类根因；按「不修就没法真写」排序；不做的写清理由和批次。**
>
> **★ 报问题的顺序和修问题的顺序几乎总是不一样 —— 而用户不会告诉你哪条是他真用的时候撞上的。**
>
> **★★ 「数据不对」先数覆盖面，「缺少接口」先查有没有两套状态机。**
