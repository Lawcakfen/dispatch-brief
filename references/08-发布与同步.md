# 对外发布的一致性维护 —— 三类「副本」、一次同步审计、两种写坏文件的方式

> 2026-11-16 实测。一天之内用户问了两次，语义上几乎一样：
>
> 1. 「以上是全部同步到公开版 Github 中了么？」
> 2. 「更新到 Github 网页了吗？我刷新了网页还显示是旧的版本内容」
>
> **两次都不是「推没推」的问题，是「推了，但副本没跟上」。第一次漏了 4 处文件，第二次漏了一张图。**
>
> ★★ 而且当天我还**自己写坏过两次文件**（双 CR、name 被覆盖）—— 见 §5。
> 这一节的存在本身就说明：**人工同步这件事，迟早会伤到文件本身。**

---

## 0. 核心认知：内容一变，有一批「副本」会静默过期

**★ 这类过期不会被任何自动检查发现** —— git status 干净、push 成功、远端文件都对，只有**人打开看**才知道不对。

**★★ 而且它的症状是「用户以为你没做事」** —— 你明明推了 6 次 commit，他看到的是同一张旧图。

**★★★ 判据：任何「源 → 多个展示面」的结构，都要问一句「源改了，哪些面不会自动跟」。**

---

## 1. 三类副本（按发现难度排序）

### 类型 A · 单文件产物里的「静态事实」—— 最难发现

**一个 HTML / 单文件产物，为了自包含，会把当时的机制细节写死在正文里。**

实测：机制图里有 8 处过时，全都藏在正文中段：

```
STEP 2   「必须带两句话」        ← 早已是三句话
cron 标题 「每 15 分钟扫一次」    ← 早已是 5 分钟
cron 表达式 `*/15 8-22 * * *`   ← 早已是 */5
「扫三样」                       ← 早已是四样（加了产物 mtime）
文件树注释「← 15 分钟扫描」
成本表「56 次/天」               ← 早已是 168 次/天
「五种输出」                     ← 早已是六种
输出列表                        ← 缺了第 ⑥ 种
```

**★ 为什么最难发现：它们不是「错误」，是「当时对、现在旧」。没有任何断言会失败。**

**★★ 检查方法（一次搜完，别靠记忆）：**

```python
# 把这几天改过的事实，做成「旧词 → 新词」清单，全文搜一遍
CHECKS = [
    ("两句话", "三句话"),
    ("*/15", "*/5"),
    ("15 分钟", "5 分钟"),
    ("五种", "六种"),
    ("扫三样", "扫四样"),
]
for old, new in CHECKS:
    n = s.count(old)
    if n: print(f"  ⚠ 「{old}」还有 {n} 处，应该都是「{new}」")
```

**★★★ 更根本的治法：产物里不存会变的事实。**
机制图这种「给人看的静态文档」躲不掉，但**可以显式标注哪几节是「快照」**，并把它列进发布前检查清单。

### 类型 B · README 里的预览图 —— 最容易被误判成「代码没推」

**实测：用户给的就是仓库首页地址，那里渲染的是 README，README 第 56 行引用了 `docs/preview.png`。**

**那张图是 11-15 截的。HTML 当天改了三轮，图一次没重截。**

**★★ 用户看到的「旧版本」，是图里的旧版本 —— 而且这张图里还有更糟的：占位符全是空白（截的是未转义的裸尖括号版本），他当初「不知道怎么操作」的截图就是它。**

**★★★ 检查方法：只要动了被截图的产物，就必须重截——写进发布清单，不靠记性。**

**★★★★ 而且重截之后要用 vision **逐项念一遍第一屏的文案**，不能只看「有没有截断」。**
错误在像素里，grep / md5 / 单测全都看不见。

### 类型 C · 文本里的数字 —— 最容易被忽略

实测三处：

```
仓库描述   「含 12 条实测踩出来的坑」   ← 实际 59 条
README     「cron 的五种输出」          ← 实际六种
README     「九节：…/ cron 的五种输出 / …」
```

**★ 数字类最容易说谎，因为它一眼看不出对错。凡是要写数字，就当场数一遍再写。**
**★★ 判据：凡是「一共 N 处 / N 条 / N 个」这种话，N 必须是脚本数出来的，不能是估的。**

## 2. 一次同步审计怎么做（不靠 git status）

**★★★ 「是否全部同步」这个问题，`git status` 和 `git log` 都答不了** —— 它们只说「本地有什么没提交」，不说「公开版缺了什么」。

### 第 1 步：两边文件清单求差

```python
pv  = files_of(PRIVATE)   # 私有版
pub = files_of(PUBLIC)    # 公开版
only_pv  = set(pv) - set(pub)    # ← 这些是「改了但没同步」
only_pub = set(pub) - set(pv)    # ← 这些是「公开版独有」（.gitattributes 之类）
```

**★ 实测这一步直接抓出 `references/01-派单与指令.md` 整个文件没同步（164 行）。**

### 第 2 步：对同名文件做字节比对

```python
diff_files = [f for f in both if open(pv[f],'rb').read() != open(pub[f],'rb').read()]
```

### 第 3 步：★ 关键 —— 对差异文件做「内容级判定」

**光看有差异没用，因为私有版和公开版本来就该有差异（`name`、脱敏）。**

**做法：把私有版按【预期规则】变换一遍，再比。变换后还不同 = 真遗漏。**

```python
EXPECT = [("workbuddy-brief-writing", "dispatch-brief"),
          ("泽哥", "你"), ("作者", "你")]

t = private_text
for a, b in EXPECT:
    t = t.replace(a, b)
if t == public_text:
    print("✓ 差异全部是预期内的")
else:
    # 输出第一处不同 + 两边的原文，肉眼判断
```

**★★ 实测量出 4 处真遗漏：**

```
02-盯梢与自动化.md   缺 62 行（整整一节「提高频率≠更接近 SuperAgent」）
01-派单与指令.md  整个文件缺失（164 行）
SKILL.md        缺一条常见坑（外部 AI 评审怎么处理）
08-发布与同步.md  文件清单落后（少列两个文件）
```

**★★★ 如果只做第 1、2 步，这 4 处里有 3 处会漏掉** —— 因为文件两边都存在，只是内容不同。

### 第 4 步：预期差异白名单（只有这四类，别的都是 bug）

```
① SKILL.md 的 name:        私有 workbuddy-brief-writing / 公开 dispatch-brief
② LICENSE 的署名            私有 <YOUR NAME> / 公开 真实署名
③ README 顶部的镜像说明      私有版多一段「权威版在 <repo>/README.md」
④ 脱敏替换                  泽哥/作者/他 → 你
```

**★★ 白名单之外的任何差异，都当 bug 去查，不许「看着差不多就放过」。**

**★★★ 脱敏规则要覆盖代词** —— 只换「泽哥/作者」不够，公开版会残留「他删标准、加标准」这种句子，读者会问「他是谁」。

```python
s = re.sub(r"(?<!其)他", "你", s)   # ★ 必须排除「其他」，否则变成「其你」
```

**替换完必须复扫两个词：隐私词（泽哥/作者/客户名/用户名/盘路径全称）和误伤词（其你）。**

## 3. GitHub 页面认知 —— 为什么「刷新还是旧的」

**用户刷新的三个可能位置，各自的真相：**

| 他打开的位置 | 实际显示什么 | 会不会显示你的改动 |
|---|---|---|
| `github.com/<user>/<repo>`（仓库首页） | 渲染 **README.md** | 只在 README 改过时 |
| `.../blob/main/xxx.html` | **源码**，不是渲染页 | 能看到，但要读代码 |
| `raw.githubusercontent.com/...` | 纯文件 | 会，但有 CDN 缓存 |

**★★ 关键：GitHub 网页上 `.html` 文件**永远不会渲染成页面**。用户若在找「排版效果」，那边永远看不到 —— 必须双击本地文件。**

**★★★ CDN 缓存：`Cache-Control: max-age=300`（5 分钟）。push 完立刻查 raw 可能还是旧的。**

**★★★★ 判断「到底推上去没有」的唯一可靠办法是 GitHub API，不是 raw：**

```bash
gh api "repos/<user>/<repo>/contents/<path>" --jq '{size: .size, sha: .sha}'
# 跟本地比：sha 一致 = server 端已经是新的
# raw 拿到旧内容 = 只是 CDN 没刷，不是没推
```

**实测那次：raw 给 159673（旧图），API 给 242153（新图）—— 两者都是「真的」，说的是不同层。**

**★★★★★ 所以对用户的话要分开说：「server 端已经是新的（API 验证 sha 一致），你看到旧的是 CDN 缓存，Ctrl+Shift+R 或等 5 分钟」。**
**另外加一个绕过缓存的技巧：URL 加 `?t=<timestamp>`（对 HTML 有效，对图片不够可靠 —— 图片以 API 为准）。**

## 4. 写 HTML 模板后的渲染验证（发布前必做）

**★ 源码正确 ≠ 页面正确。** 最典型的一类：`<中文>` 被浏览器当未知标签吃掉，页面上只剩文字、没有尖括号。

```bash
# 抓 DOM（不是源码）
edge --headless=new --virtual-time-budget=8000 --dump-dom file:///... > dom.txt

# 断言：DOM 里不该还有裸中文标签
grep -oE '<[\u4e00-\u9fff][^<>]{0,24}>' dom.txt   # 期望 0 处
```

**★★ 再断言「该出现的都在」：**

```python
for kw in ["六种输出", "产物变了但没记录", "每 5 分钟扫一次", "必须带三句话"]:
    assert kw in dom
for kw in ["两句话", "*/15", "15 分钟扫一次"]:
    assert kw not in dom      # ← 旧词必须清零
```

**★★★ 「旧词必须清零」这一条是本次最值钱的断言 —— 它同时验了「新的来了」和「旧的走了」。**

## 5. ★★★★★ 我写坏过文件两次 —— 人工同步的两个机械陷阱

**这一节不是「注意事项」，是两次真实损坏。**

### 5.1 Windows 双 CR：417 行变 1652 行，文件能打开、不报错

**现象：** markdown 从 417 行变成 1652 行，每两行之间多一个空行。
**文件能打开、能渲染、git 也不报错** —— 不查字节永远发现不了。

**根因：两次换行转换叠加**

```python
# 错
s = load(p)                       # 读进来已归一成 \n（newline="" 或手动 replace）
s = s.replace("\n", "\r\n")       # 手动换成 CRLF
open(p, "w", encoding="utf-8").write(s)
# ↑ text mode 的 open(...,"w") 会把 \n 再转成 \r\n  → 结果 \r\r\n
```

**正确写法（读写 newline 必须成对）：**

```python
def load(p):
    with open(p, encoding="utf-8", newline="") as f:
        return f.read().replace("\r\n", "\n").replace("\r", "\n")

def save(p, s):
    with open(p, "w", encoding="utf-8", newline="") as f:   # ★ newline="" 关掉自动转换
        f.write(s.replace("\n", "\r\n"))
```

**判据（每次改完 markdown 都跑）：**

```python
raw = open(p, "rb").read()
assert raw.count(bytes([13, 13, 10])) == 0, "有双 CR，文件被写坏了"
```

### 5.2 跨版本复制会覆盖身份字段

**从公开版恢复私有版时，`name:` 被一起写过去了。**

**后果不是报错，是 skill 加载不到** —— 而那个 name 被 5 个其它文件引用
（`.usage.json`、三个 skill 的交叉引用、账本）。

```bash
grep -n "^name:" SKILL.md     # 私有版必须是 workbuddy-brief-writing
```

**★★ 同理 `LICENSE` 的署名也会被覆盖 —— 它不在 .gitignore 里，是普通文件。**

**★★★ 规则：任何跨版本复制之后，第一件事是验 `name:` 和 `LICENSE` 署名。**

### 5.3 写坏了怎么恢复（不要在坏文件上手工补）

```
1) git show HEAD:<file> > 基准       ← 干净的公开版
2) 施加私有版的【增量】（哪几条是公开版没有的）
3) 按 §5.1 的 newline="" 写回
4) 双 CR 复验（必须 0）
5) 差异复验（§2 的审计）
```

**★ 关键：先想清楚「增量是哪几行」，不要重新手工编辑全文。**
实测：两次「手工合并」都引入了新 bug（表格行被切断、正撞上「patch 报 Found N matches」那条坑），
第三次用「基准 + 增量」一次就对。

## 6. ★★★★★ fresh-install 测试：发布判据不是「我这儿能跑」

**这是「能不能给别人用」的唯一验证方式。用本地仓库测永远测不出来 —— 因为本地环境已经配好了。**

```
1) git clone 到【临时目录】（不要用本地仓库 —— 里面有你的 agent-config.json）
2) 设一个【假的】HERMES_HOME（避免污染真实 state）
3) 完全不看本地经验，严格按 README 从头走
4) 断言链：
     未配置时 → 有清晰的操作指引（不是报错堆栈）
     配置后   → 自检通过
     --init   → 建基线成功
     无事件   → 静默（不是报「一切正常」）
     改文件   → 能抓住
```

**实测抓到两个真 bug（都只有新用户会撞上）：**

```
① check_heartbeat 对「没配每日 cron」的用户每 5 分钟报一次假警报（168 条/天）
② __pycache__ / .pyc 污染「今日新增文件」列表
```

**★★★ 这两个用本地仓库跑一万次也发现不了 —— 本地那条 cron 配好了、它活着，所以永远不报警。**

**★★★★ 所以发布判据是：「干净机器上照 README 能跑」，不是「我这儿能跑」。**

## 7. ★★★★ 代码要能发布：把散落的绝对路径收敛成一处配置

**现象：** 5 个脚本里 10 处写死 `C:\Users\<某人>\...` / `E:\<某库>\...`，
另外 9 处客户名 / 项目名硬编码在 `FOCUS = [...]` 这类列表里。

**后果两重：**
① 换机器直接崩（README 教人「跑那三个脚本」，一跑就 FileNotFoundError）
② 客户名不能公开（而客户名就写死在代码里）

**做法 —— 新增一个 `paths.py` 作为唯一来源：**

```
优先级：环境变量 > agent-config.json > 自动探测 > 兜底
```

**四个要点：**

```
① JSON 没有注释 → 用 `_` 开头的键写说明，读取时自然被忽略
② 自动探测要真的有用：Windows 找 %LOCALAPPDATA%\hermes，Mac/Linux 找 ~/.hermes
   项目根则「从 cwd 往上找 4 层，看哪层下面有带队列文件的目录」
③ 自检函数必须打印【每一项的值 + 来源 + 可用性】
       HERMES_HOME   <value>
                     （来源：环境变量 / agent-config.json / 自动探测）
       项目根可用    是 / 否 ← 这个必须修
④ ★★★ 配置不全时直接打印三步操作指引（复制模板 → 改哪个值 → 再跑）
```

**★★★★★ 第 ④ 条比 README 更管用** —— 实测新用户跑一次 `paths.py`
就知道该干什么，不用回头翻文档。
**这就是「可观测」的具体例子：不是告诉他有这件事，是把「下一步动作」放在他眼前。**

**★★ 配套：`agent-config.json` 要进 `.gitignore`**，仓库里只留 `agent-config.example.json`。

# 自用版 → 开源版：一份源、两个产物（2026-11-21）

> 这份 skill 自己有公开孪生仓库（GitHub `dispatch-brief`）。
> 下面是把「我机器上这份」和「发出去那份」维持在可控状态的做法。
> **通用问题**：任何「内容有用但掺了私有信息」的资产要对外发布时，都适用。

---

## 0. 先把两个词分开 —— 这里最容易说糊

```
同步 = 把自用版新踩的通用坑，挑几条摘进开源版（单向、挑着摘）
合并 = 两份变成一份（物理上就是一个文件）
```

**★★★★ 我一开始用「同步」但说的是「合并」的意思，用户当场追问「你所说的同步是指合并吗」。
这类含糊会直接导致一个错误的工程决定 —— 先把词校准，再谈方案。**

**用户的真实诉求往往是第三种，说清它：**

```
一份真源 → 两个产物（自用版 / 开源版各自由它生成）
```

**★★ 这跟「一个文件给两个读者」完全不同 —— 后者不可行（见 §2），前者可行且省事。**

---

## 1. 先量化，再决定方案

**动手前数一遍私有信息占多少：**

```bash
for k in <人名> <客户名> <项目名> <路径>; do
  printf "%-10s " "$k"; grep -rc "$k" SKILL.md references/*.md | awk -F: '{s+=$2} END{print s+0}'
done
```

**实测：16 处 / 899 行。**

**★★★★ 这个数字决定方案：占比低 → 替换表就够，不需要大动架构（不需要标记满天飞）。**
如果私有内容占 40%，标记会满天飞，那时「合并」确实不如不合并。

---

## 2. 为什么不能真的合成一个文件

```
① 脱敏是单向的、破坏性的
   真名 → 占位符，反向合并还原不回来。
   「示例书店活动海报设计」在自用版里是有用的记忆锚点，在开源版里必须是「<你的项目>」。

② 两个读者的需求相反
   自用版读者 = 我 → 路径必须写死（多一步就懒得改）
   开源版读者 = 陌生人 → 路径必须在配置里
   这不是版本差，是需求冲突。

③ 一份文件两个读者 → 每次改都要判断「这句能不能公开」→ 摩擦 → 两边都不更新
```

---

## 3. 落地形态

```
源   = 自用版目录（我每天读、每天改的那份）
产物 = 公开仓库

新增两个文件（只在自用版里）：
  publish-map.json    脱敏词表（人名/客户名/店名/绝对路径 → 占位符）
  build_public.py     50 行：删 private 段 → 排除 private-* 文件 → 按词表替换 → 写到仓库

极少数「必须整段删」的，用 HTML 注释包住（Markdown 渲染看不见，不影响日常读写）：
  <!--#private-->
  这段只给自用版：……
  <!--#/private-->
```

**★★★★ 判据：能让替换救的就不加标记 —— 标记越多，以后改越容易漏。**

**★★★ build 必须 fail-closed：**

```python
# 替换完 grep 一遍私有词，非 0 就报错退出，不写任何文件
leak = [w for w in MAP if w in out]
if leak:
    sys.exit("私有词残留 %s —— 没写文件" % leak)
```

**实测这次开源版里就残留了两处**（`示例书店活动海报设计@Workbuddy`、`我是示例·小红书`）——
**靠人眼搜会漏，靠脚本不会。**

**★★ 不做自动 push** —— 发布要人看一眼 `git diff`，这一步不该自动化。

---

## 4. 日常动作必须为零摩擦

```
改内容    → 还是改自用版（和以前完全一样，不用记「先改哪份」）
要发布    → python build_public.py → git diff 看一眼 → git push
```

**★★★★ 源必须放在「我平时就在读的那个目录」。**
放在公开仓库、再从那里 build 出自用版 → 改的时候要多一步 → 一定懒得改 → 必然分叉。
**实测这次已经分叉了 5 天（自用版 899 行 / 开源版 431 行），方向单一（开源版是真子集，0 个独有章节）。**

---

## 5. 追不追新，先看有没有人用

**★★★★★ 决定「要不要花时间同步」的第一步不是看内容差距，是看使用数据：**

```bash
curl -s --noproxy '*' https://api.github.com/repos/<owner>/<repo> | python -c "
import json,sys; d=json.load(sys.stdin)
print('star', d['stargazers_count'], 'fork', d['forks_count'],
      'watch', d['subscribers_count'], 'issue', d['open_issues_count'],
      'pushed', d['pushed_at'][:10])"
```

**实测：star 1 / fork 0 / watch 0 / issue 0 / 5 天没推 —— 没人用。**

**★★★ 结论当场变了：「挑 8 节同步进开源版」这个建议被自己推翻 ——**
那 8 节对唯一用户（作者本人）没有价值增量，对零个外部用户也没有。
**正确做法：等有人提 issue 再同步；现在只做两件 —— 修脱敏漏网、README 写清「这是快照」。**

**★★ 顺带纠正一个说法：开源版「落后 5 天」不是欠债，是设计。**
README 里写一句「这是 2026-11 的方法论快照，作者自用版一直在长，含私有信息不公开」，
以后再想起「要不要同步」，这句话就是答案。

## 6. 对外发布时的两条附带判断

```
① 「执行方」要定义成三条件接口，不要写成某个产品的说明书
   能读粘进去的指令 / 能改文件 / 能往一个日志目录写
   → WB / Codex / Cursor / Cline / 另一个会话窗口都算
   （这一点决定了适用面大一个量级，而且对作者自己也有用：换工具不用重学方法论）

② 别交全套，交「30 分钟能跑起来」的最小包
   读者要的不是完整体系，是「我也能用起来」。
   判据：他们能不能 30 分钟内跑起来？不能，就太厚了。
```
