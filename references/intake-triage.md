# 接一批「这个工具不顺手」的改造需求：怎么归因、怎么分批

> 2026-11-16 实测。用户连着提了 5 条关于内容看板的问题，5 条听着都要修，
> 归完只 3 类根因，最终 v7 只做了其中 2 类。
>
> 这份文件解决的是：**N 条抱怨 → 做哪几件 → 怎么跟你交代其余没做的。**

---

## 一、第一步永远是归因，不是排优先级

**★★★★ 直接把 5 条摊成 5 项任务，一定会发生两件事：**

```
① 改动面过大 —— 5 个模块同时动，回归面覆盖不了，哪层都没真跑通
② 做错顺序 —— 先做的那些，之后会被后做的推翻（实测：先加"流转按钮"，
   后来发现底下有两套状态机，按钮做完了也要拆掉重来）
```

**★★★ 正确动作：先问「这 5 条背后有几类原因」，再谈做什么。**

### 四类根因（覆盖大多数「工具不顺手」）

| 根因 | 识别信号 | 能不能改 | 卡在哪 |
|---|---|---|---|
| **A. 数据源没覆盖** | 某个维度恒为 0；分布完全均匀；用户说「明明有」但显示空 | ✅ 能 | 卡在「数据从哪来」——往往要用户提供，或另起抓取通道 |
| **B. 写不回文件** | 用户要「可调整 / 可编辑 / 可流转」，而页面是 `file://` 打开的单文件 | ⚠️ 要升级架构 | 卡在浏览器能力（File System Access API 或本地服务），是架构级改造 |
| **C. 信息架构乱** | 「罗列了但用不上」「看不出来源」「两块之间串不起来」 | ✅ 能，且便宜 | 纯前端重排，不动数据模型 |
| **D. 状态模型冲突** | 同一个概念在两处有不同词表 / 两份文件都能表示同一条 | ✅ 能，但必须先做 | 不修它，任何「流转」都建在沙地上 |

**★★ 一个关键判断：B 类通常会把 A、C、D 全部拖下水。**
因为「可调整」意味着「写回」，而写回要先有「写到哪、写成什么格式」——
那就是 D 类。**所以 B 不能和 C、D 同时做。**

## 二、排序判据：按「不修就没法真写」，不按工作量

**★★★★ 用户报问题的顺序、和修问题的顺序，几乎总是不同的。**

**★ 实测的排序方法：问「哪几条是你真用的时候撞上的？」**

```
真写的时候撞上的 → 必须修，否则工具继续空转
看数据的时候发现的 → 不急，而且没数据也照样能写
听起来最严重的 → 常常是最不急的
```

**★★ 实测那 5 条的真实排序：**

```
用户报的顺序：① 数据不对 ② 排期不可调 ③ 缺流转 ④ 素材用不上 ⑤ 复盘怎么录
真该做的顺序：④（素材选不出来 → 不修就选不出题）
　　　　　　　→ ③ 的根（两套状态机 → 不合并，流转无从谈起）
　　　　　　　→ ②（排期可调，需要架构升级）
　　　　　　　→ ①⑤（数据源，没数据也能先写）
```

**★ 判据一句话：能让你今晚就开始写的那几条，排最前。**

## 三、指令里必须有一节「这批不做」

**★★★ 不做的那几条，如果不写清理由和时限，用户会以为你漏了 —— 而你会憋着不问，下次一起算账。**

**写法（三列，缺一列都不行）：**

```markdown
## 附：这一批刻意不做的事（下一批再说）

| 你提的问题 | 为什么这批不做 | 什么时候做 |
|---|---|---|
| 四个账号数据不对 | 根因是数据源缺（库里只有 1 个号的文章），不是看板算错。要等你给数据 | v8 |
| 排期不可调整 | 需要 File System Access API（页面直接写库），是架构升级，要单独一批真测 | v8 主改造 |
```

**★ 三列的各自作用：**

```
第一列 = 承认我听见了（否则你觉得被忽略）
第二列 = 说明不是我偷懒（给根因，不给「优先级不高」这种空话）
第三列 = 给你一个可预期的位置（不是「以后」，是「v8」）
```

**★★ 反例：「这个优先级不高」「后面再优化」—— 这两句等于没答，而且会让你再问一遍。**

## 四、★★★ 技术技巧：截断列能当父子关系的钥匙

**场景**：一张 150 行的「角度对照表」，加一列叫「母素材」，存的是父素材标题的截断版（结尾带 `…`）。
需求是「把角度按素材分组」，但不能重建数据、不能新增字段。

**★★ 不用重建 —— 用归一化 + 前缀匹配就能归位：**

```python
def norm(s):
    """去掉 markdown 标记、引号、省略号、所有空白"""
    s = re.sub(r'[*`?""「」『』]', '', s)
    s = re.sub(r'[…\.]{1,}', '', s)
    s = re.sub(r'\s+', '', s)
    return s

def attach(sucai_list, jiaodu):
    """角度的「母素材」norm 后，是某条素材标题 norm 后的前缀 → 归位"""
    k = norm(jiaodu["母素材"])
    for sc in sucai_list:
        if len(k) >= 8 and norm(sc["标题"]).startswith(k):
            return sc
    return None
```

**★★★ 三条配套纪律（缺一条就会出错）：**

```
① 长度下限 8 —— 太短的前缀会误配（「开书店」能配上十几条）
② 必须打印归位失败的清单（失败角度的「母素材」原文 + 前 3 个候选）
   失败超过 10 个 → 停下来写清单，不许改匹配规则去凑
   （改规则会让错的也匹配上，比归位失败更糟）
③ 父子的显示要能看出「符合的 / 总数」，例如「1 / 6 个角度」——
   筛选之后如果只显示总数，用户会以为筛选没生效
```

**★ 泛化：凡是「子表有一列存了父表标题的截断版」，都可以这么归位。**
先做前缀匹配，匹配不上再谈改数据 —— **重建数据的成本比匹配高一个数量级，而且会引入两份不同步的数据。**

## 五、先数数据源的覆盖面，再怀疑代码

**★★★★ 实测：四个号全显示 0 篇，用户说「每个号都发过」。**
第一反应是「统计逻辑错了」，查了半天脚本 —— **实际是库里只有一个号的目录、7 篇存档。**

**★ 「数据不对」的第一嫌疑永远是源缺，不是算错。**

```bash
# 三十秒能跑完的覆盖面检查
find <数据根> -maxdepth 2 -type d | sed 's/^/  /'
for d in $(find <数据根> -maxdepth 2 -type d); do
  echo "  $d: $(find "$d" -maxdepth 1 -name '*.md' | wc -l) 个"
done
```

**★★ 判据：**

```
某个维度恒为 0，且分布完全均匀　→ 没数据，不是算错
分布有高有低，只是某些值不对　　→ 才是算错 / 解析错
```

**★★★ 找到源缺之后，不要立刻说「做不到」。**
给分层方案：**哪部分能自动（公开数据）、哪部分只能人工（后台数据）**。
「做不到」会让对话停住；「这两层，第一层我能做，第二层要你给」会让对话继续。

---

## 六、一句话

> **N 条抱怨先归成 2–3 类根因；按「不修就没法真写」排序；不做的写清理由和批次。**
>
> **★ 报问题的顺序和修问题的顺序几乎总是不一样 —— 而用户不会告诉你哪条是你真用的时候撞上的。**
>
> **★★ 「数据不对」先数覆盖面，「缺少接口」先查有没有两套状态机。**
