# 改造一个已有的代码文件（不是从零生成）

> 从 `SKILL.md` 拆出（2026-11-15）。

---

### C. ★★★★★ 改造一个已有的代码文件（不是从零生成）

**场景**：用户说「这个工作台不顺手」「发布页也不好用」→ 产物是**几百 KB、别人在持续维护的代码**。

**★★★★ 这一类最容易白干一轮，原因只有一个：让执行 Agent 改错了文件。**

#### C-0 ★★★★★ 动手前先打印实际数据，不要从界面推断

**这是本类任务最贵的一个坑，我实打实踩过一次整轮。**

```
看截图：顶部「已发 8」、每行都有「记数据」按钮
→ 推断「8 条都卡在记数这一步，所以复盘是空的」
→ 据此写了整套四列看板方案，让 WB 做完了一整批

事后打印 DB.items：
  13 条全部是 demo:1（示例数据），真实数据 0 条
  那 8 条每条都带全了 views / wr / likes / colls / cmts / fans / note
```

**结论：我在给一个从没真正用过的工作台做装修，解决的是一个不存在的问题。**

**固定动作（写任何改造指令之前）：**

```
① 找到数据在哪（DB.xxx / JSON 文件 / localStorage）
② 打印出来看：总条数、每条的关键字段、有没有 demo / sample / isSample 标记
③ 分清「示例数据」和「真实数据」—— 界面上通常看不出这个区别
④ 确认是真数据，界面上的现象才可信
```

**★★ 界面是「别人写的渲染」，数据才是事实。从渲染推事实，等于隔着一层猜。**

**★★★ 「示例数据冒充真实进度」是最隐蔽的一种** —— 用户自己也会被骗
（你以为账号已经发了 8 条）。**所以这条不只保护我，也保护你。**

**★★★★ 一个连带判断**：如果一打印发现真实数据是 0，
**那当前最先要做的不是改界面，是「让真实数据进得来」** ——
空壳上做装修，做完还是空壳。

#### C-1 先确定「哪个文件是活的」

AI 生成的工具常有这个病：**同一个函数在两个文件里各有一份**
（先写了 `main.js`，后来又把 JS 内联进 HTML，两份都留在原地）。

```python
import re
fj = set(re.findall(r"^function (\w+)\s*\(", open("main.js").read(), re.M))
fh = set(re.findall(r"^function (\w+)\s*\(", open("page.html").read(), re.M))
print(len(fj - fh), len(fh - fj))              # 都是 0 → 一个是另一个的逐字副本
print(html.count("<script"), html.count("main.js"))   # 0 → HTML 不引用那个 .js
```

**判据：HTML 不 `<script src>` 那个 JS + 两边函数集合零差异 → 改 HTML 里的内联 JS。**

**★★★ 指令里必须写死这一条。** 否则 WB 会去改那个看起来更「正规」的 `.js`，
改完不生效，回报「已修改」，你验收时才发现白干一轮。

**★ 副本怎么处置**：让它改完把内联 JS **整段覆盖回 `.js`**（保持同步），
并写明后果：「不这么做的后果：下次谁改 `.js` 都不生效」。
**别让它删** —— 删文件不是它该自己做的决定。

#### C-2 指令必须写的四件套

```
① 备份：沿用项目里【已有的】命名习惯（如 _bak_before_m1.html），不要发明新格式
② 改哪个文件：绝对路径 + 「哪个是活的」（C-1 的结论）
③ 范围边界：不许改什么
④ 出错怎么办：删函数导致别处报错 → 恢复函数，只加 return; 停用
```

**★★★★ ③ 要具体到能被判真假：**

```
✗ 「不要改动其他功能」
✓ 「不改 DB.items 字段结构（不加字段、不改名）
   不改 save / load / 云端同步（pullRemoteReview / pushRemoteReview）
   不改另外 6 个页面
   不改配色变量、字号体系、圆角体系」
```

**★ 为什么这么严**：几百 KB 里它「顺手优化」一个变量名的代价，
可能是你花两小时都找不回来的。

#### C-3 ★★★★ 停用，不要删除

**改别人的代码时，删东西比加东西危险十倍。**

```
删一个渲染函数 → 别处还在调 → 整页 JS 崩（报错位置离你改的地方很远）
删一个 DOM 节点 → JS 拿到 null → .innerHTML 报错
```

**固定写法，三道一起上：**

```js
// ① 容器：隐藏，不删元素
<div id="slot-ref" style="display:none"></div>

// ② 函数体第一行：直接 return，原代码一行不动
function renderSlotRef(){
  return;   // 停用：本批不做
  ...原代码保留...
}

// ③ 调用处：只去掉那一句
renderGolden();          // 原来是 renderSlotRef(); renderGolden();
```

**★ 判据：删完若报错位置不在你改的地方，就掉进这个坑了。**

#### C-4 验收清单必须有「回归项」

**这类改动最大的风险不是新功能不好用，是把别的页面弄坏了。**

```
□ ★ 另外 6 个页面（今日/选题/写稿工具箱/稿件/复盘/我的）与改之前完全一样
```

**★★ 放在清单【最后】并写明「交付前请自己点一遍」** —— 放中间会被跳过。

#### C-5 回报的第③项：它没敢动的地方

**这是判断「有没有乱改」的唯一依据。**

```
① 各组的条数（给可核对的期望值，如 4 / 1 / 8 / 0）
② 改动位置清单 + 副本同步了没有
③ ★ 哪些地方你没敢动、或按自己判断处理了 —— 逐条列
```

**★★ 不要求这一项，你只会收到「已完成，共改 7 处」，然后自己去猜哪里被自由发挥了。**

#### C-6 ⚠️ 别静默缩水用户已批准的方案

**真实发生过的内心活动**：用户批了「四列看板」，写指令时觉得风险高，
想改成「先加一个提醒条」—— **那是静默降级，等于替你否决了你自己的决定。**

```
✓ 要么按批准的方案做，把风险写进指令（用「分批 + 停用而非删除」降风险）
✓ 要么明说「第一批我建议缩到 X，因为 Y」，让你重新拍
✗ 不能默默做一个更小的东西，然后说「按你说的做了」
```

**★ 降低风险的正确手段是「分批 + 可回滚」，不是「把方案改小」。**

#### C-7 ★★★★★ 数字断言：把「做对没有」变成「敢不敢撒谎」

**凡是能数清的东西，指令里就写死一个期望数字，并写死对不上怎么办。**

```
✓ 「55 个『可以写什么』按『；或』切分，应得 150 个角度。
    不是 150 → 打印实际数字 + 退出码 1，不许生成半成品。」
✓ 「对照表解析 150 行 → 必须匹配 150 个角度。任何一个角度没匹配到账号
    → 打印该行 + 退出码 1，不要给默认值。」
```

**★ 数字必须自己先算一遍再写进指令**（我是在源文件里数了 `；或` 出现 95 次、
实际切出 150 个，才敢写这个断言）。**不要让它去猜阈值。**

**★★ 这条的三重收益：**
```
① 它没法用"看起来对"糊过去 —— 对不上就必须停下
② 验收时你不用读代码，看它有没有报错中断就够了
③ 数字本身就是你和它的共同事实基础，省掉一轮来回
```

**★★★★★ 但 2026-11-14 v2 又踩出它的上限：数字断言会「假绿」。**

```
我的对照表实际只有 131 行有效（换行把 markdown 表格撑断了）
它两次都报「解析 150 行 → 匹配 150 个角度」
```

**根因（看它的代码才发现）：**
```python
main = c[-2]                                   # 倒数取列，多一个 | 就取错
if main not in ACCOUNTS: continue              # 非账号行（表头/残片）静默跳过
```

**★★ 宽容的解析 + 静默跳过 = 只要剩下的行凑够 150，断言就是绿的。**

**所以断言只能挡「数量级错误」，挡不住「错位」和「绑定错对象」。**

**判据：**
```
断言（数量级）　　→ 写进指令，交给它跑
断言之后的全量比对 → 我自己做，见 tool-workflow-audit 的
                      references/html-board-verification.md §8.5
```

**★★★ 还有一条：解析方式也要写死，别给自由。**

```
✗ 「解析这张表」　　　　　　→ 它会选「倒数取列」这种一看就脆的写法
✓ 「按固定索引取第 5 列 / 第 6 列，并校验每行竖线数 == 7」
```

#### C-8 ★★★★ 判断活不要外包；判断结果要落成「它能改的表」

**分工边界的判据：需要懂用户业务的，我判断；不需要懂的，它实现。**

```
✗ 让它去标「这 150 个选题分别该发哪个号」
   → 它不知道用户的账号分工，会按关键词硬套，标完 150 个全要返工
✓ 我标（读一遍全部条目，按用户口头给的分工判）
   → 产出 Outputs/drafts/角度-账号对照.md（150 行表格）
   → 它只负责「读这张表」，不负责「生成这张表」
```

**★★★ 判断结果的落地形态很关键：生成「人能直接改的表」，不是 JSON。**
```
✓ markdown 表格，一列一个字段，用户改「主号」那一列就行，改完重跑脚本即生效
✗ JSON —— 用户改不了，改完还得再生成一次，多一道手
```

**★ 所以指令里要写：「这个文件是用户手工维护的，你只读不写，也不许把数据复制一份到自己代码里。」**

**★★ 分类设计必须允许「多归属」** —— 用户的真实情况是「读书会两号都发」：
```
主号（最该发这个） ｜ 可兼（也能发）
```
**强制单选会把一半条目切错。**

**★★★★ 我这一侧也犯了一个错：生成出来的表本身可能是坏的。**

```
150 行对照表，实际只有 131 行有效
根因：角度文本里带换行 → markdown 表格行被撑断 → 后半截变成非 | 开头的残片
后果：19 条绑定静默丢失（编号 116 118 120 … 144 147 148 149 150）
```

**★ 固定动作：写 md 表格的脚本，写完必须回读自检。**

```python
def clean(v):
    v = re.sub(r"\s+", " ", v.strip())    # ★★★ 换行/制表符会撑断表格行
    return v

back = open(OUT, encoding="utf-8").read()
parsed = [int(m.group(1)) for m in re.finditer(r"^\| (\d+) \|", back, re.M)]
assert len(parsed) == 150, f"回读只解析出 {len(parsed)} 行"
assert sorted(parsed) == list(range(1, 151)), "编号不连续"
```

**★★ 泛化：凡是我生成「给用户手工改的表格」，都要回读断言行数 + 编号连续。**
这跟「覆盖前重读磁盘」是同一条纪律的两个面 —— **写出去的东西，读回来才算数。**

#### C-8b ★★★★ 做分类之前，先跑一遍分布；空了就合并

**同一个会话里，标「账号」一次成功（63/43/22/22 均匀），标「类型」却塌了。**

```
用户确认 6 类（判断型/讲述型/活动招募/读书会/工具方法/案例拆解）
→ 跑完实际分布：判断 93 ｜ 讲述 1 ｜ 活动 8 ｜ 读书会 15 ｜ 方法 31 ｜ 案例 16
→ 讲述型 1 条、活动招募 8 条：这两个筛选按钮做了也没意义
```

**根因（值得记）：素材写的是「借 X 讲 Y」，X 在文本里，Y 常常不在。**
自动关键词只能匹配到 X，于是「借苏轼讲品牌觉察」被判成「读书会」——
**类型错在判据抓不到真正的落点，不是判据写漏了词。**

**所以固定顺序是：**

```
① 先按规则全量跑一遍 → 只打印分布，不写文件
② 看有没有某类 < 5%：有 → 合并，或直接改维度
③ 抽查 15–20 条，看判据是不是在抓「表面词」而不是「真实落点」
④ 分布合理了，再出表
```

**★★★ 两个备选维度，哪个能自动算准就用哪个：**

```
内容形态（判断/讲述/活动/方法/案例）→ 需要理解落点，自动判不准
花多少力气（能当天写完 / 要憋一下 / 直接能发）→ 按角度字数 + 招募关键词，可算准
```

**★ 用户说「按类型」时，「类型」可能不是形态 —— 也可能是「今天我想写哪种力气」。**
复述阶段就要把这两个候选摊给你选（见 §0）。

**★★ 分布不均不是失败，是发现**：93 条判断 + 1 条讲述，本身就在说
「你的素材几乎全是借别人的事讲自己的判断，很久没写自己的事了」。
**把这个数字原样告诉用户，比凑出一个好看的六宫格有用。**

#### C-8c ★★★★★ 「切得细」不等于「选题多」—— 虚数量要主动拆穿

**场景（2026-11-15）**：55 条素材按「；或」切成 150 个角度，界面写「150 个角度」。
用户看了一眼，只说了一句：「这 150 个角度是不是太夸张了」—— **你是对的。**

```
表面：150 个选题
实际：55 条素材 × 平均 2.7 个侧面
     同一条素材的 6 个角度，往往讲的是同一件事（分数还一样，
     「换一条」六次都在同一条素材里打转）
     52/55 条素材来自外部文章 → 140+ 个角度「别人读过同一篇也能写」
```

**★★★ 三个具体的虚：**

```
① 机器切的，不是人想的 —— 字段原名「可以写什么」，本意是「这条有几种写法」
② 没有「独特性」筛子 —— 第一问该是「别人也能写吗」，不是「我有多少条」
③ 首屏堆满 = 劝退 —— 打开看见 114 行表格，那个视觉量本身就是阻力
```

**★★★★ 但最诚实的一句不是「150 太多」，是：**

```
150 个角度，到今天为止写出了 0 篇。
一篇没写，那 20 条也一样夸张 —— 问题不在数量，在没写出过第一篇。
```

**★★ 所以不要急着砍到 20 条。正确动作是三步：**

```
① 先用「今天写这条」写出第一篇（哪怕 200 字）
② 用户写完会自己说出该砍到几条 —— 你那一刻的感觉，比我按规则砍准
③ 真正的解法是打通「项目 → 素材」：让你自己的经历进库，比例才会翻转
```

**★ 第 ③ 步为什么是根**：素材库里 52/55 条来自外部文章，
所以「讲述型只有 1 条」不是分类出错，是**你的库只收「读到的」，不收「做过的」**。
而「我为什么停掉这个项目」这类内容，别人写不了、也不会过期 ——
**一条这样的，价值大于 140 条「借 36氪 讲观点」。**

**★★ 判据（任何「我帮你生成了 N 个候选」的产物）：**
> 这 N 个里，有几个是**只有这个用户能产出**的？
> 没有这一列，N 就是虚数 —— 而虚数会让界面显得能干，让人更不去写。

#### C-9 ★★★★ 数据不完整时：显示「待补」，不许算

**配额、进度、达成率这类东西，缺日期 / 缺基数时最容易被"凑"出一个数字。**

```
✓ 本周进度 → 显示「待补」+ 一行说明「补上发布日期后才能算」
✗ 本周进度 → 用文件 mtime 当发布日期算出来，或者直接写 0
```

**★ 指令原话要给死：「宁可显示待补，不要显示一个假数字。进度条撒谎，比空着更糟。」**

**★★ 为什么这条值得单列**：假数字不会被当场发现，但会让人按错的进度做决定 ——
这比功能缺失伤人得多。

#### C-10 ★★★ 判断活落成 md 数据源，指令只负责「读它」

**场景**：用户说「那个工作台里有什么值得借鉴的」「怎么才能写得像我自己」。

**★ 完整方法论不在这里** —— 见 `tool-workflow-audit` §4.7
（什么该搬 / A类不需要新数据的分析 vs B类需要曝光数据的归因 / 开头公式库怎么从已发作品反推 / 偏科分析）。

**本节只讲「写指令时怎么落地」：**

```
① 我产出 → Outputs/drafts/开头公式库.md（或同类：对照表 / 分类表 / 规则表）
② 指令里写死：唯一只读路径 + 「这个文件用户可以手工改，你只读不写，
   也不许把数据复制一份到自己代码里」
③ 断言：解析出的条数必须等于期望值（本次 7 条），否则退出码 1
④ 要求它把「命中规则」原样输出给我 —— 规则是黑箱，用户就不信任推荐
```

**★★★ 一个只有落地时才看得见的坑：公式/规则和诊断必须咬合，否则两边都是摆设。**

```
诊断：素材 87% 是讲述型，只有 13% 是判断型；而用户评论最高的几篇全是判断型
公式：翻案式（「很多人说X。我觉得不全是。」）
→ 咬合点：翻案式就是把「讲述」翻成「判断」的工具
```

**★ 如果只给公式库、不说它治什么病，用户会当成又一份「写作技巧」不打开。**
**★★ 反过来只给诊断、不给工具，你知道「我偏讲述」也不知道怎么改。**

**下发前自检：这条公式/规则，解决的正是诊断里那个数字吗？**

#### C-11 ★★★★ 产物不能持久化时，把限制写在【界面上】，不是写在文档里

**场景（2026-11-14 v4）**：你要给看板加一个「写作区」—— 点选题 → 自动填标题 → 写正文 → 存下来。

**★★★★ 但看板是 `file://` 单文件，浏览器**写不了本地文件**。所以「存下来」这一步物理上做不到。**

**四条路当时摊给你选，你选了最简的 A（复制粘贴）：**

```
A. 写完点「复制全文」→ 自己粘到 Vault 新建的 md    ← 用户选的
B. 点「下载 .md」→ 落到 Downloads → 手动挪
C. File System Access API → 点一次授权文件夹 → 能真写进 Vault
D. 存 localStorage → ★ 绝对不行（第二份数据，必然漂移）
```

**★★★ 关键不是选哪条，是【把限制说出来】：**

```html
<div class="w-warn">
  ⚠ 这一版不自动保存。写完请点「复制全文」，粘到 Vault 里存下来再关页面。
</div>
```

**★★ 指令里必须写死「这句话必须在页面上」，不能只写在 README 里** ——
用户不会读 README，你只会在丢了 800 字之后发现。

**★★★★ localStorage 只能当「防误关」的草稿缓存，且必须标明是临时的：**

```
它存【当前这一篇】，key 固定，换选题会覆盖
页面必须写「临时缓存，刷新可能丢，请及时复制到 Vault」
★ 绝对不许把它当数据源 —— 这是「工作台 13 条 demo 冒充真实进度」的同一类坑
```

**判据（任何「只读数据源 + 可输入区」的页面都适用）：**

```
问一句：用户在这里输入的东西，关掉页面还在吗？
不在 → 界面上必须有一句「会丢」，并给一个明确的「拿走」动作（复制 / 下载）
在   → 它是数据源，那就要问：它是第几份数据？和 Vault 谁权威？
```

**★★★ 泛化的产品判断：一个页面同时做「读」和「写」，就要明确谁是正本。**
本次的答案：**Vault 是正本，页面只是草稿台 —— 所以页面必须主动把内容交出去，而不是等着被保存。**

#### C-12 ★★★★ 产物要「记住状态」时：一个条目一个文件，状态写在 frontmatter

**场景（2026-11-15）**：用户要的不是几个孤立的块，是「素材→选题→写→发→复盘」整条流程。
**流程 = 状态链，每篇内容在某个时刻只在一个状态。**

```
S1 素材 → S2 已定选题 → S3 在写 → S4 待发 → S5 已发 → S6 已复盘
```

**落地方式不是加功能，是加一条文件约定：**

```
Outputs/drafts/内容/YYYY-MM-DD-简称.md
---
title: …
account: <你的公众号>
type: 判断型
view: 我的视角
status: 已定选题          ← 只有这 5 个枚举值
plan_date: 2026-11-18
link: / zan: / cang: / ping:
---
（正文）
```

**看板按 status 分块 → 状态变更 = 改一个词。**

**★★★★ 这是绕开「页面写不了文件」的最省办法**（与 §C-11 同一个限制）：
改一个词的成本远低于「复制整篇再粘回去」，而且这些文件本来就是用户自己要建的。
**顺便符合「Obsidian 是沉淀层」——正本永远是 md，页面只是视图。**

**★★★ 三条硬约束，缺一条这套就散：**

```
① status 只认枚举值。不认识 → 打印文件名 + 实际值，**不许默认成第一个**
   （默认会让状态不明的条目混进排期，比不显示更糟 —— 同 §C-9「宁可待补不给假」）
② 两个数据源合并（新目录 + 旧清单）→ 以新的为准，旧的加「旧」标签
③ 「点按钮改状态」做不到 → 改成「点按钮复制一段改状态的说明」，让用户去改一个字
   ★ 绝对不要用 localStorage 存状态 —— 那又变成第二份数据
```

**★★★★ ④ 「生成默认值」的按钮，必须区分「新增」和「已有」两种情形。**

**这是 v5.1 才被 judge 揪出来的，而且它一定会重演 —— 因为状态链天然要求「一键生成文件头」。**

```
✗ 实测反例：[定这个选题] 永远复制
     status: 已定选题          ← 写死
     plan_date: 今天+3         ← 写死
   → 用户已经把那篇改成「在写」了，再点一次，一粘就把「在写」盖回「已定选题」
   → 状态链被打回起点，而界面上完全看不出发生过这件事

✓ 正解：先判断这条有没有对应文件
     没有文件 → status: 已定选题 + plan_date: 今天+N（默认值只给新建的）
     已有文件 → 一律用文件里的 status / plan_date / account / type / view
     按钮文案也跟着变：「定这个选题」 ↔ 「复制文件头（保留当前状态）」
```

**★★ 判据：「生成默认值」的按钮，问一句「用户可能已经改过这个字段吗？」**
可能改过 → 默认值只能用于「没有旧值」的情况，且文案要明示「保留当前状态」。

**★★★ 泛化：任何「一键填空 / 一键生成模板 / 一键登记」的按钮，都是一次潜在的覆盖写。**
**只读页面上的每一个「复制」按钮，都要问：它复制出去的东西，粘回来会不会盖掉用户的手工修改？**

**★★ 还要准备「两种入口」**，否则流程只对一半：

```
已有草稿 → 直接进 S3（在写）
只有角度 → 从 S1 开始，走「定这个选题」生成文件头
```

**★ 实测反例：用户手上那篇 155 行初稿既不在素材库、也不在发布计划里 ——
如果流程假定「所有内容都从素材开始」，它根本进不来。**

**★★★ 泛化判据：任何「多步骤流程」要落到一个只读页面上，先问三句 ——
状态存在哪？谁是正本？改状态的最小动作是什么？**

**📎 诊断侧（该不该把工具改成状态链、推荐器 vs 排期台怎么分、块和状态怎么对齐）
见 `tool-workflow-audit` §4.8。本节只讲「写指令时怎么落地」。**

#### C-13 ★★★★★ 逻辑里含「今天」的产物，今天的验收证明不了明天

**场景（2026-11-15，v6）**：看板有个排期块，标题「下周排期 · 11-16 ~ 11-22 ｜ 4 篇」。

```python
this_mon = TODAY - timedelta(days=TODAY.weekday())
next_mon = this_mon + timedelta(days=7)
next_sun = next_mon + timedelta(days=6)
start = min([next_mon] + dates)      # ← 用「下周一起」当下限
end   = max([next_sun] + dates)      # ← 用「下周日」当上限
```

**★★ 今天是 11-15（周日），`next_mon` 正好等于最早稿的日期 → 显示完全正确，验收单全绿。**

**★★★ 明天 11-16（周一）打开：**

```
this_mon = 11-16 → next_mon = 11-23 → next_sun = 11-29
start = min([11-23, 11-16, 11-18, 11-18, 11-21]) = 11-16
end   = max([11-29, 11-21]) = 11-29
→ 标题显示「11-16 ~ 11-29」，文字还写着「下周排期」← 11-16 是本周
```

**★★★★ 这不是「今天有 bug」，是「跨周那一刻才有的 bug」。今天的任何测试都测不出来。**

**修法两条，缺一不可：**

```python
# ① 范围只由【实际条目日期】决定，不用任何「周一起 / 周X日」兜底
def range_label(rows):
    dates = [parse(r["date"]) for r in rows if valid(r["date"])]
    if not dates: return ""
    lo, hi = min(dates), max(dates)
    return f"{fmt(lo)}" if lo == hi else f"{fmt(lo)} ~ {fmt(hi)}"
```

```
② 标题去掉所有相对时间词
   ✗ 「下周排期 · 11-16 ~ 11-22」   ← 「下周」是写死的假设
   ✓ 「内容排期 · 11-16 ~ 11-21」   ← 让范围自己说话
```

**★★★★★ 但最重要的是【验收怎么写】—— 这一条必须进验收清单，且写死不许含糊：**

```
□ 把 TODAY 临时设成 <跨周后第一天> 重跑一次，
  标题必须是「内容排期 · 11-16 ~ 11-21」，
  不能是「~ 11-29」，不能出现「下周」二字。
  ★★ 这一项必须实测，不要写「应该正常」。
```

**★★ 为什么必须写「不要写应该正常」**：这类修法看起来「显然对」，
执行方很容易只在今天视角跑一遍就回报「已修复」。**它不会主动去拨时钟 —— 除非你说。**

**该拨哪几个边界（按项目性质挑，至少测前两个）：**

```
① 跨周那一刻：周日 → 周一（最常坏，本次就是）
② 跨月：月末 30/31 → 次月 1
③ 跨年：12-31 → 01-01
④ 闰年：02-28 → 02-29
⑤ 时区：如果有「今天」的判断，00:00 附近的边界
```

**★★★★ 泛化判据（写任何含时间计算的指令前问一句）：**

> 这段逻辑里，「今天」是什么？它的值明天会变吗？
> 会变 → 验收清单必须包含「把今天设成 <边界日> 重跑」。

**★ 同族问题（本次同一批发现的）**：同一天同一个号排了两篇，脚本一声不响。
**「排期」这类产物最怕的不是算错，是算出一个看起来合理、实际做不到的计划** ——
而它不会报错，只会在你照着安排时间那天才发现。**所以排期产物要有冲突检测，且冲突只提示、不擅自改数据。**
