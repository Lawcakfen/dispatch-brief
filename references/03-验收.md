# 验收：执行方交付后怎么核（不采信自报）

> 从 `SKILL.md` 拆出（2026-11-15）。

---

## 0. ★★★★★ 凡逻辑含「今天 / 本周 / 下周 / 最近 N 天」→ 必须拨日期重跑

**2026-11-15 实测的翻车形状：**

```
plan_range_label() 今天（周日）算出来「11-16 ~ 11-22」全对
明天（周一）next_mon 跳到 11-23 → 同一个函数算出「11-16 ~ 11-29」
而标题还写着「下周排期」← 11-16 明明是本周
→ 明天它自己坏，今天的验收单全绿
```

**★★★ 这类 bug 最难受的地方：它不在今天。** 你今天怎么点都对，明天自动错，
而且**最可能错在跨周那一刻（周日→周一）**——也就是你最容易放松的时候。

### 具体做法（已实测通过）

**核心：不动生产文件，拷一份改 `TODAY` 再跑。**

```bash
T=$(mktemp -d)          # 临时目录，跑完删
rm -rf $T && mkdir -p $T && cp build_xxx.py $T/
cd $T && python - <<'PY'
# ★ 这一段只做纯字符串替换、不含反斜杠转义，可以放心用 heredoc
import re
s = open("build_xxx.py", encoding="utf-8").read()
print("原定义:", re.search(r'^TODAY\s*=.*$', s, re.M).group(0))
s = re.sub(r'^TODAY\s*=.*$', 'TODAY = datetime.date(2026, 11, 16)', s, count=1, flags=re.M)
open("build_xxx.py", "w", encoding="utf-8").write(s)
PY
cd $T && python build_xxx.py 2>&1 | grep -E "范围|本周|下周"
```

**★★ 三条纪律：**

```
① 必须拷副本 —— 生产脚本的 TODAY 不许为了测试改掉（改完忘改回是经典事故）
② 拨到真正的边界日，不是随便一天
   跨周 → 拨到下周一（TODAY.weekday() == 0 那天）
   月末 → 拨到次月 1 号
   闰年 → 拨到 2 月 29
③ 断言写成「把 TODAY 设成 X 重跑，输出必须是 Y」
   不要写「应该正常」—— 写「应该」的那一刻，验收就失效了
```

**★★★ 这句话也要写进给执行方的指令**，实测它会照做：

```
□ ★ 明天视角测试：把 TODAY 临时设成 2026-11-16 重跑一次，
   标题范围必须是 11-16 ~ 11-21（不是 11-16 ~ 11-29），且不出现「下周」二字
   ★ 这一项必须实测，不要写「应该正常」
```

**实测效果**：它不但跑了，还自己用 `TODAY=2026-11-16` 起副本验证，
把「范围仍是 11-16 ~ 11-21」逐字贴回来。

### ★★ 连带的设计教训：标题不许带相对时间词

```
✗ 「下周排期 · 11-16 ~ 11-22」   ← 范围是算出来的，词是写死的，两者终会打架
✓ 「内容排期 · 11-16 ~ 11-21」   ← 只写日期范围，让范围自己说话
```

**★★ 而且范围只应该由「实际条目日期的 min/max」决定**——
不要用「下周一起 / 下周日」兜底。兜底会制造一个不在数据里的边界，
今天看着对，只是因为它碰巧等于真实边界。

## 一、核心：不采信自报

**★★★★★ 执行方的回报是【自陈】，不是证据。** 它会写得很详细、很像真的 ——
但「它说解析了 55 条」和「真的是 55 条」是两件事。

### 五个固定动作

```
① 数字自己数 —— 用另一个正则独立数源文件（如 ^## 的个数），不要引用它自检的数字
② 有没有偷写源文件 —— 查 mtime：源文件的修改时间必须早于产物时间
③ 外链独立数 —— img src / link href / script src / a href / url() / @import，逐项必须 0
④ 可重跑性 —— 自己跑一遍，退出码 0，产物能覆盖
⑤ ★★★ 渲染出来的东西能不能【直接用】—— 截图看，别只读代码
```

**★ ①②③④ 验的是「对不对」，⑤ 验的是「能不能用」。**
**前者代码检查就够了，后者只有看着画面才发现。**

### ⑤ 抓出来的三类真实问题（全部通过了 ①②③④，但用户用不了）

**Ⅰ ★★★★ Windows 路径写进 JS 字符串，`\` 被当转义符吃掉**

```js
// 写的时候以为是路径
'…\n文件在 <库根>\Outputs\drafts\发布计划.md'
// 渲染出来
<库根>VaultOutputsdrafts发布计划.md     ← 反斜杠被转义吃掉，用户照着这个找不到文件
```

**★ 修法：JS 字符串里的 Windows 路径一律双写 `\\`，或统一用 `/`。**
**★★ 断言要写「页面上渲染出的路径能直接粘进资源管理器打开」，不是「路径字符串存在」。**

**Ⅱ markdown 字段切分不干净，值前面残留 `**`**

```
源文件：**可以写什么：** 「AI 在你看不见的地方使劲…」
渲染成：** 「AI 在你看不见的地方使劲…」
```

**★ 实测 114 条全中，每条开头多两个星号。** 数据没丢，但满屏噪音。
**★★ 断言：修完后任何字段都不得以 `*` 开头。**

**★★★ 但 v1.1 又补了一层，这条更重要：清完首字符后，中间还有残留，而「数量」会骗你。**

```
w1：断言「首字符不许是 *」→ 通过
w1.1：我查源码 count("**") = 7532，判断「满屏噪音，必须修」
      实际渲染后数 innerText.count("**") = 13   ← 差 500 倍
      那 7532 个大多在 DATA 的 raw 字段里，根本不渲染
```

**★ 所以：**
```
① 数 `**` 一律在【渲染后的 innerText】里数，不要在 HTML 源码里数
② 中间的 `**` 也该清 —— 这是 HTML 纯文本，`**` 不长加粗，只是脏字。
   ★ 我一开始在指令里写「只清首尾、中间保留」，那是 markdown 的思维，
     渲染到网页上是错的
③ 除非真的转成 <strong>，否则全清；工具页里十几处加粗没有价值
```

**Ⅲ ★★★★★ 源字段是「一坨」，指令没写拆分规则**

```
「可以写什么」实际是 300 字里塞了 6 个并列角度：
  ①「AI 在你看不见的地方使劲」…  ②「你想遇见什么样的人」…
  ③「六个陌生人，一桌卡牌」…    ④ 反向写《…》…
→ 卡片标题写「今天写这条」，下面跟了 300 字让你自己挑
→ ★ 等于没替你选，「收敛到 1 条」退化成「给你一坨」
```

**★★ 根因在指令**：只写了「原样搬运」，没写「这个字段可能是多个并列选项」。
**★★★ 泛化：凡是「从长文本里替你选一条」的需求，指令必须写清【拆分规则】**
（按 `；或` / `。或` / `或「` 切分，每个角度算一条独立候选），
并断言「卡片上只能出现一个角度」。

### ★★★★ 验收 DOM 时的坑：脆正则会骗你

从 `--dump-dom` 里用正则提元素，**极易被嵌套标签骗** ——
非贪婪的 `(.*?)</span>` 会先匹配到内层那个 `</span>`，提取结果为空，
看起来就像「元素不存在」。

**实测连续三次误判**（tag 元素「无」、stall 值读错），最后靠截图才确认元素其实在。

```
✗ 拿一个脆正则的空结果当「元素不存在」的结论
✓ 用稳定选择器 / 先把 DOM 片段切出来再解析
✓ 或者直接截图 —— 视觉确认比正则可靠
```

**★ 判据：「代码说没有」和「画面上明明有」冲突时，先怀疑提取方式，再怀疑页面。**

### ★★★★★ 更深一层：验收别人写的脚本，用 `import` 复现它的解析，别自己重写

**我这次又栽了一次，而且方向反了 —— 误报执行方「账号绑错了 4 个」。**

```
✗ 错：从 angleId 往后找 6000 字符内的第一个 "acct"
      angleText 很长（含引文），窗口跨过对象边界 → 抓到的是【下一个角度】的 acct
✓ 对：import 它的模块，调它自己的 parse 函数，复现它的绑定，再拿源映射全量比
```

```python
import importlib.util, sys
spec = importlib.util.spec_from_file_location("bb", r"...\build_board.py")
bb = importlib.util.module_from_spec(spec); sys.modules["bb"] = bb
spec.loader.exec_module(bb)

rows = bb.parse_angles_map(bb.MAP_PATH)          # 它的解析
# …复现它的绑定逻辑…
err = sum(1 for k, v in MAP_PAIRS if angles[int(k)-1]["acct"] != CODE[...])
print(f"150 条里错 {err} 条")                    # → 0
```

**★★ 自己重写一个「我以为它在做什么」的解析，等于在验自己的想象。**
自己重写的解析一旦和它的实现有偏差，你会把「我的正则写错」报成「它的数据错」。

**★★★ 而且抽查不可靠 —— 必须全量比。**
本次：总数对、分布全对（63/43/22/22、68/44/32/28）、抽查 6 个「看起来错 4 个」，
全量比完是 **150 条错 0 条**。

**判据：**
```
总数对 + 分布对 + 全量逐条比对 0 差异   → 通过
只有前两项                              → 不算通过
只有抽查错、全量没错                    → 先怀疑我的验收脚本
```

# 验收标准库 —— 开项目第一件事

> 2026-11-16 建。**每个项目一份，放项目目录下 `_验收标准.md`。**
>
> **★ 这份文件是「项目资产」，不是一次性文档** —— 派单时从对应阶段取标准，交付后按它判断，
> 每批发现盲区就补进去。它长什么样，决定了这个项目能走多远。

---

## 0. 为什么要有它

**没有它的时候，判据散在三个地方：**

```
我脑子里（说过就忘）　→ 每次派单重新想验收清单，想不全
每条指令里（一次性）　→ 上一批的清单，下一批不继承
judge 的 prompt（泛化）→ 只能给「看起来完成了什么」，给不了「做得好不好」
```

**★★ 后果：执行方每批都在猜「这次算不算做好」，而猜的依据是你的措辞，不是标准。**

**★★★ 更具体的后果（2026-11-16 实测）：**

```
v7 的 22 条验收清单全绿，但我扫一眼就发现素材卡标题排版糊了。
那条我没写进清单 —— 它就没报。
**没有标准库，每批的盲区都是随机的。**
```

---

## 1. 什么时候定

**开项目第一件事，在写第一份指令之前。**

**★ 不是「等项目稳定了再定」—— 那时候错误的做法已经变成习惯，改起来更贵。**

**★★ 也不是「先定全部阶段」—— 定当前阶段 + 下一阶段的轮廓就够，后面的边走边补。**

---

## 2. 怎么定（三步，两个人）

### 第一步：我列阶段

**★ 按「改动的性质」分阶段，不按时间分。**

**为什么：按时间分（第一周/第二周）会出现在同一阶段里做三种不同性质的改动，验收标准就散了。**

**例（内容看板实际的分法）：**

```
阶段 1　骨架　　　能打开、数据条数对、零外链
阶段 2　流程　　　状态链完整、块不缺、筛选不撒谎
阶段 3　修细节　　指出的 bug 真修了、跨日期不坏
阶段 4　写回能力　真能改、改了不丢、授权流程通
```

### 第二步：你改

**★ 你会做两件事，这两件事是标准库最有价值的部分：**

```
① 删掉你不认的标准
   —— 有些标准技术上对，但对你没用（比如「代码覆盖率」）

② 加上我没想到的
   —— 你的直觉常常比我的清单准，尤其「用户会怎么误会这块」
```

**★★ 第二步不能省。如果标准库全是我写的，它只是我的偏见的固化。**

### 第三步：每阶段定两组

**必须两组，缺一组就不完整：**

```markdown
**做完的标志**（正向，可勾选）
- [ ] 具体动作 → 具体可观测结果

**不许出现的现象**（负向，比正向更重要）
- 宁可显示「待补」，不许显示假数字
- 不许退回全部（筛选交集为空时）
- 不许改写原文（素材/已发布内容）
```

**★★★ 为什么负向组更重要：正向标准告诉它「该做什么」，负向清单告诉它「不许走哪条捷径」。**

**★★★★ 执行方走捷径的方式是在正向标准之外找空间 —— 你不写负向，它就会找到。**

---

## 3. ★★★★★ 一条硬原则：标准要可观测，不要可评价

**这是最容易写错的地方。**

```
✗ 界面要美观　　　　　　　→ 无法判定，最后变成「看起来还行」
✗ 性能要好　　　　　　　　→ 无法判定
✗ 用户体验流畅　　　　　　→ 无法判定
✗ 代码要清晰　　　　　　　→ 无法判定

✓ 白底深色字、零外链、无阴影、无渐变　　　　→ 可观测
✓ 重跑两次 md5 一致　　　　　　　　　　　　→ 可观测
✓ Ctrl+A 复制文本里没有出现 `**`　　　　　　→ 可观测
✓ 筛选交集为空时显示「这个组合暂时没有」，0 条结果　→ 可观测
```

**★★ 判据：如果一条标准，两个人都看着屏幕却可能给出不同答案，它就不可观测。**

**★★★ 不可观测的标准一律改写或删掉 —— 留着比没有更糟，因为它会制造「检查过了」的假象。**

---

## 4. 文件格式（照填）

**放在项目目录下 `_验收标准.md`：**

```markdown
# 验收标准 · <项目名>

> <日期> 建。<泽哥> 和 <主 Agent> 共同维护，**两边都同意才能改**。
> 执行方（Worker）**只读，不许写这个文件**。

## 阶段 1：<名字>

**范围**：<这一阶段要做什么，一句话>

**做完的标志**
- [ ] …
- [ ] …

**不许出现的现象**
- …
- …

## 阶段 2：<名字>

（同上）

## 变更记录

| 日期 | 改了什么 | 谁提的 | 为什么 |
|---|---|---|---|
| … | … | … | 发现了什么盲区 |
```

**★ 变更记录不能省 —— 它是「这份标准怎么长出来的」的证据。三个月后你会想知道某条标准为什么存在。**

---

## 5. 怎么用（三个接点）

### 接点 1：派单时

**从当前阶段取标准 → 变成指令第六节「验收清单」。**

```
✗ 每批指令重新想 22 条
✓ 从 _验收标准.md 取当前阶段的 → 再补这一批特有的 3–5 条
```

**★★ 补的那几条，来自「这一批改了什么」，不是泛化标准。**

### 接点 2：交付后

**judge 读这个文件 → 按阶段标准判断，而不是泛化地看「像不像做完了」。**

**★★★ 这是验收标准库对 judge 质量提升最大的地方 —— 它终于有了「这个项目什么算好」的锚。**

### 接点 3：发现盲区时

**★★★★ 每批交付后，人扫一眼产物 → 发现清单没覆盖的问题 → 加进「不许出现的现象」。**

**这个循环转三轮，标准库才接近完整。第一版一定不全，别指望。**

---

## 6. ★★ 谁能写这个文件

```
泽哥　　　　✅ 能写（他删标准、加标准）
主 Agent　　✅ 能写（列阶段、整理、写变更记录）
Worker　　　❌ 不许写（只读）
```

**★★★ 必须写进每份指令的边界句里：「不许修改 `_验收标准.md`」。**

**理由跟「不许改队列」一样：标准一旦能被执行方修改，它就会朝「容易通过」的方向漂。**

---

## 7. 什么时候该重写而不是追加

**★★ 出现这三种情况，别在旧标准上打补丁，重写：**

```
① 项目目标变了（不是加功能，是换了要解决的问题）
② 标准之间自相矛盾（说明当初分阶段分错了）
③ 超过 60% 的标准从没被真正验过（说明写得太多，脱离实际）
```

**★ 标准库不是越全越好。一条从没被验过的标准，等于没有，还占位置。**

---

## ★ 一句话

> **没有标准库，每批的盲区都是随机的；有了它，盲区会累积成经验。**
>
> **★ 标准要可观测，不要可评价 —— 两个人都看着屏幕却可能给出不同答案的，一律改写或删掉。**
>
> **★★ 负向清单比正向清单更重要：正向告诉它该做什么，负向告诉它不许走哪条捷径。**
>
> **★★★ 执行方不许写这个文件 —— 标准一旦能被执行方修改，它就会朝「容易通过」的方向漂。**

# 验收判据（acceptance gate）—— 实现细节与沙盒模板

> 对应 SKILL.md §0.11。2026-11-21 落地，当天在真实队列上跑通。
> 目标：把「打勾」从**读 memory 猜语义**（实测假阳性 50%）换成**跑一条命令**（确定性）。

---

## 一、队列里怎么写

```markdown
## ⏳ 待发

- [ ] **11-21** **空本子 v1.1 三件（删排期 / 实时字数 / 翻月）**：按 `WB指令-….md` 整段执行
  - 为什么：这三处用起来硌手 —— 排错的条目删不掉、写作区看不到字数
  - 只改 `空本子.html` 一个文件
  - 验收: grep -c "    ok(" 空本子.html | awk '{exit !($1>=9)}' && grep -q "删周历条目" 空本子.html && grep -q "实时字数" 空本子.html
```

**约定：**

```
· 成对写法：`验收:` 或 `验收：` 都认，前后可有反引号
· 位置：写在条目的续行里（`  - ` 或缩进两格）
· 语义：退出码 0 = 通过（bash 惯例，不要自创）
· 可以写 `&&` 串联多条 —— 失败时会被拆开逐条定位
· 用 bash 语法（grep / test / ls / awk），不要用 cmd.exe 语法
```

## 二、解析与执行（`queue.py`）

```python
def acceptance_of(item):
    """从条目续行里取 `验收:` 判据（全角/半角冒号都认，允许反引号）。"""
    for _, raw in item.get("extra", []):
        m = re.match(r"^\s*[-*]?\s*\**验收\**\s*[:：]\s*(.+)$", raw.strip())
        if m:
            return m.group(1).strip().strip("`").strip()
    return None


def _run_sh(cmd, cwd, timeout):
    bash = shutil.which("bash")
    if bash:                      # ★ Windows 也必须走 bash —— 判据是 bash 语法
        p = subprocess.run([bash, "-lc", cmd], cwd=cwd, timeout=timeout, ...)
    else:
        p = subprocess.run(cmd, shell=True, cwd=cwd, timeout=timeout, ...)
    return p.returncode, (p.stdout or p.stderr)


def run_acceptance(cmd, cwd, timeout=25):
    rc, out = _run_sh(cmd, cwd, timeout)
    if rc == 0:
        return True, (out or "通过")
    # ★ 失败必须指明是哪一条没过，否则详情只有「退出码 1」，对修的人没用
    parts = [p.strip() for p in cmd.split(" && ") if p.strip()]
    if len(parts) > 1:
        for i, part in enumerate(parts, 1):
            prc, pout = _run_sh(part, cwd, timeout)
            if prc != 0:
                return False, "第 %d/%d 条判据未过：`%s`%s" % (i, len(parts), part[:70], pout)
    return False, "退出码 %d；%s" % (rc, out or "无输出")
```

**cwd 一定要传项目目录**（判据里的相对路径都以项目根为基准）。

## 三、扫描结果分三类（`check_queue.scan()`）

```python
{
  "verified": [...],   # 有判据且通过 → 自动打勾（确定性，不用人点）
  "failed":   [...],   # 有判据但没过 → 卡片报「验收未通过」+ 判据 + 输出
  "suspects": [...],   # 没有判据 → 退回 match_done 语义匹配 → 仍只提示、人点确认
}
```

**每条记录的字段：**

```
project / queue / idx / fp（指纹，打勾用） / text / kind
criterion      判据原文（卡片上要显示，人才知道在验什么）
detail         通过时的输出，或「第 N/M 条判据未过：…」
ticked         verified 才有：本轮是否真打勾了
why            仅 suspects：语义匹配的依据（如「标识符重合 9 个」）
```

**★★ 两个关键实现选择：**

```
① 延迟读 memory：只有走语义分支才 recent_memory() —— 有判据的条目根本不需要 memory
② 打勾走「按指纹」不走「按索引」：打完一条，前排索引就变了
```

## 六、沙盒模板（★ 必须三类场景都跑）

```python
root = tempfile.mkdtemp()
proj = os.path.join(root, "样例项目")
os.makedirs(os.path.join(proj, ".workbuddy", "memory"))
# 造一个能被 grep 到的产物
open(os.path.join(proj, "产物.html"), "w").write("<html>function deleteCalItem(){}</html>")
# 队列：三条各代表一条路
#   A 判据能通过   B 判据不通过   C 没有判据（靠 memory 语义）
# memory：给 C 写完成信号，并且要复述任务名（中文短语重合需 ≥4）

r = C.scan(autotick=True)
```

**断言清单（九条，缺一条就是没测全）：**

```
A: 报进 verified / 真被打了勾 / 不在待发里了 / 进了已完成段
B: 报进 failed / 没有被勾 / 带了命令输出（含「退出码」或「第 N/M 条」）
C: 走语义匹配出 hint / 不自动打勾
```

### ★★★★★ 这里有一个必须记住的教训

**第一版测试的 `chk()` 里写了 `global ok`，而 `ok` 是 `main()` 的局部变量 ——
打了 6 个 ✗ 之后，最后仍然打印「结论：全部通过」，退出码 0。**

**修法：用列表收集失败项，结论和退出码都从列表长度算。**

```python
fail = []
def chk(name, cond):
    print("  %s %s" % ("✓" if cond else "✗", name))
    if not cond:
        fail.append(name)
...
return 1 if fail else 0
```

**这条和 `condense()` 那条（注释写「标题全留」，实际硬截）是同一类病：
会自我报告的机制，报告必须是它自己的状态，不是它的愿望。**

## 七、剩余风险与识别法

| 风险 | 表现 | 识别法 |
|---|---|---|
| **判据写太松** | `test -f 文件` 永远通过，等于没有判据 | 把产物换成空文件，它还过吗？ |
| 判据绑定实现细节 | WB 换个函数名就永不通过 | 判据依赖的名字要在指令的「命名契约」里提前约定 |
| 判据超时 | 判据里有 `sleep` / 网络请求 | 默认 25 秒超时；超时报「超时 N 秒」，不要当成不通过 |
| 条目文本过长 | 卡片上文字被截断，看不出是哪条 | `text` 截 70 字，但 `criterion` 要完整显示 |

**★★★★ 判据写太松是这里唯一无法自动防住的错，因为它长得像「通过」。**
**所以卡片上必须同时显示判据原文 —— 让人有机会看出它松。**
