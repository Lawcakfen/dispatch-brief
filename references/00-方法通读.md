# 给执行型 Agent（WorkBuddy / Codex）写工作指令

## 适用场景

你说「**给我出一个指令让 WorkBuddy 来做这个**」「让 Codex 去改」「把这个交给 WB」。

**★ 前提事实（不要每次重新发现）**：本机 **WorkBuddy 无 CLI、无公开 HTTP API**，MCP 是它连 tapnow 的单向通道 → **唯一交付方式是「我写好指令 → 你复制粘贴 → WB 执行」**。

**所以这份指令本身就是交付物。** 它是你手上唯一的操作界面，写糊了你就得来回问。

---

## 0.0 ★★★★★ 适用范围 —— 先读这一节，再决定要不要往下看

**本方案是为「执行方只能人工对接」这个约束设计的。**

**★★★★ 先把「API」这个词说清 —— 不说清，后面全读歪：**

```
这里说的不是「Agent 能不能调用工具」。它当然能，而且每天都在调
（读写文件、跑命令、搜网页，这些都是工具调用，也常被叫成 API）。

说的是【对接方向】的两头都断：
　　你 → 它　不能用程序派活（没有 CLI、没有 HTTP 端点、没有双向 MCP）
　　它 → 你　不能用程序交回结果（不会推事件、不会返结构化返回值）

所以只能复制粘贴。这套方法就是为那种情况写的。
```

```
适用：
· 你在用桌面型、只能人工粘贴的执行 Agent（WorkBuddy / Codex 桌面版 / Cursor 之类）
· 你能写指令、能读代码，但没有办法脚本化地调它
· 你想让「派单 → 盯梢 → 验收」这条链自动跑，但中间那个粘贴动作省不掉

不适用：
· 你的执行方能被程序调用（CLI / HTTP API / 双向 MCP）
· 你只在本地跑代码，不需要「派单」这个动作
· 你想要一个开箱即用的工具（这不是工具，是一套分工方法的记录）
```

**★★★ 抄这套到「能程序调用」的环境，你会得到一个比原来更慢的系统。**

**★★ 为什么：这套里最重的三个设计，全是为了绕开「两头都不能用程序对接」——**

```
① 每 5 分钟轮询（能程序调用就该用 webhook / 回调）
② 人肉复制粘贴（能程序调用就该直接 submit）
③ 让执行方写 memory 文件当汇报（能程序调用就该读结构化返回值）
```

**★ 这三样在人工对接时是唯一可行解，在能程序调用时全是负资产。**

**★ 本文里的 `<工作日志目录>`、`<队列文件名>`、`<库根>` 都是位置约定，不是固定路径。**
**★ 日志目录统一约定为 `<项目>/.agent/memory/`** —— 跟你在用哪个执行方无关，你在指令里让它写这里就行。
（早期版本写的是 `.workbuddy/memory`，仍然会被读到；想改别的名字，配 `agent-config.json` 的 `memory_dir`。）

**★★ 如果你不属于「适用」那一栏，去读 `skill-publishing` 或直接写代码，不要照抄这里的分工方式。**

**★★★ 完整前置条件（工具 5 项 / 目录约定 4 项 / 习惯 4 项 / 成本 / 最小验证路径）见 `README.md` 的「前置条件」一节。**
**如果只想要「怎么写指令」，那节之前就够了 —— 不必上自动验收那套。**

## 0. ★★★★★ 写指令之前，先把需求复述给你确认

**2026-11-14 你把这句写进了需求里：「你先理解，然后复述给我。」**
不是等你问「你怎么看」，是在**给完一段多点需求之后、你动手写指令之前**。

**触发信号（听到就停下，别写指令）：**

```
「你先理解，然后复述给我」
「你先说说你的理解」
「确认一下你懂了没」
```

**★★★ 复述必须【逐条对应你的编号】。**
你常把需求写成「1、2、3」，此时不要重组成「我的理解是……」这种整段 ——
那样你没法逐条打勾，只能整体回一句「对」，信息全丢了。

**正确形态：**

```markdown
## 要求一：<用你的原话概括，不要改写>
我的理解：
① ……
② ……
★ 这一条我理解得对吗？

## 要求二：<…>

## ★ 我还不确定的两处
① 「类型」具体指哪一层？（A 内容形态 / B 素材分类 / C 写作难度）
② 技术前提：写的内容存到哪里？（A 复制 / B 下载 / C 直接写文件）
```

**★★★★ 关键：必须包含「我还不确定的地方」，并给候选选项。**
只复述「我理解的」，你会以为你全懂了；**把不确定摊开，你补一句就齐了。**
本次正是靠这一条，才知道你说的「类型」= 内容形态、「写作」按复制粘贴最简单走。

**★★ 代价对比（本次实测）：**

```
一次复述　　 = 一轮对话
理解偏了动手 = 一整轮返工
（v1→v4 五轮里，两轮返工源于「类型维度选错」和「把示例数据当成真实数据」）
```

**★★★ 复述完要停，不要「复述 + 顺手把指令也写了」** —— 你还要改你的理解，指令就白写。

**★ 并且复述里要主动暴露技术前提**（能不能写本地文件、数据源在哪、哪个文件是活的）。
这些一旦等到你确认完才发现，就得再停一轮。

## 0.1 ★★★★★ 迭代节奏：**连续两轮之后，必须停下来真用一次**

**2026-11-14 一天之内 v1 → v1.1 → v2 → v3 → v4，五次交付、六小时。**
每一轮都更准、更贴近你的真实素材 —— 但到了 v4，**真实使用次数仍然是 0。**

```
board.html     675KB → 1.28MB
build_board.py  26KB → 66KB
标注            150 条账号 + 150 条类型
指令            37KB（4 份）
写过的内容      0 篇
```

**★★★ 这跟你原来那个工作台「7 天 0 产出」是同一个病 —— 只是这次改得更快、更准。**
**本质还是：做工具比用工具舒服。**

**所以定一条规矩：**

```
任何「工具 / 看板 / 工作台」改造，连续两轮之后必须停下来真用一次，
用过才允许继续改。
```

**★★ 理由（实测出来的，不是道理）**：
v2 之后如果你真写过一篇，v3 v4 的改动会准得多 —— 因为下面这些你会当场撞上，
而不是靠我替你想象：

```
· 写作区不保存，我会丢内容
· 「来源」那一大段挡住开头公式
· 类型筛选里「讲述型 1 条」根本点不动
```

**★ 判断「是不是在替用户想象」的自测：**
> 这一批改动的依据，是你用的时候说的一句话，还是我读完代码后的推断？
> 如果最近三轮都是后者 —— 停。

#### ⚠️⚠️ 「看截图提需求」是假信号 —— 它像真实使用，但不是（2026-11-19 实测）

**那天他从头到尾在截图上提需求，18 件。每一件都合理，因为每一件都对应一个真实的视觉观察。**

```
12:45　看截图 → 提 6 处调整 → 月历重做
14:2x　截图再反馈三处 → 删两套筛选器
16:3x　截图 → 「写这个」要预填排期
17:1x　三张截图 → 删偏科块
…
21:4x　第 14 件：配图本地预览
```

**★★★★★ 收工时：写作区空的、待发 0 篇、已发 0 篇、写过的内容 0 篇。**

**判据升级（比原来那条更严）：**

| 依据来源 | 算不算真实使用 | 能发现什么 | 发现不了什么 |
|---|---|---|---|
| 我读代码推断 | ❌ 最弱 | 逻辑错误 | 一切体验问题 |
| **用户看截图反应** | **❌ 假信号** | **排版、区块顺序、显不显眼** | **走不通的路径、缺的步骤、写到一半卡住** |
| **用户真写一篇** | ✅ 唯一算数的 | 以上全部 + 他自己都没预料到的 | — |

**★★ 为什么截图特别容易骗人：它给你一种「我在解决真问题」的踏实感，而且反馈特别快。** 但截图只能暴露「看着不对」，暴露不了「做不下去」—— 后者必须真的下沉到动作里。

**★★★ 所以 §0.1 那条规矩要跟着改：不是「两轮之后」，是「截图驱动的轮次不算真实验证」。**
他连发 18 张截图，等于 18 轮「看」，0 轮「用」。

**★★★★ 怎么把这句说给他听（他接受的说法）：**
> 「今天这 18 件，依据全是『看截图觉得不对』。这不是白做 —— 但有一类问题它永远发现不了：
> 你点进去想写，写到第三步卡住了。**这类只有真的写一篇才露出来。**
> 不用写整篇，写 300 字就行 —— 目的不是产出，是让下一轮的改动有个真实依据。」

**★ 不要说的话**：「你又在做工具不做内容了」。这句话他听过太多次，会直接屏蔽。

**★★ 这条要主动对你说，不要等你发现。**
你自己就是「做产品比做客户舒服」的那个人（你自己说的），
所以这句话不是批评，是**把你的话还给你**。

### ⚠️ 但他不同意「砍小」时，不要争 —— 把「范围」换成「批次」（2026-11-19）

**实战**：我建议把 v8 计划（约 2000 行改动）砍到「只做一件可证伪的事（移走骨架）」。
他的回答是「**1、先不砍骨架，我看做出来是什么样子**」—— **他接受整体改动，只是不要我砍。**

**★ 他的理由成立**：只移走骨架、其余不变，界面看起来还是旧的，他感觉不到差别。
**所以「砍小」不是唯一解，还有一个等价解：不砍，但分批。**

```
第一批 = 能立刻试写的最小组合（骨架挪位 + 定位器 + 复制成文件）
第二批 = 其余（信念卡 / stepper / 整理区）
★ 每批都是能独立打开使用的状态，不是半成品
★ 第一批交完就停，等真实试写反馈；第二批开工前先读 memory 里的反馈
```

**★★★ 判据：用户不接受砍范围时，把「范围」换成「批次」** —— 保住「中途有一次真实验证」，不改他要的功能总量。

**★★ 代价要说清**：分批的唯一损失是「他要多看几次交付」，换回来的是「第一批不对时能立刻定位是哪一块」。
**★★★★ 这一步不要反复劝。** 他拍了板就照做；等第一批交付后拿真实反馈说「现在能判断骨架是不是病因了」，比事前争论有用。

**★ 顺带：给执行方的补充指令里，分批要求必须写在最前面** —— 它读计划时默认目标就是「把阶段一全做完」，
你不写「第一批交完就停」，它会一口气做完四件。

### ★★★★ 上游还在改的时候，只做「不依赖界面的那一半」（2026-11-19）

**他问了一句很实际的话**：「我现在继续改主看板，你先做空本子 —— 会不会影响空本子最后的效果？」

**★★★ 会。所以要把「现在能做的」和「等上游定型的」分开：**

| 现在就能做（跟界面无关，写一次能用很久） | 现在做会白做 |
|---|---|
| 写作法的指令文本 | 界面 / 交互 / 布局 |
| 参数表（字数区间、结构、落点） | 按钮放哪、弹层长什么样 |
| 访谈题目、预设的匹配规则 | 任何依赖上游板块结构的实现 |

**★★★★ 判据：那一天他改了 18 件，全在改同一块界面 —— 那块现在做出来一定返工。**
**但「参数、文案、规则」不是壳，是内容 —— 上游怎么改都不影响。**

**★★ 而且这个安排本身有正面作用**：他改上游的每一处，都在回答「什么样才算好」。
等它定型再做下游，会准得多；现在做，等于用半成品的设计去约束成品。

**★★★ 这条跟他自己定过的规矩是同一句**：「先人工跑通 2–3 周，再整理成需求文档，不要一上来就搭工具。」
**要主动把这句话还给他** —— 他自己说过，所以容易接受。

#### ★★★★★ 但「等 X 定型再做 Y」这个安排，必须当场把「定型」翻译成事件（2026-11-19）

**他的原话：「我继续改主看板，我满意后，测试出一篇文章，然后你再做空本子，对吧？」**

**★★★ 这句话表面上是个时间安排，藏着一个永远不会到期的问题：「我满意」没有判据。**

**实测：同一块看板已经「差不多了」七次 —— v1→v7（七轮 0 篇）→ v8（18 件）→ v9（凌晨重构）。**

**★★★★★ 所以听到「等 X 定稿 / 定型 / 我满意了」时，第一动作不是答应，是问「哪一刻算」：**

```
✗ 「样式看着满意」　　　← 不可证伪，已经来过 N 次
✓ 「我用它写出并发出 1 篇」← 有事件、有日期、能验收
✓ 再加一个日期兜底：到 X 月 X 日不管怎样都动手 —— 谁先到算谁
```

**为什么「发出 1 篇」是对的判据，而不只是「写完 1 篇」：**

```
① 它同时验证了「这个工具能不能用」← 这正是下游（空本子）的前提
② 它自然产生一个截止点，不用靠感觉
③ 它逼他撞到真问题（排版、导出、存档），那些才是要改的
④ 写完不发 = 还停在工具里；发出去了才是真的走通一遍
```

**★ 说给他听的说法（他接受了这个）：**
> 「你上次说『样式差不多了』是在 v7，然后今天又改了 18 件。
> 　建议换成事件：你用主看板写出并发出 1 篇 —— 那一刻就是定型。
> 　再给个日期兜底，谁先到算谁。**日期不是催你，是给这件事一个终点** —— 你自己说过『悬着最耗』。」

**★★ 日期兜底这一半不能省。** 只有事件判据时，如果他一直不发，下游就无限期悬着；
而「悬着」正是他自己点名的最耗状态。**两个判据并联，是这个安排的完整形态。**

**★★★ 判据：任何「等 A 完成再做 B」的承诺，交付前都要能回答「A 完成的那一刻长什么样」。**
答不出来 → 这条承诺实际上等于「不做 B」。

## 0.2 ★★★★ 三个角色的边界，和这个模式的三个结构性隐患

**2026-11-15 你让我总结「Hermes 当主 Agent 管 WB」这个模式。下面是当时给出的答案，直接可复用。**

### 分工（三件不能互换的事）

| 谁 | 干什么 | 为什么只能它干 |
|---|---|---|
| **用户** | 拍板 / 粘贴 / **提供真实数据** | 只有你知道「哪个角度该发哪个号」；也只有在那一头的人才拿得到发布日期 |
| **我** | 判断 / 标注 / 出指令 / 验收 | 执行 Agent 不懂你的业务，标注它做不了（§C-8） |
| **执行 Agent** | 写代码 / 改页面 | 我改不动 1.3MB 的 HTML，也没有回归测试 |

**★★ 一句话内核：把「判断」和「执行」切开，中间用一份书面指令连接。**

### 三个隐患（主动说，不等你发现）

**① 用户是那个人肉接口 —— 这是瓶颈，也是安全阀**

```
WB 不能被程序调用（无 CLI、无 HTTP 端点）→ 每次迭代 = 你复制 + 等待 + 回来告诉我
实测一天 5 轮交付 = 5 个来回 = 6 小时
好处：每一步你都能叫停。坏处：规模上不去。
```
**★ 所以指令必须一次说对** —— 这决定了 §0 复述和 §C-7 数字断言的真正价值。

**② 验收的可靠性全压在我身上，而我一晚上错了 4 次**

```
① 说「对照表只有 131 行」→ 我的脚本被换行撑断（真 bug，我的锅，已修）
② 说「账号绑错 4 个」　　→ 我的正则跨了对象边界
③ 说「标题框是空的」　　→ 我用 textContent 读 <input>，该读 .value
④ 说「队列积了 12 条待发」→ 我用 grep 不分段，真实只有 2 条
```
**★★★ 四次全是我的验证工具不可信，不是它的代码有问题。**
**如果没有独立核对，这四次都会变成「让它去修一个不存在的 bug」。**

**★★ 四次的共同形状（值得背下来）：**
```
我手写一个「轻量版解析」去验它的结果 → 轻量版和真实实现有偏差 → 我把偏差报成它的缺陷
```
**所以固定纪律只有一条：**
```
验数据 → 用它自己的解析函数（import 它的模块）
验数量 → 用它自己的计数（parse_queue / collect_todos），不用 grep
验输入框 → 读 .value，不读 textContent
验文件 → 回读重新解析，不信写的时候的变量
```
→ 判据已经写进验收节：**验别人的东西之前，先验自己的验证器。**

**③ ★★★★ 没人真用过 —— 这是最贵的隐患**

见 §0.1。**它比前两条严重，因为前两条只影响效率，这条影响「改得对不对」。**

```
① 指令长 ≠ 做得慢。v7 424 行 / 15KB → 11 分钟收工。模糊才慢。
② 可勾选的验收清单它会逐条报，连「部分通过」都报 —— 但清单要写成能动手验的动作。
③ ★ 但它不报你没列的东西。22 条全绿，人扫一眼仍能看出排版糊了。
④ 「超过 N 就停，不许凑」救命 —— 防呆要写成【数量阈值 + 禁止动作】。
```

**★★★★ 一句话：指令的质量不在「写得多全」，在「它不用猜、也不会偷偷凑」。**

### 0.6 ★★★★★ 用户把任务分层时，先做方法论层（2026-11-16 你明确要求）

**原话：**

> 「我们这里有两个事情，你要分开处理。
> 1、**更高优化级**，是在你和 wb 工作之间协调的事情，即是我们昨天上传到 github 的 skill，以内容看板为实操案例，修正 skill 的使用方式。
> 2、实际执行中的，以 Hermes 为主 Agent（Router 的角色），wb 为工作 Agent（Worker 的角色）的具体项目推进情况，即是内容看板的改进。」

**★★ 你的分法（记下来，以后你这么说就照这个分）：**

```
第一层 · 协作机制　　怎么派单、怎么盯、怎么验收、队列谁能写
　　　　产物 = skill 本身。项目只是【案例】，案例的作用是给机制提供证据。

第二层 · 项目推进　　某个具体产品的功能、界面、数据
　　　　产物 = 代码。直接改项目文件。
```

**★★★ 为什么必须先做第一层：同一类毛病会在每个项目上重犯一遍。**

实测：那个「队列被外部改了」的坑，先在内容看板撞了一次（08:00 三条互相矛盾的警报），
如果只修项目不修机制，下一个项目还会再撞一次、再查一遍。
**机制修一次，后面每个项目都省一次。**

**★★★★ 三个具体动作：**

```

② 第一层的产物写进 skill 的哪一节，要比第二层的改动先落
③ ★ 第一层做完要【推上去】（GitHub），因为它的读者是未来的自己和别人；
   第二层做完只需跑通，不用发布
```

**★ 判据：如果你在改项目文件，却在心里总结「这条可以复用」—— 停下，先把它写进 skill，再回去改代码。**
否则那个总结会随对话一起消失，而项目文件里留不下它。

### 0.7 ★★★★★ 开项目第一件事：定验收标准（2026-11-16 补）

**→ 详见 `references/03-验收.md`**

```
问题：判据散在三处 —— 我脑子里（说过就忘）、每条指令里（一次性）、judge prompt（泛化）
后果：每批的盲区都是随机的（v7 的 22 条全绿，人扫一眼仍看出排版糊了）
解法：每个项目一份 _验收标准.md，分阶段，你 + 主 Agent 共同维护
```

**三条最要紧的：**

```
① 标准要【可观测】，不要【可评价】
   两个人都看着屏幕却可能给出不同答案的 → 一律改写或删掉

② 负向清单比正向清单重要
   正向说「该做什么」，负向说「不许走哪条捷径」—— 执行方会在正向之外找空间

③ 执行方不许写这个文件
   标准一旦能被它修改，就会朝「容易通过」的方向漂
```

**★ 定的时候是两步，两个人：我列阶段（按改动的性质分，不按时间分）→ 你删你不认的、加我没想到的。**
**第二步不能省 —— 全是我写的标准库，只是我的偏见的固化。**

### 0.9 ★★★★★ 指令的两种投递形态：贴全文 vs 贴一句话指针（2026-11-18）

**执行方跟你在同一台机器、同一个文件系统上 —— 它不只能读你粘进去的文字，也能读你写的文件。**

**所以长指令有两种送法，选错要么白写要么被做错：**

| 形态 | 什么时候用 | 粘给他的是什么 |
|---|---|---|
| **A. 贴全文** | 指令短（< 100 行）、内容全在指令里 | 整份指令 |
| **B. 贴指针** | 指令长、或已有「内容来源唯一 = 某文件」 | **一句话 + 三个防呆** |

**★★★★ 判据：如果指令里有一节是「内容来源唯一：<路径>」，这条指令就该落成文件。**
素材已经在文件里了，再把指令塞进对话框等于同一件事说两遍，而且粘的时候容易漏段。

**✓ 形态 B 的粘贴文本（实测有效，就这么短）：**

```
读 <指令文件的绝对路径>

★ 整份读完再动手，不要只读开头。里面第 1 节是三条硬规矩，第 2 节是内容来源，
第 3 节是结构，第 6 节是验收清单 —— 少读一节就会做错。

做完只写 .agent/memory/YYYY-MM-DD.md，不要动 _给WB.md。
```

**★★★ 三句防呆一句都不能省：**

```
① 「整份读完再动手，不要只读开头」　← 不加它，它读前 30 行就开工
② 「第 N 节是 X」　　　　　　　　 ← 报章节地图，它才知道总共有多少节
③ 「只写 memory，不动队列」　　　　← 标准三句话的第一句，任何形态都要带
```

### ★★★★★ 先分清两份东西：给他看的 vs 给他粘的（2026-11-19 实测）

**那天我写了一轮「六节结构」—— 一句话 / 硬规矩 / 改什么 / 必须改 py / 验收 / 不做 / 回报。**
**用户的回答只有六个字：「所以指令是什么?」**

**★★★★ 他不是没看懂，是我把两样东西混在一份里了。**

| | 给他看的 | 给他粘的 |
|---|---|---|
| **内容** | 为什么这么改、取舍、风险、我的判断 | 只有可执行的那几行 |
| **形态** | 表格 / 对比 / 判断句 | **一个 ``` 代码块，从头到尾** |
| **作用** | 让他决定要不要做 | 他直接全选复制 |
| **长度** | 可以长 | 越短越好 |

**★★★ 判据：他问「所以指令是什么 / 你直接给指令 / 指令呢」—— 是我混了，不是他没耐心。**

**✓ 正确形态：先不超过 5 行的判断，然后一个完整代码块，块里不含任何解释。**

**★★★★ 代码块要能整段复制 —— 不要在块中间插「★ 注意：……」这类说明。**
他会全选复制，块里的每句解释都会跟着飞进 WB 的对话框，让 WB 以为那也是要求。

**★ 说明放块外面，或者干脆不放（他要的往往就是那句改法，不需要理由）。**

**★★ 这条和前两节不冲突：§0.9 讲的是「给 WB 粘什么形态」（全文 vs 指针），**
**这一小节讲的是「给用户的这一轮回复里，解释和指令要不要混」。两个都做到了才算交付完整。**

### ★★★★ 三个文件各管一件事，不要合并

**不要只交文件就完事 —— 建完这三步，cron 立刻能接管：**

**★★ 第二步的 `--init` 最容易忘** —— 忘了它，他粘完指令后第一次扫描会报一堆「产物变了」，全是假警报。

**★★★★ 交付时对他说一句：「粘过去之后 5 分钟内 cron 会报『▶ 动了』，做完自动打勾 + 起验收判断，你不用管。」**
这句话的作用是**让他不用自己盯着** —— 否则他会一直回来问「它做完了吗」。

**★ 反面：如果他要的是「给别人看的一页纸」（回顾页 / 礼物页 / 说明页），指令里必须写一节「这批不做」**，
把「不做多页面 / 不做搜索筛选 / 不接数据源 / 不做动画」列死，并给理由：「这是发给别人看的一页纸，不是产品；功能一多就没人看了。」

## 0.9.5 ★★★★★ 「打勾要不要做」：先按队列长度分级，再决定判据（2026-11-20）

**用户的问法值得记下来：「你认为打勾有没有必要，或者怎样的逻辑不会猜错？」**
这是在问一个产品决策，不是在问实现。答错的方向是直接给技术方案。

### 第一步：先判断「该不该做」

```
队列 1–3 条　　　→ 不需要。他一眼就知道，打勾是多余动作
队列 5–10 条　　 → 开始记不住，需要
队列 10+ 条 + 多项目并行 → 非常需要，否则会重复派单、漏做
```

**★★★ 判据：打勾解决的是「我记得哪条做完了吗」。这个问题只在队列长的时候存在。**
**所以回答前先数一遍真实队列（`parse_queue` 数 `⏳ 待发`），不要凭印象。**
实测那天 34 个项目里只有 2 个有队列、合计 4 条 —— **那时候上打勾，成本大于收益。**

**★★★★ 更要紧的一句（要说给用户）：如果队列长到需要机器打勾，那更该改的是「减少并行」，不是「让机器猜」。**
打勾能管住队列，治不了并行。

### 第二步：要做的话，判据必须是「对 ID」不是「猜语义」

**★★★★★ 唯一能做到零误判的形态：**

```
队列条目：  - [ ] #v9-3 写作区加两个写作法按钮
执行方汇报：## 11:30 #v9-3 已完成
匹配器：    只在「ID 完全相同 且 出现『已完成』」时打勾
```

**这不是「这段文字说的是哪件事」，是「两个 ID 对不对得上」—— 没有歧义。**

**三个代价（必须一起说给用户）：**

```
① 每条任务要编 ID
② 执行方指令模板要加一句「汇报必须带任务 ID」
③ ★ 它会忘 → 那条就漏打勾
```

**★★ 第 ③ 条是真代价，但漏打勾比错打勾好（用户自己定的铁律）。**

**★★★ 所以推荐的落地顺序：先拆队列粒度（一任务一勾，见常见坑那条），再考虑加 ID。**
**只拆粒度不加 ID，误判已经能压到很低 —— 因为「第 1 件的报告」和「第 2 件的条目」标识符本来就对不上。**

### 第三步：回答用户时要说清「派单 / 打勾 / 读进度」是三件事

**用户的误解值得预判 —— 他问过：「不把 README 重写派给 WB 做，那你扫描时还能知道 WB 项目的进度吗？」**

```
_给WB.md（队列）　　→ 你派活给它　　　　← 派单发生在这里
.agent/memory/　→ 它交作业给你　　　← 扫描读的是这里
```

**★★★★ 方向相反，互不依赖。不派单照样能读出进度。**
**证据：那天 prompt 里明写「不许派单」，它照样写出了「v9 重构 B1–B5 全交付（selfcheck 25/25）」—— 那是从 memory 读的。**

**★ 唯一读不到进度的情况：执行方做完没写 memory。**
**该在「给它的指令里」解决（做完必须写 memory），不是靠 cron 派一条「请写 memory」补 —— 那会浪费一轮。**

**★★★ mtime 没变 ≠ 没读进度。** 它只是证明「没写队列」。用户很容易把这两个混成一个，要主动分开讲。

## 0.9.6 ★★★★★ 指令里不要写死会变的数字 —— 写「以当前为准 + 怎么数」（2026-11-20）

**同一个项目，一次核对里四条指令全部过期，全是因为「写指令那一刻的数字」：**

| 指令原文 | 实测 | 后果 |
|---|---|---|
| README 从 v5.1 重写到 **v9** | 看板已经 **v10** | 做完了也是过期的文档 |
| 把 **2 条**未归位角度写成清单 | 实际 **3 条**（L156/L161/L162） | 漏一条，清单不完整 |
| 跑完 selfcheck **仍 25/25** | 早已是 **26/26**（新增了一项） | 验收时对不上，会以为它跑错了 |
| 「数据来源」**114 素材 / 157 角度** | 实际 **58 条 / 163 行** | 写进文档就是假数据 |

**★★★★★ 为什么这比「没打勾」贵得多：**
打勾漏了只是「看板显示不对」，可逆；
**目标版本/条数写错 = 做出来的东西本身是旧的** —— 执行方会老老实实按 v9 写完，
那篇文档从生成那一刻起就是错的，而且**没人会回头重写第二遍**。

**✓ 正确写法：把「值」换成「怎么取值」**

```text
✗ README 从 v5.1 重写到 v9
✓ README 重写到与 board.html 当前版本一致
  （先 grep -oE "v[0-9]+\.[0-9]+" board.html | head -2 确认，不要照抄这条里的数字）

✗ 把 2 条未归位角度写成清单
✓ 把所有未归位角度写成清单（先数：grep '／' <对照表> 的行数），条数以实际为准

✗ 跑完 selfcheck 仍 25/25
✓ 跑完 selfcheck，项数与改动前一致（先跑一次看是多少，不要写死数字）
```

**★★ 判据（派单前 30 秒的小检查）：指令里凡出现 `版本号 / N 条 / N 个 / N 处 / 分数（x/y）`
—— 当场重数一遍，或者改成「以当前状态为准」。**

**★★★ 更根本的一句：队列是「写指令那一刻的快照」，而项目一直在动。**
**所以队列的正确写法是「目标状态」，不是「目标版本号」。**

**★★★★ 而且这条不只约束我 —— 它解释了 §0.4 里 judge 为什么会给出过时建议：
判据读的是「当时的快照」。所有「写下来就不再重算」的东西都会过期，
差别只在于「过期了有没有人发现」。**（→ 让判断能自我暴露过期的做法见
`project-portfolio-monitoring` §3.12 的「两个时间」徽章）

### ★★★★ 顺带更正 §0.9.5：自动打勾的乐观判断被实测推翻

**§0.9.5 写的是「只拆粒度不加 ID，误判已经能压到很低」。2026-11-20 实测：不够。**

```
队列：README 从 v5.1 重写到 v9        ← README 当时还是 v5.1，这件事根本没做
WB 的 memory：到处是「已完成 / 已交付」，且到处提到 README（项目说明天天被引用）
match_done：完成信号 ✓ + 标识符重合 10 个（调到 ≥2 也没用）→ 判「做完了」
```

**★★★★★ 根因不是阈值，是判据缺少「这件事」的语义。** 调阈值只会让它更漏，不会更准。

**★★★ 所以 `match_done` 只能当【怀疑】，不能当【判决】：**

```
判据带语义（「这件事做完了没有」）→ 必须人确认
判据是事实（文件存在 / 校验通过 / 端口能连）→ 才可以全自动
```

**✓ 落地形态：刷新时机器扫一遍 → 卡片上出「⚠ 疑似已完成 [✓ 确认完成]」→ 人点了才写。**
（实现见 `project-portfolio-monitoring` §3.18；纯脚本、零 token，一次刷新多花约 1 秒）

**★★ 而且要主动交代假阳性比例**（那次是 2 条里 1 条，50%），并给期限：
> 「用一周 —— 假阳性超过一半我就收紧判据。」

**★★★★ 不说这句的后果是实的：假阳性多了，用户会开始忽略那条提示，功能等于不存在，
而且比没有更糟 —— 他会以为自己漏看了。**

## 0.10 ★★★★★ 派单分三档 —— 「所有活都进看板」会让流程变慢（2026-11-21）

**用户提过：「以后在 WB 开新的工作区和任务，都由你分派，任务全部进项目看板，你做好 WB 规范，流程会更顺对吧？」**

**★★★ 方向对（单点分派 + 看板监管 + 规范确实减少漏活），但「全部进看板」这条必须改成三档。**
**这是他期待确认的地方 —— 半对的时候要直说哪一半要改，不要顺着答「对」。**

### 三个真实代价（都是实测，不是推演）

```
① 队列会积压，而积压反过来污染判断
   实测：WB 把两件事都做完了，队列还挂着 [ ] → judge 看到「待发 2 条」
        → 建议他「先清队列第一条」→ 让他去做已经做完的事。
   只要「打勾靠人确认」，积压就是必然；队列越长，判断被带偏的概率越高。

② 看板会变成待办清单，噪音淹掉信号
   琐事也进看板 → 8 张卡里 5 张是「改个文案」→ 他就不看卡片了。
   他自己说过「悬着最耗」—— 挂 30 条不动的，比不挂更耗。

③ 主 Agent 成了唯一入口 → 不在场流程就断
   链路：他说 → 我写指令 → 他复制 → 粘给 WB。
   他半夜想改个东西，我在不在？顺畅的流程不该有单点。
```

### 三档分流（判据不是「重要性」，是「做错了代价多大」）

```
档 A｜不问、不进看板 —— 用户直接跟执行方说
     · 一句话能说清、当天能完、不需要验收
     · 例：改个文案、调个间距、「这个按钮挪左边」
     · ★ 判据：做错了的损失 < 走一遍流程的时间

档 B｜进看板，主 Agent 写指令
     · 跨天 / 多步 / 要验收 / 会改数据结构
     · 例：空本子 v1.1 三件、小程序接线、开新工作区
     · ★ 判据：做错了要返工，或者三天后他自己会忘记当初要什么

档 C｜先聊，再定进不进
     · 会改方向、会新增项目、会动别人的东西
     · 例：要不要做微信小店、要不要接 B 端
```

**★★★★ 档 A 放权，档 B 上流程，档 C 先想清楚 —— 这样看板里只剩真正会悬着的事。**
**★★ 反过来的自测：如果某个项目在看板上挂了 3 周没人动，它当初就该进档 A 或档 C，不该进档 B。**

### 他问「这样更顺对吧」时的答法

```
✓ 先给半对的结论：「方向对，但『全部进看板』要改成三档」
✓ 每个反对点都带实测证据（积压→判断被带偏那次）
✓ 最后给可执行的替代方案（三档表 + 判断依据）
✗ 不要顺着说「对」—— 他问的是设计，需要的是把坑先说出来
✗ 也不要只说「不对」—— 前两句必须先承认哪部分成立
```

**★ 一句话内核：看板管的是「会被忘记、会悬着的事」，不是「所有事」。**

### ★★★★ 配套：立项即建 `<队列文件名>`，不是「有活才建」

**2026-11-21 实测：空本子能被看板监管，唯一原因是它有了 `_给WB.md`。**
**没这个文件的项目，在扫描里等于「没队列、看不到活」，卡片也上不去。**

```
✓ 新项目第一动作：mkdir .agent/memory + 建 _给WB.md（四段：⏳ 待发 / ⏸ 已被取代 / ✅ 已完成 / 数据源）
✓ 建完立刻验证：python -c "import queue as Q; print(Q.parse_queue('<队列路径>'))"
✗ 不要等「有活要派」才建 —— 那时已经晚了，中间这段进度全在盲区
```

**★★ 顺带：`⏸ 已被取代` 这一段不能省（见常见坑里「整批条目不要留在 ✅ 已完成」那条）。**

### ★★★★★ 建议的「对象」：只谈事情和项目，不评价他的行为方式（2026-11-21 明确纠正）

**他的原话：**

> 「我想在这件事上，你给的建议先专注在事情和项目上，而不是我的行为方式上，如果非要两者都谈，就分开两个角度来。」

**★★★ 当时我给了五条建议，其中两条是这样的：**

```
「给这套监管体系设时间预算，超了就砍项目」
「把 18 个停滞项目一次清掉：真死 / 暂停 / 要重启」
```

**这两条讲的是「他该怎么做」，不是「系统该怎么设计」。他当场把这个区别指出来了。**

**判据（给建议前自问一句）：**

```
这条建议改的是【东西】还是【人】？
  改东西（看板怎么算、队列什么格式、判据怎么写、脚本改哪）→ 直接说
  改人（他该少做什么、什么该先做、时间怎么花）→ 除非他问，否则别说
```

**★★ 「专注事情和项目」不等于「不提风险」。** 同一次对话里我还说了「判据写太松会错打勾，比语义猜更隐蔽」——
那是项目风险，他没反对。**被拒绝的是「把他的行动节奏当建议内容」。**

**★★★★ 两者都谈时必须分开两节、各自带标题，不要混在一段里：**

```
## 关于这个工作流
（设计层面的问题、改法、代价）

## 另外，关于节奏
（单独一节，明确标注这是另一个层面）
```

**★★★★★ 为什么这条值得写进 skill（实证）：**
被纠正之后，我把同样的内容剥掉行为层、只留设计层重写了一遍 ——
**他立刻回「好，按步骤做，每做完一步检查并汇报一次」。**
同一批建议，从「被反驳」变成「被采纳」，差别只在建议的对象。

**★ 我为什么会滑过去：** 项目停滞、当天 0 产出，这些是真实观察，看着像「该说」。
**但他自己比谁都清楚**（「做工具比用工具舒服」是他自己说的，§0.1 记着）。
再说一遍没有信息增量，只有立场表态。
**判据：如果这句话他自己已经说过，就不要再作为建议提出来。**

## 0.11 ★★★★★ 验收判据：把「打勾」从猜语义变成跑命令（2026-11-21 落地）

**§0.9.6 结尾那条原则（「判据带语义→必须人确认；判据是事实→才可以全自动」）这一节给了它的实现。**

**改法：队列条目里多写一行 `验收:`，内容是一条能跑的 shell 命令，退出码 0 = 通过。**

```markdown
- [ ] **11-21** **空本子 v1.1 三件（删排期 / 实时字数 / 翻月）**：按 `WB指令-….md` 整段执行
  - 这行为什么要做…
  - 验收: grep -c "    ok(" 空本子.html | awk '{exit !($1>=9)}' && grep -q "删周历条目" 空本子.html
```

**跑起来是两条独立的路，不要混：**

```
有条目带 验收:  → 跑命令
                   通过 → 自动打勾（确定性，不需要人点）
                   不通过 → 卡片报「✗ 验收未通过」+ 是哪一条没过
没有 验收:      → 退回 match_done 语义匹配 → 仍然只提示、人点确认（假阳性 50% 那条路）
```

**★★★ 为什么值得做：这一步同时解决了三个老问题** ——
假阳性 50%、每条都要人点确认、「没做」和「做错」分不清（现在失败会带命令输出）。

### 三条实施细节（都踩过）

```
① 判据要用 bash 跑（grep/ls/test/&&），不要用 cmd.exe —— Windows 上先 shutil.which("bash")
② 失败时必须拆开定位：把 cmd 按 " && " 切开逐条跑，报「第 2/4 条判据未过：`<那句>`」
   否则详情只有「退出码 1」，对修的人没用
③ 打勾走「按指纹」不走「按索引」—— 打完一条前排索引就变了
```

### ★★★★ 副作用（这条比机制本身更重要）

**判据必须在派单那一刻就写得出来 → 写不出判据，说明我自己也没想清「什么算做完」。**

**所以现在的派单方式变了：指令里要加一节「自检项命名契约」，把判据依赖的名字提前约定：**

```markdown
## 自检项命名契约（这条决定了能不能被机器验收）
闸门会跑：grep -c "    ok(" 文件.html | awk '{exit !($1>=9)}' && grep -q "删周历条目" 文件.html …
所以你要：给每件活加一条自检，名字里必须出现「删周历条目 / 实时字数 / 翻月」三个词
★★ 判断要真的能失败（不许写 ok('翻月能跳月份', true, '') 这种）
```

**★★★★ 判据依赖实现细节时，就把命名写进契约 —— 宁可提前约定一个名字，也不要事后靠猜。**

### 一个仍然存在的风险：判据写太松

**`验收: test -f 空本子.html` 永远通过，等于没有判据 —— 而且比语义猜更隐蔽，因为它看起来是确定的。**

**未解的两道防线：**
```
① 失败时指出「第 N/M 条没过」→ 松判据会立刻暴露成「一跑就过」
② 指令里明写「判断要真的能失败」
```
**★★ 但这两条都防不住我自己偷懒写松判据。可疑判据的识别法：把产物换成空文件，它还过吗？**

### ★★★★★ 顺带一条：验证脚本会撒谎，而且我这次真撞上了

**`test_acceptance.py` 第一版用 `global ok` 收集断言结果，但 `ok` 是 `main()` 的局部变量 ——
打了 6 个 ✗ 之后，最后仍然打印「结论：全部通过」，退出码 0。**

**★★★ 这跟「condense 注释写着『标题全留』但实际硬截」是同一类病：会自我报告的机制，报告必须是它自己的状态，不是它的愿望。**

```
✓ 用列表收集失败项（fail.append(name)），结论和退出码都从列表长度算
✓ 沙盒必须三类场景都跑：该响的（判据过）/ 该静的（判据不过）/ 该退回另一条路的（无判据）
✗ 只跑「真做完」一个场景，测不出误报
```

**★★★ 同一趟还撞了第二个：`python test.py | sed ...; echo $?` —— `$?` 取到的是 `sed` 的退出码，不是 python 的。**
测试明明 1 项失败，界面照样显示「退出码 0」。
**✓ 修法：先落文件再读码 —— `python test.py > /tmp/o.txt 2>&1; RC=$?; sed ... /tmp/o.txt; echo $RC`。**
**判据：任何「跑完看退出码」的检查，先确认那个退出码属于被测程序，不属于管道下游。**

**★★★★ 判据：沙盒测试要断言「不该发生的没发生」，只断言「该发生的发生了」等于没测误报面。**

**→ 完整实现与可复用的沙盒模板见 `references/03-验收.md`**

## 0.12 ★★★★★ 看板侧三件改造：状态字段 / 异常区 / 「闭环不是分支」（2026-11-21）

**§0.11 解决「派出去怎么收」，这一节解决「收回来怎么显示」。**

### ① 状态字段显式化 —— judge 只填枚举，不写散文

```yaml
stage: 开发中      # 只有五个值：未开始 / 开发中 / 待验收 / 已完成 / 暂停
next: 一个具体动作
blocker: 无
criterion: 怎么算做完（要可观测）
```

**★ 存 json 侧车（如 `_看板/pstate.json`），不写进日志 md** —— 日志是「只追加」，状态是「每次覆盖」，合在一起会互相破坏。
**★ stage 必须在枚举里，不合法就整条拒绝**：宁可不写状态，也不写个假状态 —— 假状态会被卡片当成事实显示，比没有更难发现。

**★★ 两个实测坑：**

```
· 兜底值一旦好写，模型就一定用兜底：
  「判断不了就写开发中」→ 6 个项目全填「开发中」，字段等于没写。
  改成五步判断题（做完等人看→待验收 / 明确不做了→暂停 / 验收过→已完成 / 还在改→开发中 / 没动过→未开始），
  分布才从 6×开发中 变成 5+1。
· 截断凭感觉：criterion 截到 80 字，真数据写出来是「…可点击、不出现」「renderSlotRef() 首行 r」——
  断句的判据比没有更糟，它看着像结论，其实是残句。改到 160，实测最长 119。
```

### ② 异常区 —— 只放纯脚本能算的，且「没在办 ≠ 异常」

```
优先级 1  队列挂了 >12 小时没动静      ← 派下去了、执行方可能没读到指令（★★ 2026-11-22 新增）
优先级 1  停滞 >14 天 且 队列还有活     ← 有活、没人做（最该看）
优先级 2  队列挂了 >72 小时没动        ← 派下去了、没回音
优先级 3  判断 >26 小时没更新          ← 话是旧的
共同前提：只有【队列里还有待发】的项目才判定
阈值可配：queue_warn_h（默认 12）/ queue_bad_h（默认 72），单位小时
```

**★★★★ 为什么加「>12 小时」这一档（2026-11-22 实测）：原来只有 72 小时一档，于是「昨晚派下去、今天还没开工」的项目一天之内根本不出现在看板上 —— 而它恰恰是最该被看见的。**
```
那天早上问「为什么看板上没有空本子这个项目」——
翻出来它掉进了夹缝：
  卡片区  不收（24 小时没有产出文件变动）
  异常区  不收（队列挂了 8 小时 < 72 小时）
  → 一个「派了但没动」的项目，在看板上等于不存在
★ 修法不是给它编一张「进展卡」（没进展硬编「现在到哪/建议」更假），
  而是让异常区把「刚派下去就没动静」当第一优先级报出来。
```

**★★★★ 共同前提是关键取舍：34 个项目里 19 个停滞，全报就是 19 条噪音，异常区等于没有。**
没有待发的项目不进异常区 —— 那是「没在办」，不是「出问题」。要「所有停了的都看见」，另做一个「停滞榜」，别混进来。

**★★★ 判定逻辑必须抽成纯函数（`compute_anomalies(scan, judge_times, now)`）才能单测** ——
埋在渲染函数里，「无异常」和「停滞」这两个分支写反了不报错，只是永远不响。

### ③ 「缓解办法」必须落到动作上 —— 闭环不是分支

**我提过一个缓解：「主 SKILL.md 开篇写对照表，让人知道翻哪份（派活 / 看全局）」。他回：「是哪两种情况？」**

**★★★ 两个问题：**

```
① 我写了「两种情况」却没把名字列出来 —— 量词替身被当成已解释
② 那个办法本身不成立：真实使用不是二选一，是闭环
   派活 → 盯 → 验收 → 打勾 → 看全局 → 再派活
   用户不会先停下来分类，他顺着走。
```

**✓ 改成：主文件写【闭环主干】，每一步末尾指路（该翻哪份 references）。**
**★★★ 判据：任何产品化建议，先问「用户在这个位置上会做什么动作」；答不出动作，这条建议就是纸上的。**

### ④ 「本周三件」从队列自动抽 —— 消灭第二个真相（2026-11-21）

**病灶：同一件事有三个手写/自动来源，必然漂移。**

```
聚焦页手写「本周节奏」 说：本周做 A、B、C
各项目队列手写         说：待发 X、Y
看板自动              说：项目在做什么
实测：聚焦页停在 10-25，26 天没动，而他实际在做的是内容看板
```

**★ 修法：把「本周三件」并进队列 —— 页面顶部三条 = 各项目 `_给WB.md` 的最前一条待发。**
**排序只用可解释的规则：先按三层（①→②→③，项目名去 `@后缀`/「示例的」前缀后与该层内容做双向包含匹配），同层内队列挂得越久越靠前。**
**手写只保留「顺序理由」——那一句不是从队列能推出来的。**

**★★★★ 改完立刻暴露一件事，这是这一步最大的价值：**

```
自动抽只抽到 2 条，0 条来自①层。
因为①层的活（例：登后台点提交）是人工动作，派给执行方没用 → 队列里没有它。
手写三件 = 应该做什么
自动三件 = 已经派出去的活
```

**★★★ 处理方式是加一个显式警告块，不是把缺的那条硬塞进列表：**

```
⚠ ①层（收入线）没有任何队列 —— 上面三件里没有一条来自 ①。
   这不是抽错了：「自动抽」只抽已经派出去的活；①层的活常常是人工动作。
   ①层缺位这件事本身，比这三件更该看。
```

**★★★★ 判据：自动视图暴露了「该有但没有」的东西时，加警告，不要补数据。**
补数据等于把自动视图又改回手写，漂移问题原样回来。

**★★ 另一个实测细节：卡片标题要按「：」断句，不要硬切字数** ——
第一版切 64 字，切出「…md 整」这种残句。任务名通常在冒号前，在冒号处断最自然；没有冒号才切 46 字加省略号。
（和上文 criterion 截 80 字断在半句是同一条：**断句的字段比没有更糟，它看着像结论。**）

## 常见坑

| 坑 | 表现 | 修法 |
|---|---|---|
| **让它「整理资料」** | 交出很顺但内容对不上的东西 | 写死唯一来源 + 不许编细则 |
| **只给正面要求** | 做出「高级感」而非「能读」 | 加禁止清单 + 理由 |
| **给时间自由** | 「20 分钟或 2 小时都行」→ 随便准备 | 给一个具体形状（「十来分钟，三件事」）|
| **多文件交付** | 你没法一次粘完、也测不了 | 砍到单文件单路径 |
| **没写「出错怎么办」** | 缺的地方它自己补 | 明写「留空 + 灰字待补，不许补」|
| **指令里混进内部判断** | 把「谁没发言」「占了 59%」这类带进对外产物 | 交付物口径要先分清对内/对外 |
| **从界面推断数据状态** | 看着「已发 8」就去改界面，实际全是 demo 数据 | 先打印 DB / JSON 看真实条数和 demo 标记，见 §C-0 |
| **改错文件**（AI 生成的工具常有同名副本） | 改了 `.js`，但 HTML 是自包含的 → 不生效，还回报「已完成」 | 先比对两边函数集合 + 查 `<script src>`，见 §C-1 |
| **让它「删掉」一个区块** | 别处还在调 → 整页 JS 崩，报错位置离改动很远 | 停用不删除：`return;` + `display:none`，见 §C-3 |
| **清单里没有回归项** | 新功能好了，别的页面被弄坏 | 验收清单末尾写「另外 N 页与改之前完全一样」，见 §C-4 |
| **把执行方的自报当验收结论** | 它写「已解析 55 条，一致」，你照着回报就回「验收通过」 | 自己用另一个正则数一遍 + 查 mtime + 独立数外链，见「验收」节 |
| **源字段是一坨、含多个并列选项** | 指令写「原样搬运」，「替你选一条」变成「给你一坨」 | 指令里写清拆分规则 + 断言「卡片只出现一个角度」，见验收节 Ⅲ |
| **只做代码层验收** | 数字全对、断网可用，但路径渲染成一串没反斜杠的字，用户打不开 | 必须截图看渲染结果，见验收节 ⑤ |
| **把数字断言当验收终点** | 它报「解析 150 行，一致」，其实文件只有 131 行有效 | 断言只挡数量级；分布 + 全量比对自己再做一遍，见 §C-7 上限 |
| **自己重写解析去验收** | 正则跨对象，把「我的脚本写错」报成「它的数据错」，冤枉它返工一轮 | `import` 它的模块复现解析；抽查错先怀疑自己，见验收节「更深一层」 |
| **生成的 md 表格没回读** | 内容带换行把表格撑断，150 行变 131 行，19 条静默丢失 | 写完回读断言行数 + 编号连续，见 §C-8 |
| **「上次那个 X」直接开答** | 用户说「上次那个公用模板」，我答了 A（项目看板），你实际指 B（自媒体工作台），整段建议作废 | 上下文里有多个同类物时，先一句确认「你指的是 A 还是 B」再展开 |
| **关键词判据被第三人称骗** | `has_self` 匹配「自己」→「你自己写的那一版」被当成第一人称 → 推荐了不合适的开头公式 | 判据要排掉「你自己/你自己/自我」；代词前一个字是「你/你/别」时不算第一人称 |
| **同分同日期条目霸占所有推荐** | 一条素材的 6 个角度都是最高分且同日 → 四个号的「今天写这条」全是它，「换一条」在同素材里打转 | 排序加约束：同一母素材最多出 N 条；「换一条」优先跨素材 |
| **排「本周计划」不先算今天周几** | 周六问「本周计划该开始吗」，本周只剩 1 天，排出来立刻过期 | 排周期计划前先算剩余天数；剩不到 2 天就排下周，并明说为什么 |
| **分类不先跑分布就做筛选按钮** | 6 类跑出 93/1/8/15/31/16，讲述型 1 条也要占个按钮 | 先只打印分布、不写文件；某类 < 5% 就合并或换维度，见 §C-8b |
| **验收用 textContent 读输入框** | 标题框「看起来是空的」，实际有值 → 冤枉它返工 | `<input>`/`<textarea>` 读 `.value`；块标题用 `(.*?)`+去标签，别用 `[^<]`，见 tool-workflow-audit 参考 §5.5 |
| **连改三轮，用户一次没用过** | v1→v4 六小时，board 从 675KB 到 1.28MB，写过的内容 0 篇 —— 跟工作台「7 天 0 产出」同一个病 | 连续两轮后停下来真用一次；自测「这批依据是你说的还是我推断的」，见 §0.1 |
| **产物写不进文件，但界面上不说** | 用户在写作区写了 800 字，关页面全丢，才发现「这一版不自动保存」 | 限制写在界面上（`⚠ 这一版不自动保存`），不是写在 README；localStorage 只当防误关缓存，见 §C-11 |
| **用 grep 数队列条数** | `grep -c "^- \[ \]"` 不分段，把「等外部」段的复选框也算成待发 → 11 条虚报，还据此给用户发了错误警告 | 只用 `parse_queue(qpath)["items"]` 计数；`⏳ 待发` / `⏸ 等外部` 两段约定要守，但「分没分段」也用解析器确认，见 §0.3 |
| **监测类改动没沙盒跑全状态** | init 提前设标记 → 静默；hash 没回写 → 重复报。上线后才发现 | 沙盒把「该响的」和「该静的」各跑一遍（6–7 项）再上，见 §0.3 |
| **「上次那个 X」指的是哪个 X 没确认就开答** | 用户说「上次那个公用模板」，我答了项目看板，你实际指自媒体工作台，整段建议作废 | 上下文里有多个同类物时，一句话确认再展开 |
| **自动判断给「通过/不通过」结论** | 自动化后没人复核，一次误报就直接推给用户；而我人工核时一晚误报过 4 次 | judge 只给三段事实（完成了什么 / 你该核哪几点 / 下一步），结论权留人，见 §0.4 |
| **用高频 agent cron 做监测** | 每 15 分钟起一次 agent，30 次空跑里只有 1 次有事，token 全白烧 | `no_agent` 快路（token=0）+ 事件触发才 subprocess 调 `hermes -z`，见 §0.4 |
| **监测说要"针对某个文件夹"就真去建 N 个 cron** | 维护成本随项目数线性增长，且大部分时间都在空转 | 一个全局 cron 扫所有队列即可，逻辑等价，见 §0.4 |
| **流程要落到只读页面，却没定状态存哪** | 素材/选题/写作/发布各自为政，中间断环，用户还得自己记到哪一步 | 一个条目一个 md，status 写 frontmatter，改一个词就换块，见 §C-12 |
| **只支持「从素材开始」一种入口** | 用户手上已有半成品稿件（155 行初稿），既不在素材库也不在排期表，流程进不去 | 留两个入口：已有草稿→直接进"在写"；只有角度→走"定这个选题"，见 §C-12 |
| **一键生成的默认值覆盖用户已改的状态** | 「定这个选题」永远复制 `status: 已定选题`，用户改到「在写」后再点一次，粘回去被打回起点，界面看不出发生过 | 有文件 → 一律用文件里的字段；按钮文案区分「新建 / 已有」，见 §C-12 ④ |
| **同一页出现两个同名时间范围** | 四个号块「本周 11-09~11-15」、铺排块「本周 11-16~11-22」—— 各自逻辑都对，用户看着像打架 | 加限定词分开口径：「本周配额」/「下周排期」；或只写日期范围不写「本周」 |
| **模板变量没替换就上线** | 类型筛选第一个按钮渲染成 `all 150`，其余都是「判断型 93」这类中文 | 验收清单加一条「逐个念一遍按钮文案」；纯英文/占位符混在中文列表里最扎眼 |
| **用户说「继续推进」就先去问你做到哪了** | 你经常不主动报状态（有时连「wb 做完了」都不说），问一句就白等一轮 | 先查三处再开口：产物 mtime、队列（用 `parse_queue`，不用 grep）、`<工作日志目录>` 最新日期。查到了就直接进验收 |
| **执行方自己把队列打了勾** | cron 每 15 分钟全静默，看起来像「队列空，正常」，其实是它抢在监听器前面改了状态文件 → 自动验收一次都没跑过 | 看 ✅ 那条的续行：是原指令 → tick_item 打的；是 ①②③ 报告 → 它自己改的。指令里写死「只写 memory、不许动队列」，再加 state diff 检测，见 §0.3.1 |
| **子进程只给相对路径** | judge 说「找不到项目目录、全盘搜索无结果、文件我一个都没读过」，只能靠时间戳和时间猜 | 每个文件给绝对路径 + 单列「项目绝对路径」+ 明写「你有工具，请真的去读」；改完 190s→104s 且质量更高，见 §0.4 |
| **用 bash heredoc 写含转义的 Python** | `python - <<'PY'` 里的 `\n` / `\s` 被吃成真换行或 `/s` → 字符串未闭合 SyntaxError、正则静默失效。**2026-11-16 在「已经记着这条坑」的情况下又踩三次**（脱敏、拆分、改名脚本各一次）→ 说明「记住」不够，要改成默认动作 | **默认动作：脚本里只要可能出现反斜杠 / 正则 / `re.sub` / 多行字符串 → 第一动作就是 `write_file` 落成 .py，再 `python xxx.py`。不要先拿 heredoc 试，试错再改比一开始就写文件慢。**<br>只有「一行、且不含任何转义」时才允许内联。<br>实在要内联：换行 `chr(10)`、反斜杠 `chr(92)`、正则用 `[ ]` 代替 `\s` |
| **★★★★ 同上，但触发条件宽得多：`python -c` 里含中文标点也会被整条 BLOCKED** | 2026-11-18 实测：想用 `python -c "..."` 把一个 md 里的中文句子做字符串替换（文本含 `「」` 全角引号、`·` 间隔号），命令直接被判 `BLOCKED (hardline): malformed executable payload`。**它不是报语法错，是整个命令被拦下**，看起来像环境坏了 | **判据：内联 Python 里只要出现中文标点（「」『』。、·）或多行中文 → 直接 `write_file` 落成 .py 再跑，不要试。**<br>★ 这条和上一条是同一个默认动作的两个触发条件 —— **「要不要内联」的答案默认是「不要」**。<br>★★ 这个拦法会**额外浪费一轮**：你会以为是自己引号没配对，改半天才发现是解析器拦截。<br>★★★ 反过来是好事：`write_file` 版本天然能「改完回读验证」（本次就是靠它顺手断言了行数/双 CR/关键字段都在）—— 内联做不到这个收尾 |
| **指令里那句「做完请写 X」写成了通用话** | 「简单记录一下」→ 它写「已完成按钮改色」，跟指令措辞重合不足 4 → 完成信号有、但匹配不上 → 该打勾的不打勾，静默 | 那句话里塞进【指令自己的关键词】（任务名+动作+参数）；漏打勾先查它的措辞，别急着调阈值，见 §0.3.2 |
| **沙盒多场景用例不连贯** | 上一场景的条目被下一场景覆盖 → 检测器正确报「外部修改」，我当成 bug 去查代码 | 每场景保留上场景条目，只增不改；出现「意外报警」先回看自己上一场景写了什么，见 §0.3 bug ⑤ |
| **基线和变更撞在一起** | 「记住上次状态 → 报差异」的机制，如果本轮自己也会改这个状态，基线就记成了改前的样子 → 下一轮把自改为报成外部变更 | 基线必须在「本轮所有自己的写操作结束之后」重新读取写入 |
| **用户要「可视的 HTML」，交了一张文档** | 满屏抽象描述（「会通知你」）、坑只写「已优化」、定时器画成旁边一个小方块、结尾不说用户要做什么 | ① 定时器/监听器画在流程**中间**（它是链上一环，不是外部工具）② 每种输出贴**真实推送原文**，不许编 ③ 每个坑写**代价**不写「已修复」④ 最后一节必须回答「用户还剩哪几个动作」，见 §0.2.1 + `templates/mechanism-diagram.html` |
| **日期相关的逻辑，用今天验收** | `plan_range_label` 今天算出来「11-16 ~ 11-22」全对；明天（周一）`next_mon` 跳到 11-23，同一个函数算出「11-16 ~ 11-29」，标题还写着「下周排期」→ **明天它自己坏，今天的验收单全绿** | ★ 凡逻辑含「今天/本周/下周/最近 N 天」的输出，验收必须**把 TODAY 拨到边界日重跑**：跨周那一刻（周日→周一）、月末、闰年。断言要写成「把 TODAY 设成 X 重跑，标题必须是 Y」，并写死「这一项必须实测，不要写应该正常」，见 `references/03-验收.md` §0（含可跑的副本改法） |
| **相对时间词写进标题** | 排期块标题写「下周排期 · 11-16 ~ 11-22」，而范围是按「今天算的下周一」推的 —— 今天两句话碰巧一致，跨周就自相矛盾 | 标题不带「本周/下周/这月」这类相对词，只写「内容排期 · <最早> ~ <最晚>」，让范围自己说话；范围只由**实际条目日期**决定，不用任何「周一起」兜底 |
| **排期块不做冲突检测** | 排期显示「4 篇」，其中两条是 `11-18 ｜ 公众号 ｜ A` 和 `11-18 ｜ 公众号 ｜ B` —— **同一天同一个号发两篇，实际做不到**。脚本完全不管，用户照着假排期安排时间 | 加 `find_conflicts()`：按 `(日期, 平台)` 分组，≥2 条就出一条提示条（只提示，**不删不改数据** —— 改哪篇是用户的内容决策）。★ 类比：任何「按槽位排东西」的视图都可能静默重叠，日历/房间/人力排班同理 |
| **一个会说假话的排期，比没有排期更糟** | 「4 篇」里有 2 篇发不出去；「11-16 ~ 11-29」跨到了下下周却写着「下周」 | 排期类界面的验收标准不是「有没有显示」，是「用户能不能照着它安排时间」。**照它做会撞车的，就别显示成能做的** |
| **用户一次提 5 个问题，就照单全做** | 5 条听着都要修，实际只有 3 类根因（数据源缺 / 写不回文件 / 信息架构乱）。照单全做 → 改动面过大、哪层都没真跑通，而且多数条目根本轮不到 | 先归因再排序：按**「不修就没法真写」**排，不按工作量排。指令里必须写一节「这批不做 + 理由 + 什么时候做」，否则你会以为你漏了，见 `references/01-派单与指令.md` |

| **★★★★★ 队列粒度 ≠ 执行粒度 → 「第1件完成」打了整批的勾** | 2026-11-19 实测：队列写 **1 条**「v8 第一批」，但用户中途把要求改成「逐件确认」——4 件，每件汇报后停。WB 做完第 1 件，memory 写「10:41 第1件完成：角度定位器」，`wb_watch` 把**整条**打勾。后果：cron 以为整批做完了，WB 还在做第 2 件，**后面的改动全在监控盲区**。用户看到的现象是「`_给WB.md` 的 md5 在 10:40 变了，不是我改的」——他会怀疑有人手改 | **队列的一条 = 执行方汇报的一次。** 指令里只要出现「逐件确认 / 分几步 / 每件汇报后停 / 第 N 件」，队列就必须拆成同样多的条，一件一个勾。<br>★ 判据：**队列条目的「完成」，必须正好对应执行方会写「完成」的那一次。** 一条对应四次汇报，必错。<br>★★ 拆完的额外好处：第 1 件的报告和第 2 件的条目标识符对不上，`match_done` 自己就不会误打（见下一条）。<br>★★★ 拆的时候「整批」那条**不要留在 `✅ 已完成`**（会让人以为整批做完了）—— 移到 `⏸ 已被取代` 并注明「已拆成 N 件」，原文保留备查。<br>★★★★ 反向教训：**先定执行粒度，再写队列。** 用户临时改「逐件确认」时，第一动作是回头改队列，不是等它误打勾再来修。 |
| **★★★★ 完成信号词太宽：「改完」会命中「改完做 X」；ASCII 标识符分支零阈值** | 同一次实测的完整链路：WB 在 memory 写「改前 md5 已记录……**改完**做 py_compile + node --check + md5 复核再汇报」——语义是「改完之后要做什么」，**还没做完**。但「改完」在 `DONE_SIGNALS` 里 → 直接当完成信号；再叠加 `match_done` 的 **ASCII 分支原本没有阈值**（中文分支有 ≥4），跟任务条目共享 `build_board.py` / `board.html` / `md5` / `py_compile` 任意一个就满足 → 打勾 | ① **「改完」→「改完了」**（要求后面跟「了」）。同类要小心的：「已生成」（模板生成 ≠ 交付）、「跑通」（跑通一次 ≠ 做完了）。<br>**判据：任何能出现在「计划/步骤描述」里的词，都不能当完成信号。**<br>② ASCII 分支加 `best_score >= 2`。为什么是 2 不是更高：纯中文任务走阈值 4 那条分支；能走到 ASCII 分支的，两个具体标识（任务名 + 文件名）同时出现已经是很强的一致性要求。<br>③ ★ 副作用要知道：`DONE_SIGNALS` 里**没有**「完成」二字（只有「已完成」），所以「第 N 件完成」这种写法**不会**触发自动打勾 —— **让执行方写「第 N 件已完成」，多一个「已」字就能自动打勾。**<br>④ **验证方法：拿真实 memory 原文跑四个场景**（真实报告 / 假设真做完 / 无关报告），断言「该响的响、该静的静」。只跑「真做完」一个场景，测不出误报。<br>★★★★ 这里宁可漏、不可错：漏了人工补一次，错了会让整套监控静默失效。 |
| **★★★★★ 24 项自检全绿，但新用户第一分钟就找不到入口** | 2026-11-19 实测。`selfcheck.py` **24 项全过**（标题/板块顺序/关键元素 18 个/已删 5 处/脚本能力 17 项/数据健全/文本卫生/只读源 md5）。但写作区上方那句提示写着「**在上面点『写这篇』**，选题会带到这里」—— <br>① 按钮实际叫「**写这个**」<br>② 素材池在写作区**下面**，不在上面<br>③ 点它**不直接进写作区**，先 `calPrefillFromAngle` 预填月历排期表单<br>代码注释自己写着：`silent：不滚动、不抢焦点，好让你停在下面的排期表单上` —— **用户点完停在排期表单，不知道写作区已经备好了** | **自检清单能查「元素在不在」「字段全不全」，查不了「用户找不找得到」。** 四个可执行动作：<br>① **断言提示文案里提到的按钮名真实存在**：`grep -o '<button[^>]*>写这篇</button>'` 必须 ≥1，否则这句提示就是撒谎<br>② **断言方向词**：「在上面 / 在下面」这类词要与 DOM 实际顺序一致（板块顺序可以用 `grep -oE '<h2[^>]*>[^<]*</h2>'` 拿到）<br>③ **多入口逐个走**：有 N 个入口就要有一条验收「入口 A/B/C 分别点一次，都能到达同一个终点吗」，以及「哪一个是最近的」<br>④ **`silent` 型交互必须给可见回执**：点了不跳转可以，但要让用户看见「上面已经准备好了 →」<br>**★★★ 让执行方自己在汇报里加一问：「一个没看过这个页面的人，第一分钟会点哪里？」** —— 它写不出来，就说明有可发现性缺口，而且这一问自检脚本永远替代不了。<br>**★★★★ 泛化：`可达 ≠ 可发现`。** 路径通（哪怕 1 步）不等于用户知道该点哪。空白格子里什么都没写、提示指向不存在的按钮、点完没回执 —— 这三种最典型，而它们全都能通过「元素齐全」类自检 |

| **★★★★ 改产物不改生成器 → 下次生成静默退回旧版本** | `board.html` 是 `build_board.py` 生成的产物。想改一句文案，直接改 html —— 当时看着是对的，**下次跑生成脚本就被覆盖，而且不报错、不提示、页面上只是悄悄变回旧的**。用户过几天回来会问「我说的那个改动呢」 | 判据：**文件头或 mtime 规律表明它是产物时，一律改生成器 + 重跑**。<br>★ 验收要搜**旧文案 = 0 处**（不是「新文案在不在」，是「旧的还在不在」）—— 两个方向都查才知道换干净了。<br>★★ 交付前顺手看一眼产物和生成器的大小关系（`board.html` 1.6MB / `build_board.py` 158KB）—— 一个大产物配一个生成器，就不能改产物。<br>★★★ 同类：Excel 报表、静态站、代码生成的图表、`*.min.js`。凡「有源文件和产物两份」的，只改源 | 
| **★★★★★ 数据之间用「位置/序号」绑定 → 插入一条，全部错位** | 150 个角度按序号绑定账号：`MAP = {1:"ZG", 2:"ZX,ZG", 3:"WG,DX", …}`。素材库前面插一条新素材（或 cron 早上自动摄取一条），**后面 150 条标注全部往后偏移，看板推荐到错误的人**。<br>**最难发现的地方**：它不报错、页面能打开、数字还能对上 —— 只是「这一条角度推荐给谁」全错。而且错位从「多了一条」那一刻就开始了，可能一天没人发现 | **用内容对应（标题 + 文本、稳定 ID、哈希），不用位置对应。**<br>暂时只能按序号时：**新条目一律追加到末尾，绝不插到最前面**（`最新在前` 这种排序是给眼睛看的，不能同时当数据键）。<br>★★★ 校验也别写「必须等于 150」，写「**三份数据彼此对齐**（角度数 == A 表行数 == B 表行数）」—— 写死数字的代码每加一条就坏一次，而它坏的时候不会告诉你。<br>★★★★ 判据：**凡是「A 的第 N 个 对应 B 的第 N 个」的设计，问一句「中间插一条会怎样」** —— 答案是「全错」，就不要这么设计 |
