# 把这个模式画成一张图

> 从 `SKILL.md` 拆出（2026-11-15）。

---

### 0.2.1 ★★★★ 被要求「把这个模式画成一张图」时怎么做

**2026-11-15 他的原话：「你把这个主 agent + 工作 agent，以及相关的 cron 的整个流程，做一个可视的 html」。**

**★ 这不是文档任务，是【把分散在多轮对话里的机制，收成一张能独立看懂的东西】。**
判断标准：**一个没参与这些对话的人，能不能看这一页就明白自己以后会收到什么、需要做什么。**

**模板：`templates/mechanism-diagram.html`（白底单文件，九节，可直接改内容）**

#### 九节骨架（顺序就是认知顺序，别乱）

```
01 几个角色，几件不能互换的事      ← 先立分工，否则后面每一步都要解释"为什么不是它干"
02 一次任务，从开口到收工          ← STEP 1–N，把 cron 画在【流程中间】
03 监听器的 N 种输出               ← 每种配【真实推送原文】
04 自动判断为什么只给三段不给结论    ← 设计理由（从自己的错误里来的）
05 数据在哪 —— 只有一份            ← 文件树，标出「谁有写权限」
06 判据怎么定 —— 宁可漏不可错       ← 表格：条件 / 规则 / 为什么
07 成本                            ← 0 token 的部分要单独列，那是它敢高频的原因
08 踩过的坑                        ← 每条写【代价】，不写"已优化"
09 这套东西到底在解决什么           ← 一句反问 + 用户还剩哪两个动作
```

#### ★★★★★ 三个反直觉的设计决定（价值都大于排版）

**① 把 cron 画在流程【中间】，不是画成一个旁边的小方块**

```
✗ 左边三个角色，右边一个"cron 定时任务" → 读者以为它是外部工具
✓ 插在「执行方写完 memory」和「用户收到结果」之间，标成流程的一环
```

**★★ 因为它不是旁边看着的工具，它是这条链上的一环 —— 少了它，前面的活没人收，后面的判断不会发生。**

**② 每种输出贴【真实推送原文】，不写「会通知你」**

```text
✗ 「任务完成时会有提醒」
✓ ▶ 内容看板@WorkBuddy　WB 动了（队列还剩 1 条）
  　　开始改：先把三个按钮的 color 改成 #C4362F
```

**★★ 用户看图的目的是「以后我知道会收到什么」，抽象描述做不到这一点。**
**★★★ 直接从他真实收到的消息里复制 —— 这一类内容【不许编】，编出来的示例会让他以为是承诺。**

**③ 每个坑写【代价】，不写「已修复」**

```text
✗ 「自动打勾可能误判 → 已优化匹配逻辑」（读者不知道严重程度）
✓ 「连跑 6 次全静默，而我以为它在正常工作 —— 
   成本是"你以为做完了其实没做"，比"你多问一句"贵得多」
```

**★★★★ 因为「为什么判据定成这样」只有讲了错的代价才说得通。**
**省掉代价，读者会以为那些约束是洁癖。**

#### 视觉（沿用他一贯的偏好，不是新发明）

```
✓ 白底 / 深色字 / 单文件 / 零外链 / 双击就开
✓ 状态用灰阶，不用红黄绿（那是告警色，流程状态不是好坏判断）
✓ 全部展开，可复制文本（同 project-portfolio-monitoring §3.7 ⑤）
✗ 深色底、渐变、发光、卡片阴影
✗ 动画
```

**★ 一页之内放不下就分节，不要折叠** —— 折叠会让读者漏掉「他需要做什么」那一段。

#### 交付前自检三条

```
① 外链 0（grep http:// ）—— 他可能断网/离线看
② 九节标题逐个念一遍，看有没有一节是空话
③ ★ 最后那一节必须回答「用户还剩哪几个动作」—— 
   否则整页看完他不知道自己要干什么
```
