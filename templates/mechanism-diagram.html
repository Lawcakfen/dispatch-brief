主 Agent + 执行 Agent · 协作机制

模板 · 把 <用户名> / 主 Agent / 执行 Agent 换成你自己的名字与工具

怎么用这个模板

前提：这个文件假设你的执行 Agent 没有 API、只能人工粘贴。 如果你的执行方能直接调 API，这套复杂度里有一大半用不上 —— 先读 SKILL.md 的适用范围。

用 VS Code 或记事本打开这个 .html 文件，按 Ctrl+F 搜 <（小于号）。 全文一共 40 处，分四类，换法不一样：

第 2 步验一遍
再搜一次 < —— 剩 0 处才算换完。然后双击打开，看有没有下面这两种情况：

· 本该显示项目名的地方，是空的 → 说明尖括号被浏览器吃掉了，回源码补 &lt; 转义
· 本该是示例文字的地方，变成了命令 → 说明那个位置不是占位符，改回去

另外两件要知道的：
· 「五种输出」那一节的文案是真实推送原文改的，可直接对照你实现的输出看
· 「三个坑」写的是代价，不是「已修复」—— 保留这个写法，否则下次踩了不认得

01三个角色，三件不能互换的事

用户

最终判断 · 唯一的接口

  • 提需求、说清要什么
  • 拍板（做不做、停不停）
  • 把指令复制给 执行 Agent
  • 提供真实数据（发布日期、曝光量）
  • 写完再看、用完再说哪里别扭

只有你能做：判断该不该做、哪个角度该发哪个号、这件事值不值钱。
没有任何 Agent 能替你拍板。

主 Agent

Router · 判断 / 口径 / 验收

  • 把需求翻成可执行的指令（八节骨架）
  • 做标注类判断（150 条账号、150 条类型）
  • 独立验收，不采信自报
  • 维护队列、项目卡、看板数据
  • 写 cron，跑判断

只有我能做：知道你的口径、知道哪条内容不该发、知道 执行 Agent 会在哪一步偷懒。

执行 Agent

Worker · 执行 / 量产 / 视觉

  • 写代码、改页面
  • 跑脚本、生成产物
  • 写 memory 汇报做了什么
  • 发现指令冲突会主动报

它做不了：判断内容该发哪个号、判断一个项目该不该停、判断什么值得写。
它没有你的业务上下文。

03cron 的五种输出

① 什么都没发生
不推送任何消息。静默是默认状态，不是故障。 （stdout 为空 → 不推送）
② 它开始动了
memory 出现新内容，但还没写完成信号。每个派单周期只报一次。 ▶ <项目 A>　执行 Agent 动了（队列还剩 1 条） 　　开始改：先把三个按钮的 color 改成 #C4362F 　　（这是开场信号，还看不出做完没有）
③ 它做完了 ★
队列某条被打勾（- [ ] → - [x]），然后起一次独立判断。 ✅ 完成了：<项目 A> 　　<某一批交付> 【看起来完成了什么】 【你该自己核这几点】 【下一步建议】
④ 它卡住了
派单满 4 小时，memory 一个字没动。只报一次。 ⚠ <项目 B>　派单 4.0 小时，memory 无新增内容 　　队列还有 1 条待发 —— 检查 执行 Agent 是否收到指令
⑤ 队列被外部改了
待发条目消失，但不是 cron 自己打的勾 —— 通常意味着 执行 Agent 抢着打勾了。 ⚠ <项目 A>　队列被外部改了：「<某一批交付>」从待发消失 　　★ 这轮没触发验收判断。改回 `- [ ]` 放回待发，15 分钟内会自动判断

04判断为什么只给三段，不给结论

judge.py 起一个独立 session（hermes -z + file/terminal 工具），真去读文件、真去跑命令

【看起来完成了什么】

基于它实际读到的内容，用自己话说清动了什么。文件内容和 memory 对不上，直接指出。

【你该自己核这几点】

2–4 条能直接执行的动作。要具体到查哪个文件、看哪个字段、跑哪个命令 —— 不写「检查是否正常」这种没法执行的话。

【下一步建议】

一句话。还有下一条就说哪一条；这是最后一条，就说这个项目缺什么才能继续。

★ 为什么不给「通过 / 不通过」： 2026-11-14 一天里，主 Agent 人工核 执行 Agent 交付误报了三次 —— 全是自己的验证工具错（正则跨对象、textContent 读 input、脚本被换行撑断）。 自动化以后没人复核，误报会直接推到用户面前。所以它只干「把该核的点列清楚」这件它擅长的事，结论归人。

06「完成」怎么判 —— 宁可漏，不可错

条件 规则 为什么
① 完成信号 memory 里必须出现：已修 / 已完成 / 已上架 / 已交付 / 自检通过 / 落地 「查了一下发现不能用」算探路，不算做完
② 对上号 ASCII 标识符重合 ≥ 1 个
或 纯中文短语重合 ≥ 4 个		 两个条件缺一不可，都对不上就漏着
阈值 4 怎么来的 实测「真命中」重合 10 个、「无关的完成」重合 3 个 —— 4 刚好分开 宁可漏打勾，不可错打勾
一次最多打几个勾 MAX_TICKS_PER_SCAN = 3 防一次刷太多，出问题能一眼看见
卡住阈值 STALL_HOURS = 4 少于 4 小时可能是正常在改
判断占锁 判断跑 104–190 秒。拿不到锁 只报事实、不给判断，绝不阻塞 10 分钟僵死自动清锁

08三个坑（都是实测踩出来的）

① 执行 Agent 会自己打勾，然后 cron 就瞎了

它把 <队列文件名>.md 当成任务清单，做完顺手打勾、还把报告贴进去。cron 只看「⏳ 待发」段 —— 条目被移走就永远不触发判断。

11-15 实测：连跑 6 次全静默，而它其实做完了两次。我还一度以为是「自动打勾跑通了」，其实是它抢在我前面。

修：队列开头写明文规矩（只写 memory，不许动队列）+ 加「外部改队列检测」—— 条目消失但不是自己打的勾，就报警。

② 判断跑得快，是因为它读不到文件

第一版只给相对路径 + 字节数。judge 想读内容却找不到，只能说「全盘搜索无结果」，然后靠时间戳猜 —— 看起来在判断，其实在编。

修：传绝对路径，并在 prompt 里明确要求「真的去读文件、真的跑一遍验证」。

③ 判据太松，会把无关的完成当成真完成

早期阈值取 2，「改圆角」和一件无关任务也能对上 —— 一次误判了<客户>两条，队列变 0 条。

修：阈值取实测值 4。代价是漏 —— 而漏的成本是「你多问一句」，错的成本是「你以为做完了其实没做」。两者不等价。

09这套东西到底在解决什么

过去你得盯着 执行 Agent —— 它做完没有？做成什么样？下一步干什么？
现在你只需要派单，然后等我说话。

它做完了我会告诉你三件事：看起来完成了什么、你该自己核哪几点、下一步干什么。
它卡住了我会说。它偷偷改了队列我也会说。其余时候我不出声。

★ 唯一还需要你的两个动作：把指令复制给 执行 Agent，和拍板。
前者因为 执行 Agent 没有 API，省不掉；后者因为不该被省掉。
