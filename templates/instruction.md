# WB 指令模板（每次出指令照这个写）

> 2026-11-15 建。**模板本身不是指令，别整篇发给 WB。**
> 用途：我（Hermes）出下一批指令时照这个骨架写，保证不遗漏。
> 来源：2026-11-14/15 两天从 v1 到 v5.1 共 6 轮迭代，踩过 4 次坑。

---

## ★★★ 每一份指令必须包含的两句话

### ① 边界：WB 只写 memory

```
★★ WB 注意
你只写 <工作日志目录>/YYYY-MM-DD.md。
**不要修改 _给WB.md** —— 包括打勾、包括把你的完成报告贴进去。
打勾和验收由 Hermes 的 cron 自动完成（每 15 分钟）。
你做完就停，等结果。
```

**★ 为什么必须写：**

```
2026-11-15 实测：WB 把 _给WB.md 的条目自己打勾、还把报告贴进去
→ cron 只看「⏳ 待发」段，条目被移走 = 永远不触发验收判断
→ 连跑 6 次全静默，而它其实做完了两次
→ 我还一度以为是「自动打勾跑通了」，其实是它抢在我前面
```

### ② 冲突时怎么办

```
★ 指令内部如有冲突（比如「只改文案」和「日期按实际算」），
  按**带理由、更具体**的那条执行，并在 memory 里写一行说明你选了哪个、为什么。
```

**★ 为什么必须写：** WB 两次遇到冲突，两次都主动报出来并做了合理选择。写上这句，它就不会卡住。

## 八节骨架

```
一、动手前　　　备份哪个文件（build_board.py → build_board.vN.bak.py）
二、改动范围　　做什么 + ✗ 不做什么（逐条列，防扩展）
三、具体改法　　正则怎么匹配、字段怎么取、代码长什么样
四、视觉要求　　✅ 允许 + ✗ 禁止清单，且每条禁止都要给理由
五、交互　　　　只做这些 + 不做哪些
六、验收清单　　可勾选的方框，每条都能动手验
七、出错时　　　每种异常怎么处理（★ 优先「显示空状态」不要「显示假数据」）
八、交付回报　　三件事，其中至少一件要求「必须实测，不要写应该正常」
```

## 五种好用的句式（实测有效）

```
① 「必须正好 150 行，对不上就退出码 1，不许猜」
   —— 给它一个可验证的数字，它就会去验

② 「宁可显示「待补」，不要显示一个假数字。进度条撒谎，比空着更糟」
   —— 明确告诉它降级怎么做

③ 「交集为空要显示「没有候选」，不许退回全部」
   —— 防止它用「兜底」把筛选做成假的

④ 「★ 只清首尾，中间不动」这类边界要写死
   —— 我写过一次「中间的 ** 保留」，结果纯文本渲染里全是脏字

⑤ 「这一项必须实测，不要写应该正常」
   —— 它真的会去跑，还会把输出贴回来
```

## ★ 三件我一直犯的错（写进模板防再犯）

### ① 先验自己的验证器

```
2026-11-14 一天里，我核 WB 交付误报了三次：
· 说「对照表只有 131 行」→ 是我的脚本被换行撑断
· 说「账号绑错 4 个」→ 我的正则跨了对象边界
· 说「标题框是空的」→ 我用 textContent 读 <input>
三次全是我的工具错，不是它的代码错。
```

**★ 结论：验别人的东西之前，先跑一遍自己的验证脚本看它是不是可信。**

### ② 不要用「往往/通常」的直觉写判据

**★★ 我写过 `has_self` 匹配「自己」，结果「他自己写的那一版」被当成第一人称。**

**★★★ 判据要能举出反例后还能站住才算数。**

### ③ 数据结构写进约定，别写进代码

**★★★★ `角度-账号对照.md`、`角度-类型对照.md`、`内容/*.md` 的 frontmatter —— 都是「人能改的约定」。**

**★★★★★ 一旦写死在代码里，你想改就得找我，那是失败的设计。**

## 交付后我方要做的三件事

```
① 独立核对，不采信 memory 自报
   ★ 对着它的断言一条条验，尤其数字

② 查它有没有越界
   ★ 文件 mtime 有没有碰不该碰的（数据源、队列）

③ 更新项目卡
   python project_watch.py --set "项目名" --now "..." --advice "..."
```
